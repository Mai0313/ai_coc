# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Windows-only PyQt5 desktop application that drives Clash of Clans running inside MuMu Player 12. **The screen is read by the parsers and Gemini answers three narrow questions**, which is the other way round from where this started: the loops match templates and colours off the frame themselves, and ask a model only where the walls or buildings are on the map (`GameRunner._spotted`), which building a menu belongs to (`upgrade`'s lite tier), and how to attack an opponent that already passed the loot thresholds (`_plan`, once per battle). Everything else — prices, card counts, storage bars, which of the two villages is up, whether a drop landed — is pixels. See **Attack loop** below for why, and **Finding things** for the one job a glance still beats a reader at.

An agent loop used to sit over all of it, screenshotting and asking Gemini which pixel to tap next; it went with the AI 助手 tab, and the 主控 tab now runs the same `commands.*` functions the CLI does.

## Driving the game

Four skills under `.agents/skills/` own the judgement this file deliberately does not: what to run, when to step in, when to stop, and how a long command is run and watched. They are read into every session that farms, tunes or builds here, and **they are the only copy of those rules**: this file says why the code is the way it is, the skills say how to drive it, and a rule written in both places drifts.

- **`farm`** — run the loops and judge them. Owns the farming cycle (full storages → spend the loot → farm again), which the code deliberately does not close: `stock_full` is a seam, not the end. Every stop condition and every authorisation rule for spending lives there.
- **`spend-loot`** — turn the loot into progress: walls, buildings, heroes. Leads with `ai_coc walls` / `upgrade` / `hero`, which find their own targets; looking at the screen yourself is its fallback, and the only way to upgrade anything on the builder base.
- **`tune-attack`** — farm and improve the attack in the same run, measurement first.
- **`build-feature`** — find what the game still does by hand, and automate it.

`.agents/skills/farm/references/running.md` is shared by all four and owns the mechanics: which commands run in the background and which in the foreground, why a subagent has to block instead, what `result.json` looks like, how a loop is stopped and when that is safe, and the rule that a session needing the live game stops the loop itself and starts it again afterwards. None of that is restated here.

**Every session that works on this code farms while it works, and it farms through a subagent.** That is the user's standing instruction rather than a nicety: the thinking, the edits, the test-suite runs and the review rounds are all time the emulator could be spending on a battle, whatever the task is — a bug fix, a doc change and a new feature leave it idle the same way, which is why the rule is here and not in any one skill. The farming is delegated rather than held because `farm` is a judgement loop and not a command: `stock_full` hands over to `walls`, a village that stops earning hands over to the other one, a stop has to be told apart from a finished run, and **both villages are farmed**, the builder base as much as the home village. Every one of those seams held in the main session interrupts the work at hand and fills its context with log reading, so the main session spawns **one** subagent running `farm` — in the background, named so it can be messaged later, **one model step down, no further, and with a lowered thinking budget** wherever the runtime offers the choice — how far to lower it is the spawning session's call, since the user has not fixed a level — and told that it is a subagent, so it blocks the way `running.md` says — and keeps its own context for the change. The smaller model is the measured answer rather than a saving: the skill carries the judgement in writing (what ends a run, what is spent and in what order, when to change villages), so what the model does is read a log and follow it, and the user has watched a small model handle the whole loop well. The bigger model stays on the work that has no skill to follow.

What the subagent cannot do for it is share the screen. There is one emulator, so a live test and the loop cannot both drive it, and the main session **takes the game whenever a test needs it and gives it back afterwards, without asking either time**. Taking it is `ai_coc stop`. The loop finishes its battle and exits, the subagent sees a stop it did not issue and, per `running.md`, reports where it got to instead of restarting — and **that report arriving is the signal that the screen is free**, not the `stop` command returning. A stop that lands in the gap between two of its commands is erased by the next one's claim, so a report that has not come after a battle's length means stop again, and `~/.ai_coc/state.json` still reading `stopping` means the loop simply has not reached a seam yet. The test in between usually wants a battle, against a village the farming has just filled — which is exactly the village `stop_at` stands a run down on, so `--stop-at 0` exists for it. Giving the game back is a message to the same subagent, whose context still holds the baseline and how far it got; a fresh one, told where the last one stopped, when it is gone. Saying so in the reply matters, because the user cannot see either agent's output and the one thing they are watching is whether the machine is farming.

## Commands

```bash
uv sync --group test                 # the suite needs the `test` group
uv run pytest                        # full suite (xdist, coverage gate, JUnit/XML into .github/reports)
uv run pytest --no-cov tests/test_core.py::ScoutTests::test_loot_is_read_over_grass   # single test; the gate is in addopts and a partial run cannot meet it
make fmt                             # pre-commit: ruff, mdformat, codespell, ty, gitleaks, uv-sync/lock
make gen-docs                        # rebuild docs/ from the READMEs and the source
```

Run the app with `uv run ai_coc`, which takes no flags of its own: the two that existed, `--live-test` and `--agent-command`, were smoke tests against the AI 助手 tab and went with it. What replaced them is that **the window runs the sub-commands below rather than anything of its own**, so a smoke test against the live game is one of them run from a terminal.

Fifteen sub-commands run headless instead, and they are how the game is worked on:

```bash
uv run ai_coc attack --record            # one attack pass, every frame it reads kept
uv run ai_coc attack --plan-in tuned.json  # play a written tactic, no AI call at all
uv run ai_coc attack --plan-out used.json  # write down whichever plan actually ran
uv run ai_coc attack --min-gold 0 --min-elixir 0 --min-dark 0   # attack whatever comes up first
uv run ai_coc attack --repeat 0            # keep attacking until stopped
uv run ai_coc attack --restart-every 0     # skip this run's scheduled emulator restart
uv run ai_coc attack --stop-at 0           # attack however full the storages are, which a test against a farmed village needs
uv run ai_coc attack --record --shot-every 4   # plus a frame every four seconds
uv run ai_coc stop                        # ask whatever is driving the emulator to finish this battle and stand down
uv run ai_coc walls                       # spend the storages on walls until they will not stretch
uv run ai_coc walls --keep-elixir 2000000  # leave that much behind for an upgrade already chosen
uv run ai_coc walls --at 260,260          # start from this wall, skipping the village scan
uv run ai_coc collect                     # empty every collector that has something waiting
uv run ai_coc builders                    # what each builder is on, and how long it has left
uv run ai_coc upgrade                     # put the idle builders on the dearest upgrade affordable
uv run ai_coc upgrade --at 900,430        # this building is a candidate, skipping the search
uv run ai_coc upgrade --only 金礦          # only a building whose name contains this
uv run ai_coc donate                      # give troops to whoever in the clan is asking
uv run ai_coc donate --dry-run            # walk the whole path and stop before giving anything
uv run ai_coc hero                        # what raising each hero next would cost
uv run ai_coc hero --upgrade duke         # put a builder on that hero
uv run ai_coc view --zoom out             # put the camera back at the far zoom everything was measured at
uv run ai_coc world                       # which of the two villages the game is on
uv run ai_coc world --go day              # sail to that one; already being there does nothing
uv run ai_coc launch                      # start the emulator if it is down, and bring the game up on it
uv run ai_coc launch --restart game       # relaunch the game alone, leaving the emulator running
uv run ai_coc launch --restart emulator   # restart the emulator, then bring the game up again
uv run ai_coc read <png>                  # what each parser makes of one frame
uv run ai_coc export                      # get the whole village out of the game, named
uv run ai_coc export --table              # the same, drawn for a person instead of piped
uv run ai_coc export --last               # the last one, off the disk, without touching the game
uv run ai_coc capture --count 30          # a burst off the live game, into this run's own directory
uv run ai_coc walls --label tuned         # name this run's directory; every sub-command takes it
uv run ai_coc probe --record             # spend a battle measuring the real boundary
uv run ai_coc bounds --record            # spend a battle measuring where the map ends
```

**Running real attacks to gather evidence is cheap, so do it rather than reasoning from one sample.** Training troops costs nothing in current Clash of Clans and the search fee is negligible, and neither does a battle that goes badly or deploys nothing at all — a run spent entirely on probes is a normal thing to spend, not a mistake to apologise for. The only real budget is the wall-clock time an army takes to train, and `MIN_ARMY_RATIO` backs a run out for free before the fee when it is not ready. `--repeat` is what makes that budget the only one that matters: five rounds back to back is a normal thing to spend and one battle is not evidence, because the opponent varies more than anything being changed. A round that fought nothing waits `IDLE_REST` for the barracks rather than walking the same menus again.

**Every run gets its own directory, and both sides of the app use the same one** (`RunLog`, `~/.ai_coc/logs/<when>-<what>/`). It holds `run.log` (this execution and nothing else), `result.json` (what the command answered), `frames/` when asked for, and — for `ai_coc attack` — `plans.jsonl`, one line per round holding the tactic that round played. **One file rather than one per round**: `--repeat 0` runs until it is stopped, so a night of farming is a hundred rounds or more, and a hundred small files is a directory nobody opens. Each line carries its own round number so it lines up with `run.log` and `result.json`, and a single round comes back out for `--plan-in` through `jq -c 'select(.round==2).plan'`. **The log is unconditional where `frames/` is not**, because a plan is a few hundred bytes written once a battle against a PNG encode for every frame a loop reads, and because nothing else can answer which line a given round drew: `run.log` carries a one-line summary, `--plan-out` keeps the last round and overwrites the rest, and a drop is over inside the gap between two captures. The window writes one too, now that every pass it runs is a `commands.attack` call rather than a direct drive of `AttackRunner`; a pass is one round, so its file is one line long. **There is no second file collecting every run together.** A rotating `controller.log` sat beside these for a while, on the reasoning that it answered a different question — what this machine has been doing rather than what one run did. It cost every record written twice, and what it bought turns out to be available without it: the directories are named `<when>-<what>`, so a plain listing already is that history, and `grep -r ~/.ai_coc/logs/*/run.log` answers across runs while naming which run each hit came from — which the merged file could not. The first line of every run says which directory it is, since one nobody can name is one nobody goes back to. **This existed as a convention before it existed as a feature** — the skills told a session to build the directory with shell redirection, so the layered evidence was available only to the reader who could have built it anyway, while a person running the CLI by hand or using the window got a rotating file and nothing else.

**A run's directory can be named, and its frames age out** (`--label`, `FRAME_RETENTION_DAYS`). `capture` used to take the directory to write into as a positional argument, and it was the one command writing outside its own run while already having one — so every session invented a path. Measured before this landed: `~/.ai_coc/` held five directories nobody designed, and 20 of 438 run directories were hand-named, four of them ending in `.png` because somebody read that argument as a filename, with `subagent_baseline` and `subagent-baseline` both present. What the naming was actually for is finding that run again, so **`--label` does it on every sub-command** and the directory becomes `<when>-<what>-<label>`; anything that is not a letter, a digit, an underscore or a hyphen is replaced, since a separator getting through would put the run somewhere nobody goes looking, which is the failure being replaced rather than one to reproduce in a new place. **Culling only ever takes `frames/`**, and the size split is what makes that easy to draw: those same 438 runs held 11 456 PNGs at 27.2 GB against 4.6 MB for every `run.log`, `result.json` and `plans.jsonl` together. The directory names are the history and `grep -r` over the logs is how a pattern is found across runs, so those stay; a week-old frame nobody has opened is the whole of what costs. It rides on `RunLog.open` rather than living in a command of its own, because nobody would remember to run one, and it never fails the run it rides on — a frame it could not delete is worth less than the run it would have taken down.

`--record` is what fills `frames/`, and it is off by default because it is not free: a frame is a PNG encode on the emulator, and a run of twenty battles is a few hundred of them. The window has the same switch as a checkbox. It names each capture for what the loop was asking (`0006_probe`, `0010_pass`, `0018_dropped`), which afterwards is the only thing separating a frame the parser misread from a tap that never landed. The card readers make those frames answer more than they used to: `before-drop` and `dropped` are a pair, so whether a hero really went down is settled by comparing them rather than by trusting the log line. `--shot-every` adds the other view alongside them, `tick_00012.3s.png` named by how far into the run it was taken: the loop only looks where it has a question, and a battle that went badly between two of its captures leaves nothing behind without this.

Distributables are built in CI only: pushing a `v*` tag runs `build_release.yml`, which publishes the wheel to PyPI and attaches a PyInstaller Windows build to the release. There is no local build script.

`scripts/gen_version_file.py` writes `version_info.txt` from the resolved version just before PyInstaller runs, which is what puts a version into the executable's Windows file properties. That file is gitignored: a committed copy could only go stale.

That build defaults to `--onedir`, and the dispatch form's `package_mode` switches it to `--onefile`. Measured here, onefile costs 6.6-7.0 s to reach the first log line against onedir's 1.4-3.1 s, because it unpacks the whole bundle into a temp directory on every launch. Onefile is one 76 MB file where onedir is a 174 MB folder, so it stays available, just not the default.

## Architecture

`src/ai_coc/cli.py` is the entry point behind both console scripts (`ai_coc` and `cli`) and the PyInstaller build. PyInstaller runs it as `__main__`, so its imports stay absolute even for same-layer modules and it keeps an `if __name__ == "__main__"` block.

The three layers are directories, so an import that crosses them is visible in the import line:

- **UI and orchestration** — `ui/main_window.py` (`MainWindow`), all four tabs plus every workflow; `ui/workers.py` (thread-pool workers and the log handler); `ui/render.py` (log records to HTML). The loops are kept Qt-free so they can be driven and tested without the window: `ui/attack.py` (`AttackRunner`, the farming attack loop), `ui/world.py` (crossing between the two villages), and `ui/walls.py`, `ui/upkeep.py`, `ui/clan.py`, `ui/hero.py`, which are `GameRunner` subclasses from `ui/runner.py`. `cli.py` is only argument parsing and `main()`, and `commands.py` is the headless side it dispatches to: a feature reachable only through a widget cannot be run against the live game while it is being worked on, so new work belongs somewhere `commands.py` can call it.
- **Adapters** — `adapters/mumu.py` (emulator lifecycle), `adapters/adb.py` (every ADB call), `adapters/ai.py` (Gemini), `adapters/secrets.py` (DPAPI), `adapters/config.py` (the shared settings file), `adapters/database.py` (SQLite), `adapters/mapping.py` (the community `data_id` table), `adapters/clipboard.py` (the Windows clipboard, which is where the game's own village export arrives).
- **Pure parsers** — `parsers/frame.py` (the 1600x900 frame every reader decodes through, and the size check that refuses any other), `parsers/village.py`, `parsers/scout.py` (the loot panel, the card row, the storage bars, and which of the game's screens is up), `parsers/building.py` (every building menu, its prices and its dialogs, which is what the wall loop reads through), `parsers/home.py` (collector markers and the builder panel), `parsers/boundary.py`, `parsers/field.py`, `parsers/clan.py`, `parsers/hero.py`, `parsers/world.py` (which of the two villages is on screen), `parsers/settings.py` (the two settings pages the village export sits behind), plus the two below that are techniques rather than screens.
- **Data shapes** — `models.py` at the package root holds every Pydantic model in the project; see the Pydantic rule below.
- **Prompts** — `prompts/*.md`, one file per prompt, loaded once into `PROMPTS` and filled in by `render`. A prompt is content rather than code: it is reworded far more often than the code around it, and a wall of quoted Chinese inside a module hides both. Each file is a `str.format` template, so a literal brace has to be doubled. They ship in the wheel because `[tool.hatch.build]` includes the package directory, and into the PyInstaller build through the packaging rule below.

**Two parsers are machinery rather than screens, and every other reader is built out of one or both.** `parsers/glyphs.py` reads a number by matching each digit against ten bit-pattern templates; `parsers/regions.py` finds the connected patches of one colour and measures each of them. Both used to sit inside a module named for a screen — the digits in `scout`, the patches in `home` — so four readers reached into those two by private name for machinery that was never theirs, and the module that happened to hold it looked like its owner. What stays with a screen now is only that screen's own constants: which box to crop, what counts as ink there, how far off a template a glyph may sit.

Imports across layers are absolute (`from ai_coc.models import …`) and within a layer relative (`from .adb import …`); Ruff's `TID252` enforces it and rewrites the rest.

**The game keeps two villages and reopens on whichever one it was closed on** (`parsers/world.py`, `ui/world.py`, `ai_coc world`). The home village and the builder base are separate maps with separate buildings, separate resources and separate attacks, joined only by a boat moored at one corner of each. So no command can assume which it is looking at, and until this existed none of them could tell: **`read_stock` answers on both**, because the builder base has no dark elixir and its gems bar sits at exactly the y the dark row is read from — measured, a builder base holding 10 152 gems reports `dark=410152`, the green `+` beside the number reading as a leading 4. Every loop's own "am I on the village" test therefore said yes in the wrong world, so a `walls` run started after a night session would have swept the builder base and reported it as a village with nothing on it.

**What separates them is the shield.** The home village carries a 護盾 plate in the row along the top and the builder base does not, and structurally cannot: the builder base is real-time matchmaking against a live player, so a shield there would contradict the mode's own design. What is counted is the blue `i` badge over each plate — three on the home village, two on the builder base — because the row is laid out from the middle outwards and so sits at different x in each. Measured, 233 real home village frames all read 3 and 11 builder base frames all read 2, while 4360 frames of everything else — battles, dialogs, the matchmaker, loading — read 0, which is what makes None a usable third answer rather than a failure. It replaced `read_stock` as the village test in `_home` and `_settle_game` on its own merits as well: two of those home frames had the camera at a map corner with the dark row unreadable, so `read_stock` called an ordinary village no village at all.

**Two better-looking candidates were measured and thrown away**, both because they pass on this account today and would break silently later. *The builder base's trophy plate* sits in the top-left corner where the home village shows a league badge, and this account's home village is unranked, so that box is empty there and 4364 recorded home frames read nothing in it — conclusive until the day the account is ranked, after which every home village would read as a builder base. *Counting resource rows* fails outright rather than later: the home village's gems row does not resolve as digits at all, 0 of 237 frames, so there is nothing to count.

**Crossing is a boat and nothing else, and nothing recognises the boat.** The camera clamps at the map edges, so swiping hard at the right corner ends at the same view whatever it was doing before — measured with `view_shift`, the home village stops moving after the second swipe and the builder base after the fourth, and every swipe after that reports (0, 0) — and from that view each boat is at one fixed pixel. A boat is a sprite the game dresses up for events, so it is tapped rather than looked for and the badge count is what says whether the tap worked; a tap that missed leaves the world unchanged and the next candidate spot is tried, which is the pattern `hero --at` already uses. The home village's candidates stay up and left of the measured spot on purpose, because the clan capital's own vessel is moored below and to the right of it, and the builder base's stay left of theirs because the game's right-hand button column overlaps the boat's stern.

**A tap that misses the boat does not miss the ground, and that used to end the crossing** (`uncovered`). Every spot here is a place on the map, so a tap a few pixels out opens whichever building is standing there — and a building panel swallows the swipes and taps that come after it, so the two remaining candidates were spent on the panel rather than on the map. Measured live: a `collect` run left an 8級聖水收集器 panel up, and `ai_coc world --go night` then answered 畫面還停在不明的畫面 twice in a row without moving anything, which is a dead end for whoever is driving. So a spot that did not sail is now followed by `back` if the village stopped reading, and the same step runs before the first swipe, which is what makes a crossing survive arriving on a covered village at all. `back` is safe on exactly these frames for the reason `GameRunner._home` gives: on a clear village it raises 確定退出遊戲嗎, so it is only ever pressed on a frame that is not one. **And never at a battle**, which is why it filters rather than pressing at anything `current_world` will not name: its callers hand it whatever is on screen — `commands.world` goes straight into `cross` on an unreadable frame and so does `_pick_world` when a run named a village — so a game left mid-battle by a killed run, which is a state this project has written down, would take three presses aimed at 放棄. A battle answers None instead, which every caller already reads as "nothing to sail from".

**Threading.** Every blocking call goes through `MainWindow.run_async`, which wraps the callable in a `Worker` (`QRunnable`) on the global `QThreadPool` and delivers the result back to the UI thread via `pyqtSignal`. Never call `MuMuAdapter`, `GeminiClient` or a `commands.*` function directly from a slot. A `run_stream` and a `StreamWorker` sat beside it for a while, draining a generator and emitting each chunk; the only two things that produced text as it arrived were the chat and `--live-test`, so both went with the AI 助手 tab.

**Every pass the window runs is a `commands.*` call, and that is the whole of what the 主控 tab does** (`MainWindow._run_job`, `automation_cycle`). Each checkbox names one of five jobs — `collect`, `donate`, `upgrade`, `walls`, `attack` — and the cycle round-robins whichever are ticked, one pass at a time. The job itself is the same function `cli.py` dispatches to, so a run from the window and a run from a terminal play identically by construction rather than by anyone keeping two copies in step. What is left for the window is the three things a terminal gets from `cli.py` instead: this pass's own `RunLog`, handing the log back afterwards, and starting the next pass.

**The 帳號進度 tab is one button on the same rule.** It had three — an AI-driven 自動取得, a clipboard paste and a file picker — and all three are now `commands.export`, so the window offers 取得村莊資訊 and nothing else. The table under it is filled from the saved export rather than from a fresh one, on open as well as after a run, which is what makes reopening the window free. It went from ten columns to five: `Next`, `Cost` and `Time` came from `entity_levels`, which is empty by the stated product decision below and so drew `—` on every row it ever showed, while `World` and `Category` are derivable from the section and the `data_id`. **This leaves `controller.sqlite3` with no writer but the mapping refresh**, since `_apply_village_snapshot` was the only caller of `Database.save_account`; whether the database is worth keeping at all is a separate decision, deliberately not taken here.

**This is not where it started, and the difference is what the AI 助手 tab cost.** Four of those five used to be sentences of Chinese fed to an agent loop that screenshotted, took a `uiautomator dump`, asked Gemini which pixel to tap next, and did that up to eight times per pass — while `commands.collect` and its three neighbours already did the same jobs by reading the screen. The fifth, the attack, drove `AttackRunner` directly and so **silently lacked four things `commands.attack` does**: `_settle_game` (wait for a village to paint, put the camera back at the far zoom), `_pick_world` (play whichever village is up), `_empty_cart` (the builder base's elixir is in a cart, not the storages) and `plans.jsonl`. So unifying the two sides was not a tidy-up: the window's attack was worse than the CLI's, in four ways nobody could see from the window.

**`rounds=1` on both the attack and the walls is what keeps the cycle a cycle.** Each of those commands is a series driver of its own — `attack` would keep playing until the storages filled, `walls` until neither storage would pay for another batch — and the window's job is to decide what comes next, so the collectors, the builders and the attack each get their turn. Those defaults are right for the CLI, where somebody is deliberately spending an evening or a full storage; they are wrong for one pass of a round-robin, and the walls one was missed on the first pass at this precisely because the attack was reasoned about and the other four were left on their defaults. A wall batch is up to `MAX_BATCH` walls, so a bounded pass is not a pass that barely does anything.

**`MainWindow.job_running` replaced two flags that only needed to be two because of that split.** There is one emulator, so two passes at once interleave taps on the same display; that used to be prevented by a `running_task_id` for the agent-loop jobs and an `attack_running` bool for the one job that was not one. With every pass the same shape, so is the flag.

**Logging.** `configure_logging()` in `main()` sets up a `rich` stderr console plus this run's own plain-text `run.log`. **What marks the process as already configured is a marker handler of its own, not any of the sinks**, because which sinks exist depends on the build: PyInstaller ships `--windowed`, so there is no stderr and no console handler at all, and a guard keyed off that one would let every later call fall through to `root.setLevel` — resetting the level on the one build where the 執行紀錄 panel is the only log there is, just after its selector was asked for DEBUG. The window hands the log back to its **own** run when a job ends rather than to None, since None would leave everything it writes between jobs with nowhere to go. `MainWindow._attach_log_panel` adds a handler that renders every record through `rich` and mirrors the resulting HTML into the 執行紀錄 panel under the tabs, and the panel's level selector retargets the root logger at runtime (DEBUG adds full prompts and replies). The file handler stays plain text so the log can still be grepped. `Worker.run` logs the traceback before the message box, and `sys.excepthook` catches what Qt would otherwise swallow. New adapter code is expected to log its own decisions; a feature that fails silently is the bug being fixed here.

**Attack loop** (`ui/attack.py`, `parsers/scout.py`, `parsers/glyphs.py`). 攻擊 → 尋找對戰目標 → 軍隊畫面的攻擊 → scout → deploy or skip → 回營, driven by `AttackRunner`. **Nothing in the loop asks Gemini what is on screen.** The scout screen is why: it expires after 30 seconds, and when it does the game forces the battle to start and removes the 下一個 button, so a vision call per candidate neither reliably fits the window nor is worth paying for on an opponent that gets skipped. `read_scout` matches the loot digits against ten bit-pattern templates instead — a whole frame reads in about 0.15 s — and returns three states the loop needs to tell apart: `None` (正在搜尋對手, no digits where the panel would be), a view with `can_skip=True` (the scout window), and one with `can_skip=False` (the loot panel stays on screen after the countdown, so skippability is read from the 下一個 button's orange instead). Everything is hard-coded to 1600x900, and every parser decodes its frame through `parsers/frame.py`, which raises on any other size rather than reading garbage.

**The game's own popups sit over the result screen, and one of them reads as the result screen** (`RETURN_HOME_GREEN`, `_leave_result`). **A glyph is measured from its own body, not from whatever else lands in its box.** `signature`, in `parsers/glyphs.py` along with the rest of this section's machinery, used to run from a span's first inked row to its last, so speckle that never touched a digit still stretched the normalised cell: two lit pixels four rows under the 9 of 297 906 put it 51 bits off its template and failed a row that was perfectly legible, on all four polls one battle got — which had the run report an attack that took 875k gold as one where nothing had been deployed. Gemini enters at exactly one point: `_plan` asks it, **once**, how to attack an opponent that has already passed the loot thresholds. A skipped opponent therefore costs nothing, and one call fits the 30-second window where a call per candidate does not. It answers an `AttackPlan`, which is a `steps` list and nothing else that carries judgement: one `AttackStep` per move, in the order it is played, each carrying all four of `act`, `who`, `at` and `seconds`. A field with a default is optional in the JSON schema and Gemini leaves those out, so anything the loop cannot work without carries none. Only two keep a default: `deploy_from` falls back to the named flanks, and `reason` is commentary. Three runs running came back with a start and no end, so the line was thrown away every time; a later one named five rage points, no freeze point and no hero at all against a screen holding a freeze bottle and four hero cards, which put the freeze on its fallback spot and gave every hero the `unknown` ability delay — a queen's cloak wasted on every attack. The prompt carries the drop line's own numbers for the same reason: it was drawing lines across the village, which `planned_line` then refused, so two live runs in a row used only the side it had picked. The four preset flanks are quoted to it as baselines to measure against. It answers the two ends of the line to drop the troops along, where each rage goes, where each freeze goes, and **which hero each card holds**. The prompt asks it for the side with the *heaviest* defences, which reads backwards for a farming run and is deliberate: current troops take defences head on, and a drop aimed at the loot instead leaves the storages soaking damage as tanks that never shoot back while the defences that do are still standing and killing the army. That last one is why the same call covers where each hero goes and when it fires. **Both used to live somewhere the village could not be seen from**, and the exchange was a guess made with the layout in hand for one made without it: the seconds were a table of per-hero constants in the settings file, and the position was the middle of the drop line for every hero alike. Neither survives what a village actually asks for. Heroes do different jobs in one attack — one or two walk the outside clearing the stray buildings that pull an army off course, the rest go in behind the push — and a single shared point cannot say so. The seconds are really the question *how long does the army take to walk there*, which is a property of the frame being looked at: how far the line is from the first wall, how deep the defences sit. So a `hero` step carries where that hero goes and an `ability` step after it carries when it fires, and the steps are matched to the row left to right rather than by index, because an upgrading hero cannot take the field and its card simply disappears, shifting every slot after it. A `hero` step that runs out of cards is skipped rather than shifting the rest. A queen wants her cloak inside a second or two — her equipment calls up a tank and a mirror of her, both on their own timers — where a warden's tome is worth holding until the push is under fire. Both spells carry their delay on the plan as well, since both are held back and need a time of their own rather than whatever falls out of the ordering. One point per bottle for the spells, not one point for all of them: freezes stacked on a single spot are one spell's worth of effect for the whole cargo.

A drawn line is only used when it could work. `planned_line` rejects one whose midpoint sits within `MIN_LINE_RADIUS` of the screen centre, because `push_out` moves a point *away from that centre* and so cannot move a point sitting on it: a line straight across the village would be refused at every probe with nowhere to be pushed, losing the whole army. That is what `deploy_from` is still for — the four named flanks are the fallback, each already known to run outside the boundary. `ai=None`, a failed call, or a rejected line all land on the same fallback, the flat plan's flank and its grid of rage points, so the loop still runs without a key.

Before any of that, `army_strength` reads `305/305` off the 我的軍隊 screen and backs out below `MIN_ARMY_RATIO`. That screen comes up *before* the search fee is charged, so a half-trained army costs nothing to walk away from. The digits are found by what they are not: every real digit matches a template within `ARMY_DIGIT_TOLERANCE` while the slash reads 25 and the troop icon 74, so anything over the line is a separator.

Deployment reads the card row rather than assuming it. `card_groups` splits the row where the game leaves a wider gap — 11 px between cards, and 34, 16 and 25 across the three group boundaries — which yields the troops, then the siege machine and the heroes together, then the spells. **Only the first of those boundaries has to hold**, since `_deploy` reads group 0 as the troops and flattens everything after it; the siege machine sits 16 px from the first hero, barely wider than a gap inside a group, and only ever read as a group of its own while a seam was breaking the card beside it.

**A card whose own artwork is dark breaks the row where it stands, and a broken card is a card that disappears.** The row is segmented by averaging a 100 px band down to one row of brightness, so a vertical dark band inside a card cuts it in two and both halves can land under `CARD_MIN_WIDTH`. `card_groups` is only valid on a **full** row, which is why `_scout` hands its frame to `_deploy` rather than letting it take its own: once cards grey out the row fragments below the detection floor, and the battlefield visible past its ends starts reading as a card of its own. The empty slot the row ends with is a dashed outline with the battlefield showing through, so it segments as a card whenever the ground behind it is bright enough and then arrives as one more hero to drop, which cost a run all five of that card's attempts; every real card carries a level badge in its bottom-left corner and that slot does not, which is what `_badged` reads. `counted_cards` then separates spells from heroes and the siege machine — troop and spell cards carry an `xN` in the corner, reading at least 0.20 of it in white against at most 0.07 for the others. `card_count` reads the number itself where it can, and returns None where it cannot: over a pale illustration the count merges into the artwork, which shows up as an `x` glyph of the wrong width. Its *presence* is always unambiguous even when its value is not, which is why the two are separate calls.

**The whole army goes down in about two seconds, and the tactic decides the order.** It used to be the loop's, and the loop's order was measured and right: the siege machine first as the tank that opens the path, then the troops along the flank, then the heroes straight behind them — the version before that landed the siege 7 seconds in, the last troop at 44 with a card still holding something, and the heroes at 67, against 4, 8 and 12 after. What a fixed order cannot express is a spell that belongs *between* two drops, and a rage does: it covers the troops, and they are already walking while the heroes are still being placed. So the order comes off the plan now, one `AttackStep` at a time, and the loop contributes none of its own.

**A pause is a step, and it is counted from the previous move finishing** (`AttackStep.act == "wait"`). That is what makes a tactic immune to everything upstream of its first tap. The clocks used to run from the loop's own idea of when the battle opened, which moves with how long Gemini took to answer and how long the boundary took to read — and measured over 23 recorded rounds the gap those numbers were really about, troops down to rage cast, ran from **3.0 to 10.8 seconds while the planner asked for the same 14 every time**. Nothing the planner can see says when the loop noticed the battle, so nothing it answers should depend on it. The only `opened` left is the one `_play_tactic` prints its `Played …, Ns in` line from, and no schedule sorts absolute moments any more: the list is the schedule.

**Nothing is read between two taps, and that is where the deployment used to go.** Measured on one recorded round, putting the army down took 9.15 seconds of which about **1.5 was tapping**: six captures at roughly 0.7 s each, plus the `HERO_SETTLE` and `DROP_SETTLE` waits that exist only so those captures have something to see. 84% of a deployment spent watching itself. **A refused drop costs nothing to discover late**, because the game does not consume the card it refused — so the whole tactic goes in blind and one reading afterwards says what to send again (`_settle_drops`, which hands the misses to `_drop_singles` and a row still holding troops to `_spread_troops`). That reading is taken **inside the tactic's first pause long enough to hide it** (`CHECK_BUDGET`, 2 s against a capture's 0.9), because a pause is the only idle time in a battle and a check that fits inside one is free. Later pauses spend the same frame on whether there is still a battle to play into: some card slots sit exactly where the result screen draws 回營, so a tactic outliving its battle taps its way out of the village. One bottle per planned point; every spell gets cast, because one carried home does nothing. A card is judged finished by being empty rather than by having moved: the `xN` corner repaints on the first bottle to go, so `card_drained` called a card that cast four of its five a success, and measured over three recorded battles the rage card came off the row at x1 on two of them. `live_cards` answers the question that was meant, and a card still holding something is offered the run once more. `freeze_cards` separates the two: freeze is the only spell CoC draws in cyan, reading (141, 224, 242) against rage's (163, 137, 201).

Spacing follows the spell's real footprint, which is a **240x120 ellipse** rather than a circle; where that number comes from is under **The shape is a block, not a line** below. The flat plan's grid is spaced at that pitch, and two overlapping rages waste one.

**A crowded bottle is moved off its neighbour rather than dropped** (`spaced`, `_clear_of`). The planner is given the footprint and told not to overlap, and it does not comply — measured over 24 live rounds it drew its 2x2 at 13% by 10% of the screen where the prompt asks for 15% by 13%, which puts the horizontal neighbour at 0.75 of a footprint and the vertical one at 0.56. Dropping those was the first answer, and the caller topped the cargo back up off a fixed grid laid across the whole village: **the block collapsed to its own diagonal on 24 rounds out of 24**, losing 48 of the 96 points asked for, and the grid filled the gaps with bottles like (1000, 300) behind a village being attacked from the top left. An overlapping bottle wastes itself; one on the far side of the map wastes itself *and* leaves the ground the planner picked uncovered. Pushed out to the edge of the footprint it is standing on, that same block opens into a proper one — measured on the live case, 208x90 becomes 242x121 over the same ground, and across those 24 rounds every planned point now survives with no overlapping pair left. The push is done in units of the footprint, where the ellipse is the unit circle and clearing it is a step of 1, and it repeats because one step can walk into the next bottle along. `NUDGE_CLEARANCE` overshoots that step by a hundredth, since rounding the answer back to a whole pixel is otherwise enough to leave the point a hair inside and push it to the same place until the attempts run out. A point that genuinely will not fit — one pushed into the card row, where `clear_of_controls` puts it straight back — is still dropped, exactly as every crowded point used to be.

**`NUDGE_REACH` is what stops the repeats compounding into the same bug from the other side.** Each push moves up to a footprint, so eight of them can carry a bottle right off the ground the planner was looking at: swept over 20 000 random point sets the uncapped walk reached 1.81 footprints, and one four-point cluster took (823, 396) out to (608, 212) — 215 px left and 184 px up. That is a bottle covering ground nobody chose, which is what this whole mechanism exists to prevent. One footprint is the ceiling, because past it the point is no longer the planner's, and anything that cannot be cleared inside it is dropped rather than walked out there — nothing tops the cargo up from a fixed grid any more, since a bottle on the far side of the map is the failure this exists to prevent. The real plans need a fraction of it — replayed over the recorded rounds the furthest any point moved was 0.32 of a footprint — so the cap only ever fires on a crowd the planner would never draw.

**Rage goes where the plan drew it, and it used to be moved onto the fighting.** `_onto_army` took two captures `MOTION_GAP` apart, found the busiest 240x123 patch of what had changed between them, and slid the whole pattern onto it — on the reasoning that measuring where the army *is* beats predicting where it *will be*. What that left out is when the answer arrives: the two frames, the gap and the decode were three to four seconds, all of it **after** the moment the plan asked for the bottle, against a rage that lasts eighteen. Measured over four battles, plans asking for 12, 15, 12 and 12 seconds had the bottle land at 18, 22, 20 and 19. Cutting it to one frame brought a comparable battle to 17 and no further. A reading that late is not a better answer than a prediction; it is the same answer applied to a battle that has moved on, and it cost every attack a fifth of the spell's own duration.

**What replaces it is the property the prediction rests on: troops walk toward defences.** So the prompt asks for the same thing `freeze_points` already asks for — the heaviest group of defences on the side being attacked — because that is where the army ends up and where it stops longest. Nothing sits between the schedule and the tap any more.

**The shape is a block, not a line**, and that is measured too: a rage reaches 5 tiles and the 44x44 map spans about 1040x605 px here, putting a tile at roughly 24x12, so one bottle covers a **240x120 ellipse**. Four of them in a row span 720 px against a village about 700 wide, which is why a live battle put one bottle out on the trees while the fighting was inside the wall; four in a 2x2 block span 240x120 and cover the group. The flat plan's grid is spaced at that same pitch, and two overlapping rages waste one.

Freeze was never moved and still is not: it is aimed at defences, and those do not walk anywhere.

**None of the deployment's cost was ever ADB.** Measured against this emulator, a shell round trip is 47 ms and each `input` inside one costs about 12 ms, so five taps chained with no sleep at all take 109 ms; a `screencap -p` is 0.6-0.8 s and raw is worse, at 1.4 s for 5.8 MB. Everything else was sleeps and captures the loop was paying for itself, and every one of them is now a measured number rather than a cautious one: `TAP_GAP` 0 (it was 0.05 on the reasoning that the game keeps one touch per display frame; measured again on the builder base, five cards holding four each emptied on exactly four taps with no gap at all, and a whole run at that spacing deployed all twenty troops for 80% while taking the troop half of the deployment from about 19 s to about 8), `SINGLE_DROP_DELAY` 0.15 (one burst at that spacing put the siege machine and all four heroes on the field), `SPELL_SELECT_DELAY` 0.6 (a spell's radius indicator has to be up before a placement lands, and 0.6 goes through where the 0.1 a troop is happy with does not), `DROP_SETTLE` 0.5 and `HERO_SETTLE` 1.5. A card's `xN` corner had already repainted by the first capture taken after the tap, which lands 0.86 s later because a capture is 0.7 s of that on its own. Only a spell's *selection* is slow — the card stays selected while it still holds something, so the rest follow as a fast burst, and how many times to tap comes from `card_count`, the card's own `xN`, plus one for slack.

The troop cards are emptied in passes, each pass's drops spaced across the whole line and rotated per card, so a card holding one troop does not pile it where every other card started. **A pass walks the line twice, so one of them empties the card.** At one circuit the card decided: measured on a live row of x9 dragons and x16 balloons, the first pass emptied the dragons and left four balloons, which went down 1.4 seconds later — a settle, a capture and a decode behind the rest of the army, which for a balloon is a long way behind. **Which way this cuts depends on the army, and both directions are measured**: a tap costs about 0.062 s and a pass boundary costs 1.4 s whatever it carries, so on that row the old shape spent 3.91 s reaching the last troop against the new one's 3.15 s, while an army of four cards none holding more than twelve pays 0.74 s per card of tapping into nothing and runs about 3 s longer. **That trade is now only paid by a card whose corner will not read**: a counted card says what it holds, so each is tapped that many times plus one, and `DROPS_PER_PASS` is both what a card the artwork swallowed falls back to and the ceiling on what any count may ask for — measured on a row of x9, x3 and x2, 34 taps rather than 75. Which corners read was measured as well: of those three the two on blue plates came back 3 and 2, while the pale one merged its `x` into the background as a single 25 px span matching no character, so the fallback has to stay. **The ceiling is there because this reader fails high**: a four-pixel sliver of card art past the last digit matches a `1` inside tolerance on some frames and not others, and across three committed fixtures the same x12 card reads 12, None and 121 — the last of which, taken at face value, is 122 drops in one burst, about 7.6 s, more than double what reading the count saves. Clamped, a genuinely larger card loses nothing; it takes another pass exactly as it used to. Later circuits land **between** the first one's points rather than back on them, because the stride only orders one circuit and the second walks the same twelve in the same order: without the offset a card of sixteen stacks its last four exactly where its first four went. `DEPLOY_PASSES` is still behind all of it for a card bigger than two circuits. **A pass strides across the line rather than walking along it** (`DROP_STRIDE`, coprime with `LINE_POINTS`, so the coverage is unchanged and only the order moves). What that buys is the card that runs dry partway through a pass, since the troops it did put down are wherever the first few taps went: three baby dragons used to empty into a huddle 41 px wide, and a baby dragon rages only while no other air troop is within about three and a half tiles — 84 px across at this camera — so all three sat in each other's way and not one of them ever raged. At this stride they land 208 px apart. A full card of twelve hog riders lands exactly where it always did. `live_cards` says which cards are spent — a spent card goes fully greyscale, which brightness alone does not separate — so passes stop as soon as the cards are empty rather than running a tap count guessed up front. The row is walked once more after a delay because a hero card taps into its ability once the hero is on the field.

**The settings file no longer holds a clock of any kind, and that is the point** (`AppConfig`, `AttackStep`). Ability and spell timings were a table of per-hero constants a user could edit, which meant editing them was guessing how long an army takes to walk across a village nobody had looked at. `_plan` then *threw away* whatever Gemini answered for the same field, on the reasoning that a still frame says nothing about how long this machine takes to put an army down — true, and beside the point, because the number is about how long the army takes to **walk**, and that is exactly what the frame shows. So the exchange was a guess made with the layout in hand for one made without it. Every clock now lives on the plan, and `plans/flat.json` carries the old constants as the fallback for a run with no key. No per-hero clock is left in the code: a `hero` step naming nobody (`unknown`, which is every hero on a flat plan) sends every hero still in hand, and an `ability` step naming nobody fires every hero that is out, so on a flat plan every ability fires at the same moment, the twenty seconds of `wait` steps after the last drop.

**A tactic is a file, not a set of constants** (`plans/flat.json`, `AttackPlan`). `_plan` settles on one of three: the plan handed to the runner, which skips Gemini entirely and is what `--plan-in` fills; the one Gemini answers; or `plans.flat()`, the everything-spread-evenly default that reproduces exactly what the loop used to hold in `DEPLOY_LINES` and a fixed grid of rage points. Flat is a safe tactic rather than a good one — it runs against any village and gives a baseline to compare against. A plan is one ordered list carrying every point and every pause, so a written one reads as a script — `siege → troops → hero → wait 4s → rage x8 → wait 15s → freeze → wait 1s → ability` is what `plans.flat()` says, and the log prints exactly that line before playing it; `--plan-out` writes back whichever ran, which is what makes a battle worth repeating repeatable. Like `prompts/`, the directory ships through `[tool.hatch.build]` and needs its own line in the PyInstaller step.

**The battle map is a diamond, and `MapFrame` is what says where** (`models.py`, calibrated in `parsers/boundary.py`). `DEPLOY_BOUND` is the ground the game will accept a drop on, wider than the 44x44 grid the buildings sit in. It is read off live frames rather than detected in them, because a village theme repaints the ground the edge runs along while the camera stays put, and it is good to about 20 px — enough to keep a pushed drop on the map, not enough to land on a chosen tile. `push_out` clamps to `DEPLOY_BOUND` and not only to the playfield rectangle, whose own corners are off the map: a hero refused four times ended up at (30, 175), where the map spans x 596 to 1004. `ai_coc bounds` is how to argue with those numbers rather than re-eyeball them: it spends a battle walking each of six rays inwards from the screen edge until a troop lands, and fits a diamond to what the game accepted. The rays are the horizontal and diagonal ones on purpose — vertically the map runs off the top and bottom of the screen before its edge is reached, so those rays would measure the UI. **Its first run took the very first probe on all six**, at (1570, 400), (30, 400), (1100, 700), (500, 700), (505, 105) and (1095, 105): the screen runs out before the map does, so the diamond cannot be seen from inside it and what comes back is a lower bound. That was enough — the building grid widened by five tiles a side, which is where this started, would have clamped four of those six back inside, so `DEPLOY_BOUND` is its own constant, sized to contain everything the game took while still excluding the screen corners no ray reaches. The loop no longer leans on it much either: `_drop_single` sees a drop pushed somewhere the game will not take and pushes again, where before it was lost in silence.

**The deployment boundary can be read rather than guessed** (`parsers/boundary.py`). The game draws its own red stroke around the ground it will refuse, for the whole battle rather than only while a card is selected, so one screenshot carries it. It is UI painted over the scene, so a village theme changes the ground under it and not the stroke: measured across four themes, red sits between 125 and 220 with `red - max(green, blue)` at 85 to 105, against -20 to -30 for the grass beside it. The red ceiling is load-bearing — a wall highlight reads (255, 71, 0) and a fire (255, 140, 24), both of which clear the score. `boundary_reach` returns how far the stroke reaches along one ray rather than a polygon, because a line to spread troops along is all the loop ever wanted, and it answers nothing at all where the crossing sits closer than half the distance the ray was able to travel: a ray stops at the playfield edge, so where the boundary lies beyond that edge the ray never meets it and whatever red it grazed becomes its answer. Two live surveys put every crossing that matched the game at 0.62 of the distance travelled or more, and every one that turned out to be inside the village at 0.45 or less. A wrong reading costs more than no reading, because the loop trusts it and pays five refusals finding out. `fitted_line` bends a preset flank onto it through **three** anchors, not two: a village is a diamond, so a straight chord between two boundary points cuts back inside across its middle, and fitting only the ends had two flanks in a row refused at all five pushes before a third worked. `deploy_line` walks whatever anchors it is given, so the drop line follows the village. It is a better opening guess, **not** a guarantee: a ray whose boundary lies past the playfield edge never meets it, and the pushing below stays as the backstop. `ai_coc probe` is how to find out how good the guess currently is — it spends a battle dropping two troops either side of the predicted line on twelve rays and reports how many agreed. Its first run measured 7 of 12, with four of the five disagreements putting the line *inside* the real boundary, which is why `fitted_line` throws away a fit whose three anchors sit at wildly different distances: an anchor inside the village is the expensive way to be wrong, since the line then cuts through and every probe on it is refused.

**Nothing can be deployed until the countdown ends, and the loop waits for it** (`_wait_for_battle`). A tap the game ignores raises nothing at all, so an army put down during the scout countdown is an army that never lands. The wait hands back the first battle frame too, which is what `fitted_line` bends the preset flank onto: the boundary is only drawn once the battle is under way, so this is the first moment it can be read.

**The zoom is asked for rather than checked** (`_settle_zoom`, `AdbController.zoom`). Every coordinate here was measured at the game's far zoom limit, and a game that has drifted off it misses all of them — the drop line, the card row and the spell grid alike, silently. **There is nothing to check against**: the game reports no zoom level, and two attempts to read one off a frame were each defeated by something else moving in it — the deployment boundary shrinks as buildings fall, and the village ground gets covered by whatever panel the game opens. What is known is that zooming out past the limit does nothing at all, so every battle opens with a pinch out rather than with a measurement.

**The safety net is also the only detector, and the height is the signal.** What it reports on is the deployment boundary's height *before* the pinch, which is the one measurement of this that survived a live run. Not the width: every round faces a different opponent, and swept over one day the widths ran 909 to 1560 while nothing was wrong. Not the frame's byte length either — that was tried first and cried wolf on its second live round, 30 KB apart with the village measuring 549 and 559, which is two seconds of animation rather than a changed camera. The height works because a village too big for the screen is clipped top and bottom, so it reads short whatever the opponent's layout: every healthy round of that day fell in 500 to 572 and the one round that deployed nothing came back 411. What prompted this was a live round that came back `spanning 1481x411` where every other round of the same run measured 535 to 572 tall — a village grown too big for the screen and clipped top and bottom — and that round deployed nothing. Note the shape of that reading: **the width is useless for this and the height is not**, because each round faces a different opponent whose village is its own width, while the height of a clipped village is the tell.

**The camera is measured, not assumed** (`village_box`, `_settle_camera`). Everything else reads it without being able to check it: `push_out` moves a drop away from the village, the preset flanks are screen coordinates, and the spell grid is spaced off the middle. The same red stroke answers where the village is — the four UI panels painted in the game's own red are masked out, and the box is cut where 2% of the stroke lies outside it rather than at its last pixel. Measured across nine battles and both theme fixtures the game opens every attack with the village already within 35 px of the centre, so `_settle_camera` normally reads once and does nothing; `CAMERA_TOLERANCE` keeps it that way and leaves the drag for a camera genuinely left somewhere else. It runs before `_plan`, which is what keeps `_panned` below to one meaning — the flanks and the plan are then both drawn against a centred village, so one offset moves both. Its own drag is deliberately *not* recorded there, because it ends with the village back in the middle. A single-finger swipe pans the battle camera about 1:1 for small drags and clamps at the map edges; **with a card selected the same swipe deploys troops along its path instead**, which is why every drag happens before a card is tapped.

Known and not fixed: it is handed the **scout** frame, where `village_box` is outside what it was calibrated on. The scout screen carries an orange 下一個 button that the box's mask does not cover, and measured live that pulled the box out to x 1500 against 1269 for the same village moments later — so a run can spend two drags and five seconds shoving a centred village 72 px left and 48 px back. Moving the call onto a battle frame means moving it after `_plan`, and then the presets and the plan need different offsets, which is a second coordinate frame for a 60 px error.

**The lower flanks need the camera moved, because the card row is standing on them** (`_clear_flank`, `FLANK_ROOM`). The playfield stops 200 px above the screen's own edge and a village fills nearly all of what is left: measured over nine battles the red line spans 530 to 575 px of the 595 there are, so a lower flank has under 30 px of ground to drop on. That is what one recorded battle spent three pushes clamped against y 700 for, what another spent 32 seconds deploying into where an upper flank takes 12, and what a third deployed nothing at all on. So the village is dragged clear of the card row before the army goes down it, sized off its own red line and only when it is really short. The side comes from the flank about to be used rather than from the plan's `deploy_from`, since a plan whose line is rejected falls back to its named flank and the camera has to follow whichever is really used.

**A camera that has moved is written down, and everything is read through it** (`_pan`, `_panned`, `_onscreen`). The preset flanks, the plan's line and its spell points are all drawn for a village in the middle of the screen, so the record is what keeps them pointing at the same village afterwards. How far the camera went is read by sliding one frame over the other along the drag (`view_shift`), not by measuring the village twice: `village_box` trims to a profile of red that is as much village trim as boundary, and on a live drag of 98 px the game took in full it reported 23. The search runs along the drag rather than over the plane, because that is where the camera can have gone, and it answers nothing at all for a drag the game swallowed — which is what a swipe becomes once a card is selected.

**A drop is judged by the card that made it, never by the screen** (`card_drained`, `field_units`). The game gives no usable refusal signal. Measured live: a troop tapped inside the boundary is as often swallowed in silence as it is answered with 你無法在紅線區域內派遣部隊; 請選擇其他兵種, 已部署所有兵力 and 該法術已用完 are the same red in the same place; and a burning building fills the same box. Reading that banner meant `_usable_line` returned 0 on its first try every time so the flank was never actually tested, `_spread_troops` pushed the flank out twice in every one of six recorded runs for refusals that never happened, and every hero came back "landed" whether it went down or not — one recorded run reported four of four while the fourth never left its card. What the game does say is on the card. A counted card repaints its `xN` corner when it loses one, by 368 to 1139 pixels against exactly none for a card that did not, so `card_drained` reads the corner rather than the number and works on the giant's card where the count itself will not read at all. A hero's card does not empty, because it becomes the ability button, so `field_units` reads the health bar that appears over it instead — 0.33 to 0.37 of that strip against at most 0.02. That strip sits *above* the card row, so the battlefield shows through it until the bar is drawn, and a brightness-and-hue test read that as a bar: swept over 126 recorded frames taken before anything had been deployed, it called a hero landed on 52 of them. Blue is what separates them — measured, the bar runs (101, 231, 9) and grass (131, 184, 53) — and the same sweep now reports none. Both signals take about a second to appear, which is what `DROP_SETTLE` and `HERO_SETTLE` are for; on a hero a false negative is not free, since the retry taps its card again and that is its ability.

**The drop line adapts, because layouts vary more than any fixed line survives, and nothing is probed first.** `_usable_line` used to drop three troops at the ends and middle of a candidate line, ask whether a card drained, and walk all four preset flanks until one took them. Three troops is three troops sent to die alone in front of the defences before the army meant to cover them exists, and it was paid on every battle whether or not the line was ever in doubt. What is left is `_flank`, which costs nothing: the camera is dragged clear of the card row when the flank needs the room, and the line is bent onto the boundary the game draws. `_spread_troops` then carries what the probing used to — it pushes the flank further from the middle when a whole pass drains nothing, clamped to `PLAYFIELD`. That backstop was always underneath the probing anyway, because the village is a diamond and the ground around it is **not convex**: a line with both ends outside the boundary can still cut through it, which is what a battle that deployed nothing at all against a boundary reaching past every preset paid for. `_wait_out_battle` is still the backstop underneath: loot that never moves across a whole battle means nothing was placed, and the report says so rather than claiming success. **Its False is not the alarm on its own, though; `_seen` is what separates the two cases.** A panel read on every poll whose numbers never move is the deployment that came to nothing. A panel that never read at all says only that — measured over one twelve-round run, two rounds polled a village whose loot panel would not resolve on any frame, and both had in fact taken their opponent for 800k and 1.1M. Reported as the same thing, the check that exists to catch an army that never landed cried wolf on one round in six, which is worth less than no check at all.

**Every point a drop can land on goes through `clear_of_controls`**, which holds it inside `PLAYFIELD` and lifts it off the 放棄 button. The bottom of the screen is the army card row, so a tap there selects a card instead of deploying: a plan answering `y_pct` 80 put a hero at y 720 and spent all five of its attempts tapping its own cards. `prompts/attack_plan.md` tells the planner the same limits in percentages, so it stops drawing lines under the UI in the first place.

**Every one-off drop is verified against its own card, and the whole row goes down at once.** `_drop_singles` puts the siege machine, or every hero, on the same spot in one shell round-trip, waits `HERO_SETTLE` and asks which of those cards put something on the field; only the ones the game did not take are offered another spot. One card at a time cost a capture to frame the drop, a settle and another capture to judge it — three and a half seconds each, so four heroes spent seventeen seconds arriving.

Where those retries go is `single_spots`, and it is not simply "further out". `push_out` stops moving a point once it reaches the edge of `DEPLOY_BOUND`, because everything past that is clamped straight back: measured live, a siege machine refused at (266, 199) was pushed four more times, came back within two pixels of itself every time, and was never deployed at all — in the one battle of that run that was lost. Whatever the pushes cannot reach is tried along the drop line instead, and two spots closer together than `SPOT_APART` are the same spot rather than a retry. Only the heroes that actually landed reach the schedule, because a hero still in its card answers an ability tap by deploying instead, with nothing around it and no ability fired.

**Which of those one-off cards held a hero is the plan's own count, and a health bar cannot say it.** The leading card is a hero on any army carrying no siege machine, and nothing on the row separates the two: neither shows an `xN`, and both sit in the same group. That used to be settled by `field_units`, on the reasoning that the game never draws a bar over a siege machine. It does — measured across all three rounds of a recorded run, the 攻城戰車 landed and its card read as a hero on the very next frame. So the leader was scheduled an ability it has none of, and **every real hero after it was read a slot off the card it names**: the queen went out on the king's twenty seconds where her cloak wants one. She was the whole cost of it on that army — the three behind her were a king, a 亡靈王子 and a duke, all three of which want about twenty seconds, so being read a slot apart cost them nothing. An army carrying a warden or a champion would have paid on every card. As many heroes named as there are one-off cards is an army with no siege machine, one fewer is an army with one, and that arithmetic holds whether or not the leader made it onto the field — which the bar cannot speak for either. The bar stays as the answer only where there is no plan to count, and there every card takes the same `unknown` delay anyway.

**Spells are verified too, and a card that would not cast is offered the run once more.** `_cast` reads the same corner: a cargo that never leaves the card is the quiet half of the same bug, since nothing downstream notices and the report says the attack went in. The cards are asked together rather than one at a time, for the reason the heroes are — a capture and a settle apiece was most of what a cast cost. Freeze can be placed inside the red line — measured, a rage dropped on the town hall landed while a troop aimed at the same spot did not — so a spell that fails is a swallowed tap rather than a refused position.

**Builder base attack loop** (`AttackRunner.world`, `_run_night`). The same runner plays both villages, because everything after a battle opens is shared — the camera, the boundary fit, the drop line, the card row. What differs is the way in and what the row means, and both are short. `ai_coc attack --world night` crosses first; with no `--world` it plays whichever village is up and says so in the report, because the game reopens on the one it was closed on and refusing to play that one would stand half the runs down.

**Getting into a battle is two buttons instead of five, and there is nothing to weigh.** 攻擊 sits in the same corner and opens 開始進攻, whose 立即尋找 goes straight to the matchmaker: no scout screen, no 下一個, no loot thresholds, no search fee, and no army check — the builder base refills its army the moment a battle ends, measured on the dialog straight after one that lost all twenty troops. Both outcomes pay, a win in gold and a loss in elixir, so there is nothing a threshold could usefully refuse.

**`night_attack_menu` needs two features and one is not enough**, which is the same trap the boat presented: its 立即尋找 is green, and a village is mostly grass. Measured through the button's own box, a home village battlefield reads up to 0.69 of button green against the dialog's own 0.63 — so what settles it is the cream panel behind the button, which no battlefield has and which the matchmaker, also pale, has no green button on. Either test alone has false positives over 4320 recorded home frames; together they have none.

**The matchmaker waits for another live player**, so it is the one screen that has to be recognised rather than passed through: measured here, one search took five and a half minutes and another twenty seconds. `searching_opponent` reads its 取消 button — 0.87 of red against at most 0.20 on any recorded home frame, the closest being the 放棄 button in the corner of every battle. A search that runs past `SEARCH_PATIENCE` is cancelled and started again rather than sat out, because a fresh one gets a fresh pass over whoever is queueing now and the builder base charges nothing for it. The state file is read throughout, since a stop that takes minutes to show reads as one that did nothing.

**The card row is the home village's, reversed.** There the troops come first and the heroes follow; here the machine leads and the troops follow it. So the split is read off the `xN` corner rather than off a group index — only troops carry a count in either village — and `counted_cards` already answered that question for both.

**`card_count` reports the builder base as unreadable, and that is the safe half of a measurement.** The two villages write the count differently, `x4` there against `4x` here, and the builder base draws it half as big again: 18 px against 9 to 15. Two attempts at one reader for both were measured and both rejected. Finding the `x` by which end matches no digit template breaks a home card whose own digit is as wide as its `x` — `cards_full`'s third card reads 2 and would stop reading at all. And the builder base's digits miss every template far enough that its 4 comes back as a 9, 23 bits off, which is inside `COUNT_DIGIT_TOLERANCE` and so would be believed. A count nobody can read costs the fallback tap count; a count read as more than twice what the card holds costs the burst that follows it.

**`live_cards` does not hold there either, and this one cost a whole deployment.** In the home village a card goes greyscale the moment it is empty, which is how `_spread_troops` knows to stop. In the builder base it greys when the troops it put out **die**: measured over one recorded attack, all five cards read `0x` on the frame after the first pass while every one of them was still in colour, and they went grey one at a time over the next thirty seconds as the fighting killed them. Believed, that bought four more passes tapping into empty cards — and since each of those drained nothing, `_spread_troops` answered by pushing the flank out, so the line walked 280 px away from a village the army had already reached. `_spread_night` uses the pass itself instead, and **which pass it is settles what nothing draining means**: a pass taps `DROPS_PER_PASS` against a card holding about four, so a later one draining nothing is an empty row, while the *opening* one draining nothing is a line the base has grown over and the flank is pushed out. That is the same job the probing used to do, without spending three troops to do it.

**The machine goes in ahead of the troops, which is the other way round from the home village.** There the siege machine opens the path and the heroes follow the army in; here the machine *is* the army's cover, so it lands first and the troops follow once it has walked far enough to be taking the fire — troops landing beside it split that fire and waste the tanking. How long the head start is comes off the plan as `NightPlan.troops_after` rather than out of a constant, for the reason every other clock in this project moved onto a plan: it is a question about the base in the frame, and only something looking at the base can answer it. The one wait it produces is spent offering the machine its ability rather than sleeping. `plans/night_flat.json` carries 4 seconds as a written-down starting point, which is what a flat plan is for.

**A machine that died in the stage before does not go out again.** That is the ordinary case rather than a corner: the second stage opens with whatever survived, so a machine that spent the first one tanking is usually gone, and its card stays on the row greyed out. Sent anyway it costs `_drop_singles`'s whole ladder of spots — five taps, each with a settle and a capture — before reporting that it took nothing, plus the head start held for a machine that is not there. `live_cards` is what says so, and this is the one question it answers *well* in this village: a card there greys when the unit it put out dies, which is exactly what is being asked. It is the same reading that makes it useless for "is this card empty", where the question is whether anything is left to deploy rather than whether it is dead.

**And one that survived comes back with its card preselected when the second stage opens, so the loop taps the field there rather than the card, until the border says it went.** Measured on five recorded second stages, the stage opens on a countdown with the machine's card drawn at the selected width with a white border. What sends it from there is a tap on the field, and one blind tap was not enough: the plan's spot fell outside the smaller second base's ground on a live round, the game swallowed it, and the machine sat selected in its card for the whole stage while every ability offer only toggled the selection. So `_send_selected` walks the plan's spot and then `single_spots`, reading `selected_cards` — the same white border `card_groups` relies on — after each, because the health bar cannot say it: a machine carried over keeps whatever health it had, and `field_units` reads a bar no longer green as no bar. Dropping it the usual way was five taps on what is by then its ability button and five spots the game answered with 請選擇其他兵種, and `field_units` then read its damaged health bar — darker green, then yellow to red as the health falls, where the reader wants the bright green of a full one — as no bar at all: `never landed`, about fifteen seconds of retries, the troops held behind a machine already fighting. **Worse, `card_groups` could not see a selected card at all**: 118 px against a ceiling of 116, and a 1 px sliver of the white border inside its seam kept the two pieces from rejoining, so every recorded second stage read `0 machine card(s) still alive` and the machine was offered no ability for the whole stage. `CARD_SELECTED_SPAN` is the wider ceiling, allowed only between two white columns, which a fragment's own edges never are. And in either stage every machine card still alive is offered the ability whatever the landing read said, since the tap is harmless on a card still holding its unit.

**The machine's ability is not scheduled, because there is no moment to schedule.** It recharges for the whole battle instead of firing once, so `_wait_out_night` offers every one-off card the tap once a second (`ABILITY_TAP`) and the game takes the ones that are ready; only the capture that asks whether the stage is over is paced at `ABILITY_POLL`. Measured over about thirty recorded battles: the ability is ready the moment the machine lands, a tap fires it, the bar over the card refills in about 14 s, and a tap during the refill changes nothing, so repeating the tap costs a 50 ms shell round trip and nothing else. A tap on a card whose unit never made it onto the field selects that card and does nothing else, so this is safe on a machine the boundary refused as well. `NightPlan` carries no clock at all for the same reason — no spells either, which is why it is its own model rather than an `AttackPlan` with half its required fields left empty.

**A stage can end without a result screen, and waiting for one cost a whole second stage.** The game opened it with a fresh timer and the surviving troops back in their cards; `battle_over` stayed False because a live battle is not a result, so `_wait_out_night` spent its full `BATTLE_TIMEOUT` tapping a dead machine's card while the stage ran out. What marks the boundary is the card row being repainted — the counts go from the `0x` a spent row shows back to whatever survived. Measured over that battle, the corners moved on exactly two frames, once into the second stage and once into the result, against none at all in between; the run without a second stage moved them once.

**The second stage is played rather than predicted.** The game offers one after a first attack takes the whole base, sending what survived against the opponent's other, smaller one, and it only does so above some league. Neither condition is worth encoding: the loop asks the one question that cannot go stale, which is whether it is back on a village, and deploys again into anything else with a card row on it. **Measured once, on a battle that reached 100%.** The game opened the second stage and the loop played it: `The card row was repainted; this stage is over`, then 共出兵 2 次. An earlier 100% run went straight home instead, so the offer is not made on every one of them.

**Storage limits are asked there too, against this village's own ceilings rather than its own setting.** Its storages are a different size from the home village's, so a written-down number would stand a run down against a ceiling belonging somewhere else — which is what the night path did without any at all for a while, and then with a second set of numbers for a while after that. What it is given now is `AppConfig.stop_at`, a percentage both villages share, measured against the ceilings the loop reads off these bars. They are checked before the search rather than after it, for the reason the home village checks before its fee: the search is free in game but waits on a live player, and one has run to five and a half minutes, which is the real price of a round with nowhere to put what it wins. `read_builder_stock` is what feeds them, and it reads two rows rather than three so the gems bar never travels as a dark elixir reading.

**The capacity is written on the bar, if you tap it, and that is what one setting can now serve both villages from** (`storage_capacity`, `AttackRunner._settle_ceilings`, which reads once a run and keeps what it read, since a storage only grows when a builder spends days upgrading one). The game answers with 最大儲存量 in a tooltip that hangs under the bar, so its first line moves down with the row by the bars' own 84 px pitch. Six typed-in amounts became one share because every one of those amounts measured stale: the home village was configured at 15M against a real 24 000 000, and the builder base at 2M against a real 2 450 000 elixir — 18% of a village nobody could ever farm into. The label is what makes the line readable, by not being a number: swept over both villages every real digit lands within 3 bits of its template while 最大儲存量 and its colon read 52 and up, so `split_numbers` cuts the line at the label and the capacity is the last number left. `CAPACITY_TOLERANCE` sits at 15, well under that gap rather than beside it — at 40 the colon comes back as a `2` and the builder base's 2 450 000 reads as 24 500 000, a ceiling ten times the real one that no run could ever reach.

**The tooltip is a toggle, and the third row of the builder base is never tapped.** Tapping a bar opens it and tapping again puts it away, so a row that reads nothing is left alone rather than tapped shut: the one way to read nothing on a village that has the bar is to have closed a tooltip somebody left open, and the next attempt then opens it. That village's third row is its gems bar, whose green `+` spans x 1345 to 1385 and opens the shop — so two rows there is not a limitation but the right answer, since a resource with no ceiling is left out of the comparison and that one does not exist. The read happens in `_open_attack_menu` just before the 攻擊 tap, which is the one moment a round is known to be standing on the right village with nothing over it, and it is kept for the rest of the run: a storage only grows when a builder spends days upgrading one, against six taps and three captures to ask again every round.

**The two resources arrive by different routes, and one of them has to be fetched.** Gold lands in the storages directly — measured, a 100% attack paid 99 000 — while the elixir goes into a 聖水車 moored beside the boat and stays there. `ui/world.py`'s `collect_cart` fetches it, and `commands.attack` runs it every `CART_EVERY` battles rather than every one, because the cart accumulates and emptying it costs a drag to the map corner and back. `ai_coc collect` on the builder base does the same thing, which is why that command reads the world first: there are no collectors to sweep there and one cart instead.

**It is judged on `read_builder_stock`, not `read_stock`**, for the reason that reader exists: the third row `read_stock` insists on is the gems bar there, and 10 152 gems come back as `dark=410152` with the green `+` read as a leading 4. Two costs, both real. That row has to resolve at all for `read_stock` to answer anything, so a gems row that will not read loses the whole trip — the taps are spent, the elixir is collected, and the report says 0. And it logged `Village holds … dark=410005` in the middle of a builder base run, which is the one line a reader has to tell the two villages apart in a log.

**Tapping the cart opens a sheet rather than collecting**, which is the opposite of the home village's collector markers and cost the first attempt everything it went for — the tap landed, the sheet came up, and the storage bars afterwards said nothing had been paid. `loot_cart_open` reads its 收集 button, at 0.82 of button green against at most 0.07 over 4300 recorded frames of both villages, and the sheet is closed again afterwards because it covers the middle of the village. Measured on the first one this emptied: 300 000 elixir, out of a cart that holds 1 000 000.

**Finding things** (`GameRunner._spotted`, `prompts/find_targets.md`). Every loop under `ui/` that acts on the map has the same first problem — where is the thing — and until this existed they all answered it the same bad way. `_sweep` taps a blind grid, takes two and a half minutes, and lands where it lands: it is a sample rather than a search, and its grid stops at x 1220 and y 500, which leaves most of a village outside it. A pair of eyes on a screenshot beats it in one look, but only while somebody is there to look, and a run in the background cannot stop and ask.

**One finder, three questions, three different checks.** `_spotted(what, notes, count)` fills `find_targets.md` and returns screen points; what it is looking for and how the answer is verified both stay with the caller, because those are what actually differ — a wall menu, a priced 升級 button, hero cards. That division is what makes an imperfect finder usable at all: a wrong point costs one tap and one capture, about 1.7 s, so **asking for more points than the run needs is the right shape rather than a waste**. `WALL_SPOTS` is 12 against six or so wanted, `BUILD_SPOTS` 14 against however many builders are free, and `HALL_SPOTS` 3 against one building — three because the first guess that opens the hall ends the search.

**Measured live against one village on the run this landed with**: 12 of 12 answers opened a wall menu, the first of three guesses at 英雄殿堂 opened the hall, and 9 of 14 buildings had a priced upgrade on them, each call taking about 10 s. **And it reaches ground the grid cannot** — of those nine buildings only two sat within 45 px of a grid point, while four were more than 75 px from one, against buildings 70 to 120 px across. One of them was a 9 900 000 upgrade, which is exactly the kind `_pick` exists to find.

**A point below `SWEEP_LIMIT` is dropped rather than tapped.** That is the row of buttons the previous selection left on screen, so a tap there presses one of them instead of choosing something on the map — measured, four of twelve answers landed in it and each opened whatever that row happened to be offering. The prompt carries the floor as a percentage (`SPOT_FLOOR`) and the model obeys it, 0 of 14 on the next run; the filter is what makes that a guarantee rather than an improvement.

The sweep stays underneath all three. A village whose walls or buildings nobody can place still has them, and two and a half minutes of grid taps beats a run that finds nothing — which is also what a run with no API key gets, unchanged from before this existed.

**Wall loop** (`ui/walls.py`, `parsers/building.py`). Walls are the one thing in the village that upgrade the instant they are paid for, tying up no builder and running no timer, so they are where a village puts loot when the storages fill towards the share `stop_at` stands the farming down at. Like the attack loop it is Qt-free, and like the attack loop it asks Gemini exactly one question — where the walls are, and nothing else.

**Finding a wall is the one thing here a screen read is worse at than a glance**, and it is `GameRunner._spotted` that does it now — see **Finding things** above, which every loop under `ui/` shares. `_candidates` runs three finders in order of how much they know: the spots a caller named, then Gemini, then the sweep as the fallback. Everything after the finding stays a screen read, because that is the half the loop does better — the price, the batch size, which resource pays, and never reaching a gem button.

**Which is only safe because every spot is verified before it is spent on.** `_verify` opens each one and reads the price off its own menu, so a wrong point costs one tap and one capture and is dropped with a line saying so. That is what makes an imperfect finder usable at all, and it inverts the usual pressure: **asking for more spots than the run needs is the right shape**, since a miss is nearly free while too few candidates leaves `_pick` nothing to compare and buys the first thing it sees. `WALL_SPOTS` is 12 against six or so actually wanted — measured live on the earlier run that gave the wall loop its own finder, nine of those twelve opened a wall menu, priced 3 600 000, 4 900 000 and 6 300 000, so the comparison `_pick` exists for survived three misses. The shared finder's own run above came back 12 of 12 on a different day, so this is a rate that moves rather than a number. The whole find took 23 seconds including the call, against two and a half minutes for the sweep it replaces. It also settles the model question — nothing here is racing anything, so this uses `gemini_model` rather than a cheaper one picked for speed, and a second setting would exist only to hold a smaller model.

**Every tap on a raw village coordinate goes through `GameRunner._opened`, and a guessing finder is what makes that load-bearing.** Every spot here is a place on the map, so one that misses a wall opens whatever building is standing there, and a full-screen panel swallows every tap after it. `_opened` reads the storages after each tap and backs out when they stop reading, which is the rule the sweep was built around and is now the one walk the sweep, the named spots, the spotted ones and the wall's neighbours all take. A hand-named spot misses because the camera moved since somebody looked; a spotted one misses because it was a guess. Neither is rare.

**The sink runs out with the town hall, and the loop cannot read that it has.** Wall levels are capped by the town hall: measured live at TH 15, every wall on the map reached 16 and its 升級 then opened a sheet reading 注意！你需要將大本營提升至16級！ with 確認 drawn in grey. `game_dialog` reports neither button on a sheet like that — which is the structural guard working, since the loop can only ever press a green 確定 — so `_confirm` answers "升級 was tapped but no confirmation came up", the point is dropped, and the run ends with 每一個位置都沒有買成. It costs about two minutes and buys nothing, and no amount of reading will improve on that without reading Chinese. **What it means is that walls are finished as a resource sink until the town hall moves**, which is a decision for the player rather than for this loop.

That state also changes the menu: at TH-capped level the plain menu's second button is 整排選取 rather than 升級更多, so `menu.add` selects the whole row and swaps the menu for one selling nothing but rings — which is where 每一個位置都沒有買成 actually comes from. A fallback that reopened the menu and bought the single wall was written and reverted: it works, and on the one village where it fires the purchase is gated anyway, so there is no measurement saying it buys anything.

**A wall upgrade needs a free builder; it just never keeps one.** It completes the moment it is paid for and hands that builder straight back, which is why a village with one builder idle can buy the whole map and a village at 0/5 can buy nothing at all. Measured live at 0/5, every batch was confirmed and then not charged for, the game answering 所有建築工人都在忙碌中 and offering to finish something with gems — one wall at 1 600 000 refused exactly as an eight-wall batch at 12 800 000 was, which is what rules out the size and the purse. This was written down for a while as the game refusing whole batches for a reason of its own, which sent readers looking for one; the rule is the answer, and it is also what says what to do about it, since freeing a single builder reopens the sink. That dialog carries a gem button and no 取消, and `game_dialog` reports neither of its buttons, so `_home` waits it out and presses `back` — which is what keeps the gems structurally unreachable here as well. It is gone by the time the loop looks, so what the loop reads instead is the builder counter, and it stops the whole run rather than walking the rest of the village at forty seconds a wall.

**Nothing in it looks at a wall.** Every level repaints the wall, as it does every other building, so a reader taught to recognise the thing selected needs re-teaching at each level and again after any retexturing update. What is read is only the UI the game paints on top: the resource icons on the button row and the price beside them, identical whatever is selected. **A wall is then identified by the one thing no other building can do — being upgradeable with gold *or* elixir.** Everything else takes a single resource, so a row carrying an elixir drop with a gold coin one `BUTTON_PITCH` to its left, and the same price written beside each, is a wall and nothing else is. The drop is the anchor rather than the coin because the wall ring on the *next* button along is gold too, and that is the one button that must never be tapped: it is only ever reached by counting rightwards from the drop, which nothing does.

**Not one button in that row sits at a fixed x.** They are laid out from the middle of the screen outwards, so a batch with fewer than ten walls left to add loses its 新增城牆+10 and every button after it shifts half a pitch — measured, the gold button moves from 887 to 799. One located button locates the rest; a written-down one taps 聖水 where 升級 used to be.

**The two menus are never told apart, because they do not need to be.** 升級更多 on a plain menu and 新增城牆 on a batch occupy the same place in the row and do the same thing, so the loop taps that place and reads the answer. **The unit price is the difference one more wall makes**, which settles both questions at once and in pure arithmetic: a plain menu answers the same price back, because 升級更多 makes a batch of the wall already selected, and that means one wall at that price; a batch answers one wall dearer, and the total over the difference is how many it holds. Nothing reads a level, and nothing reads Chinese.

The price is read in red as readily as in white. Red is the game saying the village cannot afford this, and the loop sizes its own batch against `read_stock`, so what it needs is the number — a price abandoned for being red would have the whole menu read as "not a wall". Both prices must read and must agree, since a wall costs the same in either resource and two different numbers mean one was misread.

**Which wall is next is decided by price, and that is the seam an AI planner replaces** (`_pick`). Walls get dearer at every level, so the cheapest menu *found* belongs to the lowest wall found — lowest-first without anything reading a level. Found, not on the map: nothing here sees every wall, which is what the next paragraph is about. A batch that was just paid for is re-read before the next round, and it now quotes its *next* level, which is dearer than every wall still at the old one; that one re-read is the whole of what stops a run pushing one section of the village further and further ahead of the rest.

Finding a wall is a sweep rather than a remembered spot, for the reason `_sweep` always is: `_scan` taps a grid and keeps whatever opened a wall menu. A tap that opens a screen instead — a barracks, a laboratory — is caught by `read_stock` coming back None and backed out of, and that check runs on the neighbour taps below as well, because they are the only taps in this loop that go in on raw village coordinates.

**But a wall the sweep lands on is a sample of its section, not the cheapest wall in it.** Walls sit about 45 px apart and the sweep steps 160, so it passes over three of them between samples, and a section holds several levels at once. Swept at wall pitch over one live village the strip held 32 walls at 1 600 000, three at 2 400 000, two at 3 200 000 and three at 4 000 000 — and the sweep's own six samples landed on the 4 000 000 ones every time, which at 7.5% of the section is not chance. Those are the level the town hall caps, so `_pick` chose the cheapest of them, the game refused every batch, and **the run bought nothing while 32 walls three levels lower stood beside them** — reported as 每一個位置都沒有買成, which reads as "the walls are finished" and was taken for it. `_scan` now taps `WALL_PITCH` out in four directions from each wall the sweep finds: the sweep finds the sections and the neighbours find the levels. One pitch serves both axes even though the camera is isometric, because a section is a solid block several walls deep — measured on the run that proved the fix, four of the eight neighbours found came from each axis. The run after it bought 18 walls.

A batch is judged bought by the storage really moving, not by the dialog being confirmed — a tap the game swallows raises nothing, and the alternative is a loop counting walls it never paid for. `MAX_BATCH` is not a limit the game imposes: it keeps the price inside its 127 px button, and a price that will not read is the one number every decision here rests on.

**Upkeep loops** (`ui/upkeep.py`, `ui/clan.py`, `ui/hero.py`, `parsers/home.py`, `parsers/clan.py`, `parsers/hero.py`, and `parsers/regions.py` under the first two of those). Four jobs that keep a village from standing still while the attack loop farms for it, and all of them follow the wall loop's rule: **read the UI the game paints on top, never the thing underneath**.

- **`collect`** taps the marker floated above every collector holding something. Tapping one collects it outright, no menu and nothing to confirm, so this is the shortest loop here. The markers are found by colour and then held to a size, and the size is doing most of the work: colour alone answers thirteen patches of gold and nine of magenta on one village frame — storage bars, the shop button, a spell factory, a burning building — and every one of them is far larger or far smaller than a marker. Two of the three are the icon itself; dark elixir's is nearly black, so what is measured there is the bubble's orange plate. Gains come from the storage bars rather than from counting markers, because a full storage takes none of what it is offered — measured, three dark markers tapped and `dark +0`. A pass that finds the same markers standing made no progress and stops the passes, which is what that full storage looks like.

- **`upgrade`** puts idle builders to work, and picks the **dearest** upgrade the village can afford — or the one `--only` names. **Which building a menu belongs to is the one question every parser here provably cannot answer**: 金礦 and 箭塔 open menus that are identical to `upgrade_buttons`, and what separates them is a line of Chinese that no reader here reads. So `_name` crops the band the game writes it in (`NAME_BAND`, fixed and centred, measured across nine live menus) and sends that strip to the **lite** tier — a classification rather than a judgement, asked once per candidate rather than once per run, which is the call pattern a cheaper model is actually for. Without a model the name is simply unread, `--only` matches nothing, and the report falls back to the coordinate it always used.

    **Known and not fixed: the lite tier leaks its own reasoning into the string.** Measured live over one village, 4 of the 11 labels it read came back with the model thinking out loud inside `name` — `儲金罐oidal or standard name, but reading the exact label: 儲金罐(16級)`, one that repeated 級 several hundred times, and two more of the same shape. It ships anyway because **nothing downstream is misled by it**: `--only` is a substring match, so the real name is still found inside the junk, and no decision here rests on the name being clean — a polluted one costs a long log line and a long field in `result.json`. A `max_length` on the schema is the obvious next thing to measure, along with whether the main tier does it too; neither has been. It finds them the same three ways the wall loop does — `--at`, then Gemini, then the sweep — which matters more here than there, because the grid misses most of a village and the one thing this loop must not do is spend a scarce builder on a cheap upgrade it settled for. That is the opposite of the wall loop and for the opposite reason: there the loot is scarce, so the cheapest batch buys the most wall; here the *builder* is scarce — five of them, busy for days — so one spent on something cheap is one not available for the upgrade that was actually holding the village back. Walls are skipped, since they need no builder. **The confirmation comes in two shapes**: a wall's little dialog, and for everything else a full-screen sheet (將金礦升至10級？) whose 確認 is green — and so is a village, all over, so what separates them is that the sheet covers the storage bars. Reading the storages straight after that sheet closes reported "could not be read" on an upgrade that had in fact started, so the read goes through `_home`.

- **`donate`** gives troops to whoever is asking in the clan chat. It cannot be done on demand — somebody else has to ask first — so it is written to cost almost nothing when nobody has. The panel confirms nothing: a tap on a card gives those troops away there and then, which is what `--dry-run` is for.

- **`hero`** raises one hero in the 英雄殿堂, and reading is the default: what each hero's next level costs is the number the decision rests on, and `--upgrade <hero>` is what turns it into a purchase. Only for the hero named — which hero is worth a builder is a judgement about how the village plays, not something a price settles. It has the longest reach of the four, since a hero level runs the better part of a day. **A hero is identified by the flat colour of his card's banner**, the one identifying mark on that screen that is not artwork: the game paints each card frame in a theme colour, the same pixels at level 1 as at level 100 and the same wherever the row has scrolled. Measured over three captures at two scroll positions every hero came back within 2 of its colour, and the closest pair — 野蠻人之王 (113, 11, 33) and 飛龍公爵 (89, 0, 46) — sits 29 apart. **A price is not permission, and the button says which.** A hero the hall's own level has capped keeps its price and loses its button: the plate greys, the number stays, and a tap is answered with a red line naming the hall level it wants first — Chinese, so nothing here reads it. Measured live, 飛龍公爵 at 15 asked for 220 000 dark against a village holding exactly 220 000, and `hero --upgrade duke` reported 點了 duke 的升級，但沒有出現確認畫面, which reads as a swallowed tap rather than a button that was never live. `HeroCard.upgradable` is read off the plate instead: swept over one screen holding both kinds, a live button runs `green - max(red, blue)` from 29 to 44 and a greyed one is a perfect grey at 0, so the two do not overlap. It is checked before affordability, because the village can be holding exactly what the card asks for and the button still be dead.

    **And a third button appears in exactly that place, which spends gems** (`GEM_GREEN`). A hero already being raised has 立即完成 where its 升級 was — the same green plate, the same pixels, a number beside it — and that number is a gem count. `_resource` was a two-way test with no third answer, so the gem fell through to "dark", the number read as a cheap price, and the plate was live: measured on the live hall, `warden 268 dark upgradable=True` against a village holding 11 359 gems, one tap from finishing an upgrade with them. That is the one thing this project says must be structurally impossible, and the building menu already had its own guard for it while the hall had none. What separates them is that **the gem is the only green icon**: swept over both committed halls and the live frame, `green - max(red, blue)` runs -120 for the elixir drop and -7 to -9 for every dark one against +48 for the gem, so the line goes between rather than beside either. A card whose icon is neither resource reports no price at all, which reads it as what it is — a hero already being raised — and `_blocked` already had that message.

**A banner matching no hero is dropped rather than reported as an unknown one**: 我的軍隊 stands its own heroes on tall coloured plates, and a run that took those for hall cards walked into that screen, called it the hall, and stopped sweeping for the real one. What that costs is a hero the game adds later reading as absent, which is a run that says it cannot find him.

- **`builders`** opens the panel behind the builder counter and says what is running and when the next one comes free. The counter alone reads 1/5 and says nothing about how long, which is what left the wall loop stopped with no way to tell a ten-minute wait from a two-day one. **The rows that are running upgrades are the ones carrying a progress bar**: the panel's other two sections, 建議升級 and 其他升級, write a price in the same place in the same white, so a reader going by the text would report a gold cost as a countdown. Nothing reads the names beside them — they are Chinese and they differ in every village. A time is digits plus one unit character, and only the **first** unit is matched: the game writes them descending and adjacent, so 天 settles that the second number is hours and 小 that it is minutes. Measured across every recorded panel, one unit's own readings land within 16 bits of each other, the nearest other unit is 49 away and the nearest digit 54. The button toggles rather than opens, so a read that finds no panel is worth one more tap before it is called a failure, and the last tap shuts it again because the panel covers the middle of the village.

**Getting into the hall is three problems the sweep does not have.** Its own button is a gold crown, which is artwork, so what is located is the 升級 button beside it and the row's fixed pitch does the rest; what that button *is* gets settled by tapping it and reading the screen that came up, which is why a barracks' 訓練 costs one capture to rule out. And **a remembered spot opens a different building each time**: buildings overlap, and a tap landing on two of them cycles between them — measured at (990, 430), three taps in a row selected the hall, then the archer tower beside it, then the hall again — so `--at` taps up to `AT_TRIES` times rather than trusting a coordinate. Asking is tried before any of that now, and it is where the finder pays best: one building, so the first guess that opens it ends the search, and measured live the first guess did. **One pass of `_sweep` steps over this hall entirely**: its grid steps 160 by 120 against a building 70 to 120 px across, so the hall sat 86 px from the nearest grid point and was walked past twice. A caller looking for one particular building runs the grid again at `SWEEP_STAGGER`, which lands on the middle of each gap the first pass left — 14 px from the hall — and pays for the second pass only when the first came back empty. `--at` is a shortcut for a run that already knows, not how the command works. What no pass reaches is the lower third of a village: the grid stops at y 500 because the button row a tap opens sits below it, and a camera already at its far zoom cannot be panned to bring that ground up.

**A price is shrunk to fit its button, so how tall a digit is depends on how many of them there are.** Measured across the recorded menus, five figures are drawn 16 px tall, seven 13 to 14, and eight 12 — of which the digits with no ascender measure 11, under `MIN_GLYPH_ROWS`. So `digits_from` takes its row floor as a parameter and `parsers/building` passes a shorter one; the loot panel keeps 12, since that floor is what stops a storage bar's fill highlight reading as a digit. Without it the short digits dropped out one at a time and whatever survived was reported as the price — 英雄殿堂's own 10 400 000 came back as 14, and `ai_coc upgrade` could not see a single eight-figure upgrade while picking the dearest one it could find. `PRICE_TOLERANCE` was defined and never passed for the whole of that time, which is why it presented as a number rather than as a failure: **a truncated price is the dangerous kind of wrong**, because one that keeps seven of its eight digits still clears `MIN_PRICE` and gets spent against.

**Two things in that button row must never be tapped, and both carry an icon that reads as a resource.** 加速所有同類項目 spends a magic item and the wall ring spends rings; the speed-up's potion answers the elixir test outright, so without a guard a sweep reports "an upgrade costing 1 elixir" and a loop taps the item away. Both sit on a **blue plate**: measured at one corner, blue reads blue-minus-red of 199 to 204 and every ordinary plate reads -20 to -29. A price under `MIN_PRICE` is thrown away for the same reason, since nothing in the village upgrades for single figures.

**偵察 is not 增援.** A friendly-challenge card in the chat carries a green button of its own, and a larger one — measured 5154 px against the request's 4754 — so "the biggest green in the panel" opens somebody's village instead of the donation panel. The challenge is the card with 進攻 in red on the same row, and that is how it is skipped. Green also means nothing until the chat is actually open: with it closed that panel is the left half of a village, and a village is mostly grass.

**The donation panel floats.** It is drawn against the request card that opened it, so its top moves with wherever the chat had scrolled to — measured, y 166 on one run and y 109 on the next, 721 px tall both times. Every row on it is an offset from that top, found by reading the run of plate down a column in the panel's right margin. A card the village cannot give is drawn in greyscale, which is not a matter of degree: measured across a full panel, givable reads 52 to 101 of saturation and the rest read 0.2. **A donation cannot be judged by the cards** — a card holding twenty barbarians gives five and still reads five — so what says one landed is the panel repainting, measured at 28605 bytes for one gift against nothing at all for the cards.

**Every loop shares `ui/runner.py`, and what it mostly owns is getting back to the village.** Four different things can be in the way and none of them wants the same treatment: a game still loading wants waiting on, a panel wants `back`, a dialog wants 取消, and a dropped session wants the game restarted. **`back` is only ever pressed on a frame that is not a clear village**, because on the village it raises 確定退出遊戲嗎 — with a building menu open as readily as without — and that dialog is the same panel with 確定 in the same green in the same pixels as the one that pays for an upgrade or a wall batch, so `game_dialog` reports both buttons and picks neither: only the caller knows which question it just asked. A frame that reads as nothing at all is therefore never a clear village, whatever else it turns out to be — and `_seen_village` is what decides whether it is waited on or pressed at, since the launch patience is only owed to a game that might still be starting. Measured over four wall runs, that took the gap between a sweep tap opening a building and the first `back` from 26-34 seconds to none. A dialog has to be answered rather than read past: its own dimming is what stops the storage bars reading, though they stay perfectly legible to the eye.

**A dropped session is answered by restarting the game, not by tapping 重新登入遊戲.** The button reloads the game anyway, so the two cost the same seconds, and the tap also costs a hard-coded position belonging to one emulator at one resolution. Measured live: a `collect` run walked into the idle dialog mid-sweep, restarted, and was back on the village 19 seconds later — **on a different display**, which is why `restart_game` resolves it again rather than keeping the old one. **The 連線已中斷 dialog needs no reader of its own**: it is the same sheet with 再試一次 where 重新登入遊戲 was, it reads through `idle_disconnected` at 0.94 dark and 1.00 flat, and a restart logs in again exactly as either button would — so `_settle_game` answers it that way too, once, where before it sat under the dialog for the whole of `launch`'s wait.

**The server not answering is its own state, and the loop waits it out rather than tapping at it** (`loading_screen`, `AttackRunner._wait_out_loading`). Measured on one night of unstable servers: twice the game sat on 正在載入 with the bar at 1% for 25 to 40 minutes and came back on its own, and neither a game restart nor an emulator restart shortened either. Every reader answers None on that screen, so the attack loop spent its five attempts, `uncovered` pressed `back` at nothing, the round ended with 畫面不在主村 and `IDLE_REST`, and the log read as a game on the wrong screen rather than a server that was down — which sent the farming session into exactly the restarts that do not help. 8 of 12 rounds of one run went that way. What is read is the bar alone, because it is UI over a splash that changes with the season: the right-hand end of its grey plate, clear of the 正在載入 label across its middle, plus the purple fill at its left end, which no other screen carries. Swept over 11 464 recorded frames the fill box is what makes it clean — a grey strip alone reaches 1.000 on a result screen, and no frame that was not this screen put more than 0.006 of purple in the fill — and a plate pixel counts grey or purple, so a bar that has crept along reads the same as one stuck at the start. On it `_open_attack_menu` polls every `SERVER_POLL` for up to `SERVER_POLLS` (45 minutes, above both outages), capturing straight off the emulator rather than through `_frame` so a recorded run is not left holding hundreds of copies of the same bar, checks the state file inside the wait, and waits **once per load**: a game that loaded and then dropped back onto the screen is a server that is not staying up, and the round ends with a message naming that, or the stop, rather than the village. A restart is a new load and gets a new wait, because `restart_game` returns a couple of seconds before the village paints and the frame after it is this screen; the attempts bound the round, not the stop. `uncovered` and `_home` answer the screen without pressing `back`, and `_settle_game` names it in the reason `launch` logs when it gives up.

`_sweep` is how anything on the map is found, and the only way: every building is its own artwork and gets repainted at each level, layouts differ between villages, and the camera moves. So the sweep taps a grid and reads what the game opens, backing out of anything that turns out to be a full-screen panel rather than a menu.

**Authorization is structural now, and it used to be prompt-level.** The automation-tab checkboxes were interpolated into the agent loop's prompt as 自主升級／刷牆／自主進攻 flags, with the prompt forbidding gems, cash, deletion and account operations and nothing below it enforcing any of that. That whole layer went with the AI 助手 tab: a checkbox now decides whether a `commands.*` call is made at all, which is a branch rather than a sentence. What is left to keep in mind is unchanged — treat any new capability that spends resources as needing its own guard in code, and note the shape the two spending loops already use. The wall loop only ever taps coordinates derived leftwards from the elixir drop, so the wall ring and every gem button on the row are unreachable by construction; the hero hall reads `GEM_GREEN` off the plate rather than trusting the two-way resource test that let a 立即完成 button through.

**Stopping is a flag, not a stopped timer.** `MainWindow.automation_active` is a plain bool rather than `automation_timer.isActive()` because the worker threads read it too. Stopping used to leave the timer quiet and nothing else, so the pass in flight ran to the end. `automation_cycle` and `_queue_next_cycle` answer to it, and `MainWindow._stopping` is what carries it down into a loop already running. `AttackRunner` checks only between opponents: a battle already committed is played out, since abandoning one mid-deploy leaves the army on the field and the game on a screen the next run cannot get home from.

**And the window reads the same file, which it deliberately did not before.** `MainWindow._stopping` answers to both the button and `ai_coc stop`, so a terminal ends a window's pass as well. What made that unsafe until now was stated here as the reason the window was left off it: a second stop source with nowhere to clear the flag would have the window standing itself down the moment it started. `start_automation` taking a claim is what removed that — it overwrites whatever an earlier run left behind, so the window finally has the clearing it never had a place for. **The claim is held across the whole cycle rather than per pass**, in an `ExitStack` on the window, because every pass is its own `commands.*` call and a release at the end of each would publish `idle` through the `NEXT_CYCLE_DELAY` before the next one starts — read from outside as an emulator nobody is using. A pass's own claim nests inside that one and does nothing, and `finished` is where it goes back rather than `stop_automation`, since pressing the button leaves a battle still playing. `commands.attack` and `commands.walls` take `should_stop` as a **function parameter rather than a field on their options model**, because it is a callback and not a value: the models are Pydantic and travel from `cli.py`, and a callable on one would make it unserialisable for the sake of one caller. The default is `stop_requested`, so nothing a terminal does changed.

**Handing the emulator back is why the stop has to be latched** (`stop_seen`, `_stood_down`). The release writes `idle`, so by the time the pass returns the `stopping` a terminal asked for is gone — and a stop that ends one pass while `_queue_next_cycle` starts the next one `NEXT_CYCLE_DELAY` later is a stop that did not stop anything, which is the exact failure the paragraph above describes from the other direction. `_stopping` runs on a worker thread and only records; `_stood_down` is the UI thread acting on it, from the two places a pass can end at — `finished` and the next `automation_cycle`. And the latch is cleared in `start_automation` for the reason the claim is taken there as well: one left set by a run that stopped would stand the next one down before it had done anything.

**A headless run is stopped by a file, because nothing can send it a signal** (`ai_coc stop`, `STATE_PATH`). `should_stop` was written for the window's button and `commands.attack` simply never passed it, so it sat at its "never stop" default for the whole of the time the CLI became how the game is played: a run started from a terminal was one that could not be stopped at all. Its only other exit is a `KeyboardInterrupt` handler, and that is unreachable from outside the process — whatever put the run in the background can kill it but cannot send it a Ctrl-C, and a killed process never reaches the handler, so it leaves the army on the field, the game on a screen the next run cannot get home from, and `result.json` empty with only the log to count from. **That is one command with four reasoning steps in front of it** (kill which process, find its id, what breaks, what to clean up), which is why it was the thing a weaker model could not do. So stopping is a file: `ai_coc stop` marks `~/.ai_coc/state.json` and returns, touching neither the game nor any process. The loop reads it in two places — `commands.attack`'s round loop, and `AttackRunner.should_stop` between opponents, which is already the only place a stop is safe — so the worst case is one battle rather than one whole round of searching. The barracks wait polls it at `STOP_POLL` rather than sleeping the minute through, since a stop that takes a minute to show reads as one that did nothing. Measured live: asked at 00:19:54 while a battle was already under way, it ended at 00:21:41 with `result.json` written and the game on the village, and the 28 seconds by which it missed that round's own check are exactly why it cost a whole battle rather than none.

**One flag serves every long loop, not one mechanism each** (`GameRunner.should_stop`). `walls` answers it too, in two places. **Between batches**, which is the only safe place inside one: a batch is a menu, a confirmation and a storage read, and leaving mid-way strands a dialog over the village. Whatever it already bought stays bought, because a wall upgrades the moment it is paid for. And **during the opening scan**, which is the longest unguarded stretch a run can have and the opening of every run not given `--at`: a grid tap costs a `MENU_SETTLE` and a capture, and each wall it lands on costs four neighbour taps more, so a stop checked only between batches would sit unanswered for minutes on the one path every ordinary run takes. Leaving the sweep is safe in a way that leaving a batch is not, because the sweep already backs out of whatever each tap opened. `--rounds 0` against a village full of walls is the other run here long enough to be worth interrupting, and a stop that only worked on one of the two would be a stop nobody could rely on.

**That scan check now lives one layer down, in `GameRunner._opened`**, which is the walk the sweep, the named spots and the spotted ones all take — so every subclass gets it rather than the one that wrote it. `WallRunner._scan` still makes its own, because it has a batch loop below the walk that `_opened` cannot see. And **`upgrade` is wired to the stop now, where the other three upkeep commands are still not**: `collect`, `builders` and `hero` really are single passes measured in seconds and `donate` stops on its own the moment nobody is asking, but `upgrade` falls through to `_sweep` whenever there is no key to ask with or the finder comes back empty, which is a couple of minutes with nothing else to interrupt it. This was written down here as "single passes measured in seconds" covering all four, which was simply false for that one.

**The same file says who is driving, which is the half a flag could not do** (`RunnerState`, `claim`, `read_state`). A flag existed only while somebody was asking, so nothing on this machine recorded that a run was under way: a second session — and this project is worked on from more than one at a time — had no way to tell a farming run from an idle emulator, and was told in the chat instead, which is a step whoever is driving has to remember on every session and which nothing catches when they forget. So every command that opens ADB claims the file on the way in and writes `idle` on the way out (`read` and `stop` excepted, since neither touches the emulator), and `status` runs `running` → `stopping` → `idle`. **It is never deleted**, because a file that existed only while a run did cannot separate "nothing has run here" from "one just finished", and the second is what a session asking for the screen actually wants; `ended` and `log` ride on the `idle` record for the same reason. `ai_coc stop` can then name what it stood down, or say there was nothing to stop — which the flag could not, having written a file whether or not anything was listening.

**The claim at the start is what takes over a stop nobody read.** A `stopping` left standing by a killed run would otherwise end the next run before it had done anything, reported as a stop nobody asked for, which is the failure the old clear-at-the-start answered. The release at the other end is not its mirror: it publishes what the run was and when it ended rather than removing a request. Only the process that claimed writes it, because a run that outlived its own record must not wipe out the one after it.

**Deleting the file by hand is a stop, and it is the escape hatch rather than the mechanism.** Whoever is left when the agent driving the loop has died has one move that needs no command and no pid, and it is the one a person actually reaches for: delete the file. The loop reads a missing file as a stop and writes it back as `idle` on the way out, so the file coming back is the receipt that it really stood down. `_held` is what keeps that from firing where it should not — a machine that has never run this has no state file either, and without it every first run would read its own absence as a stop and end at zero rounds. It holds the claim this process wrote rather than a bare bool, because the deleted file is also the only place `started` lived: measured on the first deletion this ever answered, the `idle` that came back had no start time and so could not say how long the run had taken.

**Nothing here refuses a second run.** A claim overwrites whatever was there, so two commands started at once still drive the same display; the file exists to let a session avoid that rather than to prevent it, and the check belongs to whoever is about to start. Refusing would mean telling a live run from a killed one, which is a pid liveness call — and on Windows the obvious one is a trap: CPython's `os.kill` is `TerminateProcess` for every signal except `CTRL_C_EVENT` and `CTRL_BREAK_EVENT`, so `os.kill(pid, 0)` silently kills the run it was asking about. A stale `running` costs a reader one `Get-Process`, and the next claim clears it either way.

**Reading it never raises and writing it is atomic**, both for the same reason: two processes share this file and one of them is in a battle. `should_stop` is polled from inside one — between opponents, and after every tap in `GameRunner._opened` — with nothing above it catching anything but a `KeyboardInterrupt`, so an exception on a read would end the series with the army still on the field. Every failure lands on "carry on", and only a genuinely missing file is a stop. The write goes to a scratch file and renames, because `write_text` truncates first and a read landing in that window returns zero bytes, which parses as a broken file that was never broken.

**Nothing here holds the session open, and nothing should.** `ai_coc online` used to send a short drag every two minutes for exactly that, on the rule that Clash of Clans will not let an opponent attack a village whose owner is in the game. That rule no longer holds: the account's owner reports that the current game raids a village whether or not anyone is looking at it, so the whole feature bought nothing and it is gone, along with `keepalive_seconds` and the window's 保持上線. What is left in its place is the shield the game hands out after a raid: observed on the night this was measured, the village took two raids once the keepalive had died with the emulator and then carried a 護盾 reading 4 小時 20 分, so the loss is bounded without anything here running all night.

**Getting the game up is its own command, because every other one only assumes it** (`ai_coc launch`, `RestartScope`). **It now leaves the game at a village and at the far zoom** rather than at a pid: `ensure_coc` is satisfied by `pidof`, which says nothing about whether the screen can be driven, and every command after it aims coordinates measured against that one view. `_settle_game` is the shared step — poll `read_stock` until the village paints, then pinch out — and `LaunchReport.at_village` says whether it got there, because a game still on its loading screen answers every later command by silently missing what it aimed at. **Zooming out is also what centres the village**: the map clamps the camera at its own edges, so at the far limit the diamond fills the frame with its middle within about 20 px of the screen's, and nothing has to find the village to put it there. They all reach the game through `_controller`, which calls `ensure_coc` and gives up on whatever that cannot fix — so a terminal had no way back from a cold machine, an emulator that died, or a session dropped for idling that no loop was running to catch. `MuMuAdapter` had all three of these long before anything could reach them, which is the same shape as the stop above: the capability sat in the layer below while the layer that drives the game headless never passed it on. **The scopes exist because nothing down here can tell a wedged emulator from a working one** — MuMu reports the instance running and ADB answers, so only whoever is watching the screen knows. `none` is `ensure_coc` alone and costs a couple of seconds on a village already up. `game` restarts the package on an emulator left alone, and calls `ensure_coc` **first** rather than after, because a game can only be stopped on an emulator that is already up; on a cold machine that inner call is the whole job and the restart then costs one relaunch of a game that had just started, which is cheaper than refusing and naming a different command. `emulator` restarts the instance and lets the single `ensure_coc` that follows bring the game back, since `restart_coc` on top of that would relaunch a game that had only just come up. **But it has to watch the instance go down first** (`_await_shutdown`): `control restart` returns as soon as the request is sent, so the state read straight after is still the old one, and `ensure_coc` skips its entire boot wait for anything still reporting `android_started` — which aims a `monkey` launch at an emulator on its way down, and then either wastes a launch or dies on `AdbControlError` in the one command whose whole purpose is recovering from that. An instance **missing from the listing is not down either**, because MuMu drops one for a moment mid-restart and `ensure_coc` raises on an index it cannot find; only one that is listed and no longer started ends the wait. `was_running` is on the report for the same family of reasons: `ensure_coc` either returns a running game or raises, so a "is it up now" field could only ever read True, while whether this call *found* it up is the difference between a cold machine and a wasted one.

**The camera has one zoom worth being at, and it is where it already is** (`ai_coc view`, `AdbController.pinch`). Every coordinate in this project was measured at the game's far zoom limit, and measured live that is where the game sits: a pinch to zoom out from there changes nothing at all, while one to zoom in takes the bare-grass share of the frame from 0.39 to 0.23. So `--zoom out` is safe to run blind and is how a session that zoomed in to look at something gets back — but it cannot widen the view past what the game gives, which is why the lower third of a village stays out of the sweep's reach.

**A pinch goes to one node, and Android says which** (`touch_device_for`). The first version sent every gesture to every multi-touch node, on the grounds that MuMu publishes one per display and does not say which is which. It does say, in `dumpsys input`, and sending to all of them is not harmless: MuMu keeps a launcher on its other displays, where two fingers switch away from the foreground app — observed live as a zoom that worked and left the emulator showing the launcher with the game behind it, so every command after it tapped at a home screen. The chain is three hops, each one printed by the system: the InputReader device whose viewport carries `uniqueId=local:<the display's physical id>` — the same number `display_for` returns — then its `EventHub Devices: [ N ]`, then the EventHub entry headed `N:` whose `Path:` is the node. Measured live it resolves `4619827767814508545` to `/dev/input/event8` out of four candidates, and the count of candidates is not even stable between calls. A hop that will not resolve falls back to every node plus a relaunch, which is survivable where a pinch aimed at the wrong display silently is not.

**`input` has no two-finger gesture of any kind**, so a pinch is the multi-touch protocol written straight to the device node with `sendevent`. Two things make it work, both paid for by gestures the game accepted and ignored: **the device's axes are the screen's swapped** — it reports x to 900 and y to 1600 against a 1600x900 screen, so a point goes down as (y, x), confirmed by tapping (430, 990) and watching the building at screen (990, 430) open — and **`BTN_TOUCH` is not optional**. `sendevent` addresses a device rather than a display, so nothing routes it the way `input -d` is routed; MuMu publishes one touchscreen per display and does not say which is which, so the gesture goes to all of them and the game answers on its own.

**Coordinates are hard-coded to 1600x900.** Gemini returns percentages, and whatever reads them converts with `x_pct * 16, y_pct * 9` — `GameRunner._spotted` for a target on the map, `_plan` for a drop line. Any other instance resolution taps the wrong place. Related known quirk: ADB `wm size` reports 900x1600 while the screenshot arrives as 1600x900.

**`MuMuAdapter`** uses `mumu-cli.exe` (JSON output) for discovery and lifecycle only; every capture and input goes through `adb.py`. Two rules were paid for in bugs, do not undo them:

- `_clean_environment` strips `QT_PLUGIN_PATH` and friends from every subprocess, because the PyInstaller bundle's Qt plugin paths break mumu-cli, which is itself a Qt application.
- `ensure_coc` escalates launch → poll → restart instance, because MuMu reports Android ready before a `monkey` launch will reliably stick.

**`adb.py` owns ADB.** `AdbController` wraps `adbutils`, one instance per serial, and `MuMuAdapter.controller()` caches them — that is how several emulators coexist, since each MuMu instance publishes its own port (`AdbEndpoint`, port 0 meaning not listening yet). `use_adb_executable` points `ADBUTILS_ADB_PATH` at MuMu's own `nx_main\adb.exe` so the adb server matches the emulator. Do not shell out to `adb.exe` from anywhere else.

`AdbController.shell` takes a list or a string, and the difference matters: adbutils escapes every argument of a list, so shell syntax has to go as a string. `tap_many` is the one caller that needs it: a pre-joined list arrives as one unknown command name, which is half of what a battle that deployed nothing while reporting success paid for. **The other half, the sleep between the taps, turned out not to be needed at all** — see `TAP_GAP` for the measurement that replaced its reasoning, and for why zero is safe to keep given that every caller either has slack or reads the cards afterwards.

**Every capture and every input names a display.** MuMu runs several Android displays and opens the game on one of its own, leaving display 0 on the emulator's launcher. Unqualified, `screencap -p` prefixes the PNG with a multi-display warning and the decode fails, while `input tap` silently lands on the launcher. `AdbController.display_for(package)` finds the right one and returns a `DisplayTarget`; `screencap -d` takes its physical id and `input -d` its logical id, because MuMu numbers the two schemes apart. Do not drop the `-d` flags.

**`GeminiClient`** is the only place the app talks to Gemini, through the `google-genai` SDK's Interactions API. Every request body is a `GeminiRequest`, never a hand-built dict. `generate` returns the whole text; `generate_structured(prompt, SomeModel, png)` sets `response_format` from the model's JSON schema and returns the validated instance, so no code strips ```` ```json ```` fences by hand. A `stream` sat beside them, setting `stream=True` and yielding the `step.delta` text events; the chat and `--live-test` were the only callers and both went with the AI 助手 tab, which leaves every call this app makes a structured read against a fixed prompt. `list_text_models` feeds the Model picker in Settings and only appears after 測試連線 succeeds. The default model is `DEFAULT_GEMINI_MODEL` in `constants.py`.

**Storage** lives in `~/.ai_coc\`: `controller.sqlite3`, `account_json/` (one `VillageExport` per account, which is what `ai_coc export` writes and `--last` reads back), `config.json`, the DPAPI-protected `gemini.key.dpapi`, `state.json` (which command is driving the emulator, and whether it has been asked to stand down), and `logs/` holding one directory per run. The schema is created idempotently in `Database._initialize` with no migration tooling, so a changed table means bumping `SCHEMA_VERSION` and handling existing databases yourself. **A table that stops being created is the case that needs the second half of that**, since it survives on every database that already had it and on none made afterwards: `knowledge` and `tasks` belonged to the AI 助手 tab, so `_initialize` ends with a `DROP TABLE IF EXISTS` for each. The API key never goes into `QSettings`, only into the DPAPI file.

**One settings file, because a run has to play the same way from either side** (`AppConfig`, `adapters/config.py`). Loot thresholds, storage limits and the Gemini model all used to live in `QSettings`, which only the window can reach, so a run started from a terminal got the field defaults instead — all three thresholds at zero, which is "attack the first opponent shown". That was written down as deliberate and was, for a loop being studied; it stopped being deliberate the moment the same command became how the game is played, and it cost a battle against a village holding 70k gold under a 500k threshold. `AppConfig`'s own defaults are the ones the window has always shown rather than the field defaults underneath them, since `LootThresholds()` means "take anything" — right for a model, wrong to farm with; `stop_at` carries its own 90 for the same reason, because a 0 there is "never stand down". A file that will not parse raises rather than falling back, for the same reason. `attack --min-gold/--min-elixir/--min-dark` overrides the file for one run, and `None` and `0` mean different things there: omitting a flag keeps the configured value, passing zero takes that threshold out, which is how a run being studied gets the old behaviour back. `probe` and `bounds` stay on `LootThresholds()` — they want any battle at all, not a good one. The storage limits reach a headless run now too, so a full village stands one down before it searches; the report says which resources stopped it, and `--repeat` ends the series there rather than coming round to read the same full storage. `--stop-at` overrides that percentage for one run on the same `None` against `0` terms, and zero is there for one situation: a test battle is played against whatever village the farming left behind, and a farmed village is a full one, so without it the file's value ends the test series before the code under test has run. **Every watched storage has to be full, not one of them** (`StorageCapacity.full`). It began as any-of-them, on the reasoning that loot past a full storage is thrown away on collection — true, but that prices the search fee against one resource when a battle brings home three. What settled it was a live village whose elixir cap had grown to 21.5M against a configured 20M: every check stood the run down with five million of gold room unused, and no amount of farming could ever fill it. **A share of the ceiling rather than an amount is what killed that whole class of bug**, and what let the two villages share one setting: the numbers are read off the game, so nothing goes stale and nothing has to be typed twice. A resource whose ceiling would not read is left out and neither stops a run nor holds one open, which is what the builder base's absent dark elixir relies on. That is also what ends a testing session early, so a run of battles wants somewhere for the loot to go. **The models live in a `gemini` block with one entry per tier**, `main` and `lite`, each holding `model` / `base_url` / `thinking_level`. Two rather than one because the two call patterns differ, which is the only thing that justifies a second model at all: `main` answers **once per run** against a whole screenshot — the attack plan, the target finder — so nothing there is racing anything and the better model is simply the right one, while `lite` answers **once per candidate** on a cropped strip. Named for the role rather than the product, because a key called `flash` holding `gemini-4-pro` is a lie the file keeps telling. A tier is exactly a `GeminiSettings` minus its key, so building a client stopped being four lines of copying one field name onto another — and **the key is not in that block, deliberately**: `ConfigStore.save` writes every field of every nested model, so a slot there would put an empty `api_key` in a plaintext file beside the DPAPI store built to keep it out of one. `GeminiClient` carries it as its own field. A file written before the tiers existed, holding a flat `gemini_model`, is not carried over: the before-validator that lifted it into `main` was a migration, migrations do not stay, and the rewrite below drops the stale key so such a file comes back on the default model. `thinking_level` is here for the same reason as the model: every call this app makes is a screen read against a fixed prompt, so the budget buys latency rather than a better answer, and `low` is the default for both tiers. **A file holding a key the model no longer reads is rewritten to what it does read.** Pydantic ignores an unknown key, which is what keeps an upgrade from failing and what leaves the key sitting in the file looking like a setting still being honoured: `timings` survived in every existing file after every clock moved onto the plan, so a user editing 大守護者's thirty seconds there would have been editing nothing at all. The same pass fills in a key the file never had, and a file that already matches is left untouched, since a run that only reads it has no business changing its timestamp. **The emulator is restarted on a schedule, because MuMu drops frames** (`restart_every`, `_restart_emulator`). Nothing here measures that and nothing can: the drop belongs to the emulator, builds over hours, and by the time it shows the run has been playing badly for a while already. So this is the one number in the file that is somebody's observation rather than a measurement, which is exactly why it belongs in the file — whoever is watching the screen is who gets to change it. `--restart-every` overrides it for one run, and `0` there turns it off where omitting the flag keeps the file's value.

**It counts battles rather than rounds.** A round that found no opponent, or backed out on a half-trained army, barely touched the emulator — counting rounds would spend restarts on a run that has mostly been waiting for barracks, and the empty rounds a restart itself costs would feed back and make it restart more often still.

**And it waits for a village rather than for the process.** `launch("emulator")` returns as soon as `ensure_coc` has seen the game's pid, and that pid exists seconds after the `monkey` while the village is not on screen for much longer than that. `display_for` raises on a game with no window yet, and `AttackRunner` has none of `GameRunner`'s patience for one still loading — `_open_attack_menu` gives up after about 32 seconds of tapping at a loading screen, which costs a round off the count and then `IDLE_REST` on top of it. So the restart polls `read_stock` until the village reads, which is how every loop here tests for the home village anyway. **That the village reads is the signal; what it reads is not** — measured on a live restart, the storage bars animate up from zero while the game loads and the first frame that resolved came back at 12.4M gold against a real 19.7M, so a number logged there reads as a village raided overnight.

**A restarted game does not come back at the zoom everything was measured at, and that is the failure this feature could most easily have caused.** Observed live: the restart succeeded, the village read, the loop carried on — and every battle after it deployed nothing at all, reporting `0 of 4 hero card(s) landed` and `3 troop card(s) still hold something` for two rounds before a recorded frame showed a battlefield zoomed most of the way in. The drop line, the card row and the spell grid are all screen coordinates taken at the far limit, so a zoomed-in game misses all three. `_restart_emulator` therefore pinches out before handing the run back, which is safe to do blind because zooming out past the limit does nothing.

**And a cold boot is not a fixed cost.** Measured on one machine within a single run, the first restart had the village up 22 seconds after `launch` returned and the second had not got there in 120 — which is the feature arguing for itself, since an emulator slow enough to need restarting is also slow to come back. `RESTART_POLLS` is therefore sized for the bad case: a run that reaches the end of it loses the series, while one that waits an extra minute loses a minute. Each poll also logs which of the two states it is still waiting on, because a game with no window yet and a game stuck on its loading screen are the same sentence to the caller and different problems to whoever reads the log. **Both the runner and the frame ticker are pointed at what came back**, since MuMu opens the game on a display of its own choosing and a ticker left on the old one spends the rest of the night timing out into warnings nobody reads.

What stays in `QSettings` is what no terminal command asks for: the automation checkboxes, the live preview, the retry interval. The step that once carried the registry's thresholds and model over into the file on the first run is gone with the rest of the migrations: every machine running this has had the file for a while, and a migration left in place is a code path nobody exercises.

**Village export** (`ai_coc export`, `commands.export`, `parsers/settings.py`, `adapters/clipboard.py`). The game will write the whole village out as JSON — every building, every level, every troop — which is the one complete account of what a village holds and far more than the screen readers can see. It lives behind 設定 → 更多設定 → scroll to the bottom → 複製, four fixed coordinates measured on the live game.

**It used to ask Gemini where each of those buttons was**, once per step, through a `locate_target` prompt and a `LocatedTarget` model that are both gone now. Nothing about those buttons moves, so that was an AI call for a constant — and an unreliable one, since a wrong answer is a tap at a coordinate nobody chose.

**What replaces the AI is not the coordinates but the reading.** Each step confirms its own screen before the next tap, and the reason is the page itself: the top of 更多設定 carries a red 刪除帳號 button, and while that one sits far above the copy coordinate and scrolling only pushes it further up, a scroll that did not take leaves the tap on the 更高幀數 toggle — which flips a game setting and reports nothing at all. `settings_open` needs **two** features rather than a threshold: its 更多設定 plate reads 0.422 green, but a battle result screen puts 0.262 of its own 回營 button in that same box and an event reward page 0.205, both found by sweeping every committed frame. The SUPERCELL ID band across the top is what no other screen has — 0.806 blue against at most 0.047 on all 66 of them. `export_row` is two features for the same reason: the white word JSON is 0.280 on the row and 0.094 at the top of the page, but 0.938 on the settings window, whose cream panel fills that box, so the 複製 plate beside it (0.452 against 0.000) is what rules that one out. JSON is read rather than the Chinese beside it because it is latin text the game leaves untranslated in every language it ships.

**The payload leaves through the Windows clipboard, not through ADB.** The copy button writes to the **Android** clipboard, and reading it from that side was measured and rejected: `cmd clipboard get` has no shell implementation on this emulator (Android 15, SDK 35) and `am get-clipboard` is gone, which leaves only the binder service, called by a transaction id that moves between Android releases and fails silently when it does. **Nor by trying that first and falling back to this**: its refusal is a plain string rather than a non-zero exit, so the test would compare against output nobody has seen succeed — and all three ways it could go wrong (a background read refused, a 7 KB payload truncated by `adb shell`, a failure indistinguishable from an empty clipboard) hand back a village JSON that still parses and still carries a tag. `adapters/clipboard.py` carries what would have to be established before that path is the more reliable one. MuMu mirrors the clipboard onto Windows, which is where the GUI's old 匯入剪貼簿 path was already reading it from — through Qt, so a terminal could not. `adapters/clipboard.py` reads it through ctypes instead, and CLI and GUI now share the one call. **The clipboard is emptied before the copy is tapped**, so what turns up afterwards is known to be new: measured, a cleared clipboard stayed empty for ten seconds with nothing copied, and without that a tap that missed reads back the last run's payload and reports success on it. **And whatever was on it is written back afterwards**, because it belongs to whoever is at the keyboard and this is worth running while they are in the middle of something else — verified live with a sentinel string, which survived a full export. That write is why `_opened` names an owner window: opened with NULL, `EmptyClipboard` sets the owner to NULL and every `SetClipboardData` after it fails, so the restore would silently leave the clipboard empty rather than putting anything back. Nothing here has a window of its own, so it borrows the desktop's.

**Only the named result is kept, and nothing is lost keeping it.** The file under `account_json/` used to hold the game's raw payload under `raw` alongside the parsed entities; it now holds one `VillageExport` — every section as entities, every field of every row still on them through `VillageEntity`'s tolerance, plus the export time and the boosts. `name` is None where the community mapping has no entry rather than the number repeated: measured on one real export, 65 of 226 have no name, and writing the id into the field would hide which ones to revisit when the mapping catches up.

**Village parsing is deliberately tolerant.** Unknown sections and fields are preserved verbatim, unknown `data_id`s are queued into `unknown_entities` instead of failing the import. Game updates add IDs; keep it tolerant. **That is why there is no list of section names any more**: there was one, of twelve, and measured against a real export it was dropping ten of the game's own — `helpers`, `decos`, `obstacles`, `skins`, `house_parts` and their builder-base twins, including three helpers the mapping does name. A section is now whatever the document holds a list under, so one the game adds next release survives without a code change, and a row written as a bare number (`skins`, `house_parts`) is read as one too.

## Project rules

- **Every structured value is a Pydantic `BaseModel`, no exceptions.** New shapes go in `models.py`: emulator and CLI payloads, database rows, parsed files, AI replies, requests, settings and the chat transcript. The adapters are models too (`Database`, `SecretStore`, `AdbController`, `MuMuAdapter`, `GeminiClient`), so they take keyword arguments and put their non-field state in `PrivateAttr`. Only Qt subclasses and the ctypes `DATA_BLOB` stay plain classes, because their base class rules it out. Do not introduce a `dataclass`, a `TypedDict`, or a bare `dict[str, Any]` that travels between functions, and do not read a value out with `.get("key")` when a model could have declared the field — historical key names belong in `AliasChoices`, not in an `or` chain. Parse at the boundary with `model_validate` / `model_validate_json`, and write JSON out with `model_dump_json()` / `model_dump()` rather than `json.dumps` over a hand-built dict; a bare list that travels between functions gets a `RootModel` (`AttackSeries`). Both of the ones that used to make this point — `UiElementList` and `AccountRowList` — were lists on their way into a prompt and went with the AI 助手 tab, so nothing here builds a prompt out of a list any more. Ask Gemini for structure through `GeminiClient.generate_structured` and a model, never by parsing the text yourself. Models mirroring an external format that gains fields between releases carry `model_config = TOLERANT` so unknown keys survive.
- **A model field's type must be importable at runtime.** `[tool.ruff.lint.flake8-type-checking] runtime-evaluated-base-classes` keeps `TC003` from moving those imports into `if TYPE_CHECKING`, which would leave the model unbuildable. If a new model base class appears, add it there.

- **Send the user every image you look at.** Whatever you captured, whatever the loop recorded, whatever you read in from somewhere else — if you looked at it and drew a conclusion from it, send a copy rather than leaving a path behind. Almost every question in this project is settled by looking at a frame, so the user is looking at the same frames you are; they just cannot see your tool output. - **Deliberate deviations from the repo template**, documented in `pyproject.toml` comments: coverage gate is `--cov-fail-under=75` rather than the template's 80, because `ui/main_window.py` is the untested PyQt shell and a seventh of the statements — the suite measures 81% with everything under the window around 90%, and the gap is what a change may cost before it is asked to bring tests with it; `[tool.ty.environment] python-platform = "win32"` is required or `winreg`/`ctypes.windll` fail to resolve on Linux CI runners; ty excludes `cli.py`, `ui/main_window.py` and `ui/workers.py` because PyQt5 ships inaccurate stubs; `allowed-confusables` carries `／` and `？` for the Chinese UI strings; `check-added-large-files` excludes `tests/frames/`, because a screen fixture is a 1 to 3 MB PNG whose exact pixel values are the measurement and quantising one loses what it was committed to prove; the sdist ships no `tests/` at all, because the suite is nothing without those same frames and they are 33 MB of a live account's screen carrying player and clan names, which an sdist would publish to PyPI whatever this repository's own visibility is; the `build_release.yml` matrix is Windows-only because nothing here runs elsewhere, and **`test.yml`'s is too**.

**That last one was paid for by a green CI that was testing almost nothing.** `adapters/mumu.py` imports `winreg` at module scope and `commands.py` imports that, so on a Linux runner `test_core.py` failed to import and its 208 tests never ran — 15 did, out of `test_ai.py` and `test_render.py`. The job stayed green because `uv run pytest | tee` reports **`tee`'s** exit code, so pytest's own result was discarded: a collection error, or any failing test, read as a pass. Both are fixed: `windows-latest`, and `shell: bash` on that step — Actions runs that as `bash --noprofile --norc -eo pipefail`, where the implicit shell it replaces is `bash -e` alone. The shape is worth remembering — **a suite that cannot import is indistinguishable from a suite that passes**, unless something checks the count. `code-quality-check.yml` stays on Linux, because ruff and ty read the source rather than import it, and ty is told the platform anyway.
