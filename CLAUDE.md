# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Windows-only PyQt5 desktop application that drives Clash of Clans running inside MuMu Player 12. Gemini does the semantic screen reading; the app turns its answers into ADB taps and verifies the outcome on the next screenshot. Farming attacks read the screen themselves rather than asking Gemini what is on it: `ui/attack.py` drives them from template-matched reads, and calls Gemini exactly once per attack, for the tactical choice alone. See **Attack loop** below.

## Development flow

Read `gh-dev-flow` before starting; it owns the path from a task landing to the change being merged. In this repo that path always ends the same way: open the PR as a draft, run `code-review` over the branch and fix what holds up, then merge once CI is green. Merging on green needs no further approval.

## Commands

```bash
uv sync --group test                 # the suite needs the `test` group
uv run pytest                        # full suite (xdist, coverage gate, JUnit/XML into .github/reports)
uv run pytest tests/test_core.py::ScoutTests::test_loot_is_read_over_grass      # single test
make fmt                             # pre-commit: ruff, mdformat, codespell, ty, gitleaks, uv-sync/lock
make gen-docs                        # rebuild docs/ from the READMEs and the source
```

Run the app with `uv run ai_coc`. Two CLI hooks exist for smoke tests: `--live-test` captures a frame and asks Gemini to describe it, and `--agent-command=<text>` types a command into the AI tab and executes it. Both save a proof screenshot of the window when `COC_LIVE_TEST_SCREENSHOT` / `COC_AGENT_SCREENSHOT` point at a path.

Four sub-commands run headless instead, and they are how the game is worked on:

```bash
uv run ai_coc attack --frames <dir>       # one attack pass, no window, every frame it reads kept
uv run ai_coc attack --plan-in tuned.json  # play a written tactic, no AI call at all
uv run ai_coc attack --plan-out used.json  # write down whichever plan actually ran
uv run ai_coc read <png>                  # what each parser makes of one frame
uv run ai_coc capture <dir> --count 30    # a burst off the live game
uv run ai_coc probe --frames <dir>        # spend a battle measuring the real boundary
```

**Running real attacks to gather evidence is cheap, so do it rather than reasoning from one sample.** Training troops costs nothing in current Clash of Clans and the search fee is negligible, and neither does a battle that goes badly or deploys nothing at all — a run spent entirely on probes is a normal thing to spend, not a mistake to apologise for. The only real budget is the wall-clock time an army takes to train, and `MIN_ARMY_RATIO` backs a run out for free before the fee when it is not ready. `--frames` names each capture for what the loop was asking (`0006_probe`, `0010_pass`, `0018_banner`), which afterwards is the only thing separating a frame the parser misread from a tap that never landed.

Distributables are built in CI only: pushing a `v*` tag runs `build_release.yml`, which publishes the wheel to PyPI and attaches a PyInstaller Windows build to the release. There is no local build script.

`scripts/gen_version_file.py` writes `version_info.txt` from the resolved version just before PyInstaller runs, which is what puts a version into the executable's Windows file properties. That file is gitignored: a committed copy could only go stale.

That build defaults to `--onedir`, and the dispatch form's `package_mode` switches it to `--onefile`. Measured here, onefile costs 6.6-7.0 s to reach the first log line against onedir's 1.4-3.1 s, because it unpacks the whole bundle into a temp directory on every launch. Onefile is one 76 MB file where onedir is a 174 MB folder, so it stays available, just not the default.

## Architecture

`src/ai_coc/cli.py` is the entry point behind both console scripts (`ai_coc` and `cli`) and the PyInstaller build. PyInstaller runs it as `__main__`, so its imports stay absolute even for same-layer modules and it keeps an `if __name__ == "__main__"` block.

The three layers are directories, so an import that crosses them is visible in the import line:

- **UI and orchestration** — `ui/main_window.py` (`MainWindow`), all five tabs plus every workflow; `ui/attack.py` (`AttackRunner`, the farming attack loop, kept Qt-free so it can be driven and tested without the window); `ui/workers.py` (thread-pool workers and the log handler); `ui/render.py` (Markdown and log records to HTML). `cli.py` is only argument parsing and `main()`, and `commands.py` is the headless side it dispatches to: a feature reachable only through a widget cannot be run against the live game while it is being worked on, so new work belongs somewhere `commands.py` can call it.
- **Adapters** — `adapters/mumu.py` (emulator lifecycle), `adapters/adb.py` (every ADB call), `adapters/ai.py` (Gemini), `adapters/secrets.py` (DPAPI), `adapters/database.py` (SQLite).
- **Pure parsers** — `parsers/village.py`, `parsers/scout.py`, `parsers/boundary.py`.
- **Data shapes** — `models.py` at the package root holds every Pydantic model in the project; see the Pydantic rule below.
- **Prompts** — `prompts/*.md`, one file per prompt, loaded once into `PROMPTS` and filled in by `render`. A prompt is content rather than code: it is reworded far more often than the code around it, and a wall of quoted Chinese inside a module hides both. Each file is a `str.format` template, so a literal brace has to be doubled. They ship in the wheel because `[tool.hatch.build]` includes the package directory, and `build_release.yml` needs its `--add-data` line for the PyInstaller build to carry them.

Imports across layers are absolute (`from ai_coc.models import …`) and within a layer relative (`from .adb import …`); Ruff's `TID252` enforces it and rewrites the rest.

**Threading.** Every blocking call goes through `MainWindow.run_async`, which wraps the callable in a `Worker` (`QRunnable`) on the global `QThreadPool` and delivers the result back to the UI thread via `pyqtSignal`. A call that produces text as it goes uses `MainWindow.run_stream` and a `StreamWorker` instead: it drains a generator and emits each chunk. Never call `MuMuAdapter` or `GeminiClient` directly from a slot.

**The AI 助手 transcript is a model, not a text buffer.** `MainWindow.chat` is a `ChatTranscript`; `_say` appends a `ChatMessage` and `_paint_chat` re-renders the whole transcript into the `QTextBrowser` through `ui/render.py`. Bodies are Markdown, rendered by `markdown-it-py` with raw HTML disabled, and styled by `CHAT_STYLESHEET` (Qt honours only a subset of CSS 2.1). A streamed reply grows the last message in place, and repaints are throttled by the `chat_repaint` timer rather than fired per token.

**Logging.** `configure_logging()` in `main()` sets up a rotating plain-text file at `~/.ai_coc\logs\controller.log` plus a `rich` stderr console; `MainWindow._attach_log_panel` adds a handler that renders every record through `rich` and mirrors the resulting HTML into the 執行紀錄 panel under the tabs, and the panel's level selector retargets the root logger at runtime (DEBUG adds full prompts and replies). The file handler stays plain text so the log can still be grepped. `Worker.run` logs the traceback before the message box, and `sys.excepthook` catches what Qt would otherwise swallow. New adapter code is expected to log its own decisions; a feature that fails silently is the bug being fixed here.

**Agent loop** (`execute_agent_command`): ensure CoC is running, then loop up to `max_steps` (8 normally, 25 when the command mentions 進攻/戰鬥/搜尋資源村). Each step captures a screenshot plus a `uiautomator dump`, sends both to Gemini and reads back an `AgentAction` through structured output, applies it, sleeps 2 s and re-observes. Anything outside `tap|back|swipe_up|swipe_down` ends the task, so a new action verb needs a `Literal` member on `AgentAction`, a branch in `_apply_agent_action` and a mention in the prompt.

**Attack loop** (`ui/attack.py`, `parsers/scout.py`). 攻擊 → 尋找對戰目標 → 軍隊畫面的攻擊 → scout → deploy or skip → 回營, driven by `AttackRunner`. **Nothing in the loop asks Gemini what is on screen.** The scout screen is why: it expires after 30 seconds, and when it does the game forces the battle to start and removes the 下一個 button, so a vision call per candidate neither reliably fits the window nor is worth paying for on an opponent that gets skipped. `read_scout` matches the loot digits against ten bit-pattern templates instead — a whole frame reads in about 0.15 s — and returns three states the loop needs to tell apart: `None` (正在搜尋對手, no digits where the panel would be), a view with `can_skip=True` (the scout window), and one with `can_skip=False` (the loot panel stays on screen after the countdown, so skippability is read from the 下一個 button's orange instead). Everything is hard-coded to 1600x900 like `_apply_agent_action`, and `read_scout` raises on any other size rather than reading garbage.

Gemini enters at exactly one point: `_plan` asks it, **once**, how to attack an opponent that has already passed the loot thresholds. A skipped opponent therefore costs nothing, and one call fits the 30-second window where a call per candidate does not. It answers an `AttackPlan`, whose `deploy_start` and `deploy_end` are **required** for a reason: with defaults they were optional in the JSON schema and three runs running came back with a start and no end, so the call was paid for and the line thrown away every time. It answers the two ends of the line to drop the troops along, where each rage goes, where each freeze goes, and **which hero each card holds**. The prompt asks it for the side with the *heaviest* defences, which reads backwards for a farming run and is deliberate: current troops take defences head on, and a drop aimed at the loot instead leaves the storages soaking damage as tanks that never shoot back while the defences that do are still standing and killing the army. That last one is why the same call covers abilities too: timings live in `AttackTimings`, keyed by hero rather than by card position, because an upgrading hero cannot take the field and its card simply disappears, shifting every slot after it. A queen wants her cloak almost at once where a warden's tome is worth holding. The freeze carries its delay there as well, since it is the one spell held back and it needs a time of its own rather than whatever falls out of the ordering. One point per bottle for the spells, not one point for all of them: freezes stacked on a single spot are one spell's worth of effect for the whole cargo.

A drawn line is only used when it could work. `planned_line` rejects one whose midpoint sits within `MIN_LINE_RADIUS` of the screen centre, because `push_out` moves a point *away from that centre* and so cannot move a point sitting on it: a line straight across the village would be refused at every probe with nowhere to be pushed, losing the whole army. That is what `deploy_from` is still for — the four named flanks are the fallback, each already known to run outside the boundary. `ai=None`, a failed call, or a rejected line all land on the same fallback plus `RAGE_PATH`, so the loop still runs without a key.

Before any of that, `army_strength` reads `305/305` off the 我的軍隊 screen and backs out below `MIN_ARMY_RATIO`. That screen comes up *before* the search fee is charged, so a half-trained army costs nothing to walk away from. The digits are found by what they are not: every real digit matches a template within `ARMY_DIGIT_TOLERANCE` while the slash reads 25 and the troop icon 74, so anything over the line is a separator.

Deployment reads the card row rather than assuming it. `card_groups` splits the row where the game leaves a wider gap (11 px between cards, 25 or more across a group), which yields troops, siege machine, heroes, spells in that order. It is only valid on a **full** row, which is why `_scout` hands its frame to `_deploy` rather than letting it take its own: once cards grey out the row fragments below the detection floor, and the battlefield visible past its ends starts reading as a card of its own. The empty slot the row ends with is a dashed outline with the battlefield showing through, so it segments as a card whenever the ground behind it is bright enough and then arrives as one more hero to drop, which cost a run all five of that card's attempts; every real card carries a level badge in its bottom-left corner and that slot does not, which is what `_badged` reads. `counted_cards` then separates spells from heroes and the siege machine — troop and spell cards carry an `xN` in the corner, reading 0.21 of it in white against at most 0.03 for the others. `card_count` reads the number itself where it can, and returns None where it cannot: over a pale illustration the count merges into the artwork, which shows up as an `x` glyph of the wrong width. Its *presence* is always unambiguous even when its value is not, which is why the two are separate calls.

The order is the attack itself, not an implementation detail: **the siege machine** goes first as the tank that opens the path; then the troops down the flank; then **rage** along `RAGE_PATH`, the route they are about to walk. Rage used to be cast before any of them, on the reasoning that the troops should be inside it the whole way in — which holds only if they land at once, and they do not. Measured across three battles the last troop is down 30 seconds after the first spell and the heroes 39, against a rage that lasts 18, so cast first it had expired before most of the army was on the field. Then the heroes, and after that everything that waits on a clock runs from one sorted schedule in `_run_schedule`, each move at an absolute moment rather than a delay. Two clocks feed it, because the two numbers mean different things: a hero's ability is timed from **that hero landing**, which is what a queen's cloak is worth, while the freeze is timed from the **attack opening**, because that is how it is judged on screen — about half a minute in, as the push reaches the first line of defences — and hanging it off the heroes would move it by however long the army happened to take to go down. Freeze used to be cast after the last ability, which meant it inherited the slowest hero's timer: a champion at 45 seconds put it a minute and a half into a three-minute battle, long after the defences it was meant to stop had done their work. One bottle per planned point; every spell gets cast, because one carried home does nothing. `freeze_cards` separates the two: freeze is the only spell CoC draws in cyan, reading (141, 224, 242) against rage's (163, 137, 201).

Spacing follows the spell's real footprint. A rage reaches 5 tiles, and the 44x44 map spans about 1040x605 px here, which puts a tile at roughly 24x12 — so the footprint is a **240x120 ellipse**, not a circle, and `RAGE_PATH` is spaced at that pitch. Two overlapping rages waste one.

Timing is load-bearing too. A troop card is tapped repeatedly, so a swallowed tap costs one troop, but a hero, siege machine or spell gets a single attempt. Selecting a spell opens a radius indicator before it will accept a placement: measured live, a placement 0.6 s later was still swallowed where 1.5 s went through. Only the *selection* is slow — the card stays selected while it still holds something, so the rest follow as a fast burst. Casting each spell as a full select-and-place took 18 s, by which point a rage cast first had nearly run its 18 s duration out before the troops even landed. How many times to tap comes from `card_count`, the card's own `xN`, plus one for slack.

The troop cards are emptied in small passes, each pass's drops spaced across the whole line and rotated per card, so a card holding one troop does not pile it where every other card started. `live_cards` says which cards are spent — a spent card goes fully greyscale, which brightness alone does not separate — so passes stop as soon as the cards are empty rather than running a tap count guessed up front. The row is walked once more after a delay because a hero card taps into its ability once the hero is on the field.

**A tactic is a file, not a set of constants** (`plans/flat.json`, `AttackPlan`). `_plan` settles on one of three: the plan handed to the runner, which skips Gemini entirely and is what `--plan-in` fills; the one Gemini answers; or `plans.flat()`, the everything-spread-evenly default that reproduces exactly what the loop used to hold in `DEPLOY_LINES` and `RAGE_PATH`. Flat is a safe tactic rather than a good one — it runs against any village and gives a baseline to compare against. A plan carries `timings` as well as points, so a written one is the whole tactic in one document rather than positions whose schedule lives somewhere else; `--plan-out` writes back whichever ran, which is what makes a battle worth repeating repeatable. Like `prompts/`, the directory ships through `[tool.hatch.build]` and needs its own `--add-data` line in `build_release.yml`.

**The battle map is a diamond, and `MapFrame` is what says where** (`models.py`, calibrated in `parsers/boundary.py`). `VILLAGE_GRID` is the 44x44 grid the buildings sit on and carries the tile-to-pixel conversion; `DEPLOY_BOUND` is that grown by five tiles, which is the ground the game will accept a drop on. Both are read off live frames rather than detected in them, because a village theme repaints the ground the edge runs along while the camera stays put, and both are good to about 20 px — enough to keep a pushed drop on the map, not enough to land on a chosen tile. `push_out` clamps to `DEPLOY_BOUND` and not only to the playfield rectangle, whose own corners are off the map: a hero refused four times ended up at (30, 175), where the map spans x 596 to 1004.

**The deployment boundary can be read rather than guessed** (`parsers/boundary.py`). The game draws its own red stroke around the ground it will refuse, for the whole battle rather than only while a card is selected, so one screenshot carries it. It is UI painted over the scene, so a village theme changes the ground under it and not the stroke: measured across four themes, red sits between 125 and 220 with `red - max(green, blue)` at 85 to 105, against -20 to -30 for the grass beside it. The red ceiling is load-bearing — a wall highlight reads (255, 71, 0) and a fire (255, 140, 24), both of which clear the score. `boundary_reach` returns how far the stroke reaches along one ray rather than a polygon, because a line to spread troops along is all the loop ever wanted, and it answers nothing at all where the crossing sits closer than half the distance the ray was able to travel: a ray stops at the playfield edge, so where the boundary lies beyond that edge the ray never meets it and whatever red it grazed becomes its answer. Two live surveys put every crossing that matched the game at 0.62 of the distance travelled or more, and every one that turned out to be inside the village at 0.45 or less. A wrong reading costs more than no reading, because the loop trusts it and pays five refusals finding out. `fitted_line` bends a preset flank onto it through **three** anchors, not two: a village is a diamond, so a straight chord between two boundary points cuts back inside across its middle, and fitting only the ends had two flanks in a row refused at all five pushes before a third worked. `deploy_line` walks whatever anchors it is given, so the drop line follows the village. It is a better opening guess, **not** a guarantee: a ray whose boundary lies past the playfield edge never meets it, and the probing and pushing below stays as the backstop. `ai_coc probe` is how to find out how good the guess currently is — it spends a battle dropping two troops either side of the predicted line on twelve rays and reports how many agreed. Its first run measured 7 of 12, with four of the five disagreements putting the line *inside* the real boundary, which is why `fitted_line` throws away a fit whose three anchors sit at wildly different distances: an anchor inside the village is the expensive way to be wrong, since the line then cuts through and every probe on it is refused.

**Nothing can be deployed until the countdown ends, and the loop waits for it** (`_wait_for_battle`). A tap the game ignores raises nothing at all, so probing during the scout countdown drains no card and every flank would read as unusable. With a key this never showed, because the planning call outlasts the countdown by itself; without one `_plan` returns at once and every run would have probed into it. The wait hands back the first battle frame too, which is what `fitted_line` moves each preset flank out onto before the first probe.

**The camera is measured, not assumed** (`village_box`, `_settle_camera`). Everything else reads it without being able to check it: `push_out` moves a drop away from the screen centre, the preset flanks are screen coordinates, and the spell grid is spaced off the middle. The same red stroke answers where the village is — the four UI panels painted in the game's own red are masked out, and the box is cut where 2% of the stroke lies outside it rather than at its last pixel. Measured across nine battles and both theme fixtures the game opens every attack with the village already within 35 px of the centre, so `_settle_camera` normally reads once and does nothing; `CAMERA_TOLERANCE` keeps it that way and leaves the drag for a camera genuinely left somewhere else. It runs before `_plan`, so the planner is looking at the screen the drops will land on. A single-finger swipe pans the battle camera about 1:1 for small drags and clamps at the map edges; **with a card selected the same swipe deploys troops along its path instead**, which is why this happens before anything is tapped.

**A drop is judged by the card that made it, never by the screen** (`card_drained`, `field_units`). The game gives no usable refusal signal. Measured live: a troop tapped inside the boundary is as often swallowed in silence as it is answered with 你無法在紅線區域內派遣部隊; 請選擇其他兵種, 已部署所有兵力 and 該法術已用完 are the same red in the same place; and a burning building fills the same box. Reading that banner meant `_usable_line` returned 0 on its first try every time so the flank was never actually tested, `_spread_troops` pushed the flank out twice in every one of six recorded runs for refusals that never happened, and every hero came back "landed" whether it went down or not — one recorded run reported four of four while the fourth never left its card. What the game does say is on the card. A counted card repaints its `xN` corner when it loses one, by 368 to 1139 pixels against exactly none for a card that did not, so `card_drained` reads the corner rather than the number and works on the giant's card where the count itself will not read at all. A hero's card does not empty, because it becomes the ability button, so `field_units` reads the health bar that appears over it instead — 0.33 to 0.37 of that strip against at most 0.02. Both take about a second to appear, which is what `DROP_SETTLE` is for; on a hero a false negative is not free, since the retry taps its card again and that is its ability.

**The drop line adapts, because layouts vary more than any fixed line survives.** `_usable_line` drops troops at both ends and the middle of a line as probes and asks whether the card drained, then pushes the flank further from the middle and probes again, clamped to `PLAYFIELD`. It returns **how many steps out it got to**, not the line, because everything downstream keeps pushing from there; restarting that count at zero made the deploy loop's first push land back on the line already in use, so a real refusal moved nothing. `_spread_troops` pushes again mid-deploy when a whole pass drains nothing, because probing the ends is not sufficient: the village is a diamond, so the ground around it is **not convex**, and a line with both ends outside the boundary can still cut through it. This was paid for by a battle that deployed nothing at all against a village whose boundary reached past every preset line. `_wait_out_battle` is still the backstop underneath: loot that never moves across a whole battle means nothing was placed, and the report says so rather than claiming success.

**Every point a drop can land on goes through `clear_of_controls`**, which holds it inside `PLAYFIELD` and lifts it off the 放棄 button. The bottom of the screen is the army card row, so a tap there selects a card instead of deploying: a plan answering `y_pct` 80 put a hero at y 720 and spent all five of its attempts tapping its own cards. `prompts/attack_plan.md` tells the planner the same limits in percentages, so it stops drawing lines under the UI in the first place.

**Every one-off drop is verified against its own card, and every card gets its own attempts.** Heroes and the siege machine go down through `_drop_single`, which frames the drop, waits `DROP_SETTLE` and asks whether that card put something on the field; a card that took nothing has its spot pushed out and tries again. `_drop_singles` starts each card from wherever the last one worked rather than sharing one budget across the row — sharing it meant a first hero that needed five pushes left the other three never tapped at all. Only the heroes that actually landed reach the schedule, because a hero still in its card answers an ability tap by deploying instead, with nothing around it and no ability fired.

**Spells are verified too, and a card that would not cast is offered the run once more.** `_cast` reads the same corner: a cargo that never leaves the card is the quiet half of the same bug, since nothing downstream notices and the report says the attack went in. Freeze can be placed inside the red line — measured, a rage dropped on the town hall landed while a troop aimed at the same spot did not — so a spell that fails is a swallowed tap rather than a refused position.

**Authorization is prompt-level only.** The automation-tab checkboxes are interpolated into the prompt as 自主升級／刷牆／自主進攻 flags, and the prompt forbids gems, cash, deletion and account operations. Nothing below the prompt enforces this. Treat any new capability that spends resources as needing its own guard in code.

**Task durability.** Every agent command becomes a row in `tasks`. A task left `PENDING` is picked up again by `resume_pending_tasks` shortly after startup and after each completion, and `automation_cycle` refuses to queue new work while one is running.

**Stopping is a flag, not a stopped timer.** `MainWindow.automation_active` is a plain bool rather than `automation_timer.isActive()` because the worker threads read it too. Stopping used to leave the timer quiet and nothing else, so the attack in flight ran to the end, the agent loop ran to its step limit, and — the one users actually noticed — the task in flight finished and `resume_pending_tasks` started the next `PENDING` one. Every entry point now answers to the flag: `automation_cycle`, `_queue_next_cycle`, `resume_pending_tasks`, `AttackRunner.should_stop` and the agent loop's own step check. Two consequences worth keeping in mind. Resuming is gated on it too, so a `PENDING` task is picked up by `start_automation` rather than at startup — nothing at all runs until the button is pressed, and the ordering there matters, because a `PENDING` row makes `automation_cycle` stand down and only `resume_pending_tasks` clears it. And a command typed into the AI tab passes `automated=False`, because that one is the user's own and the stop button has no business killing it. `AttackRunner` checks only between opponents: a battle already committed is played out, since abandoning one mid-deploy leaves the army on the field and the game on a screen the next run cannot get home from.

**Coordinates are hard-coded to 1600x900.** Gemini returns percentages, and `_apply_agent_action` converts them with `x_pct * 16, y_pct * 9`. Any other instance resolution taps the wrong place. Related known quirk: ADB `wm size` reports 900x1600 while the screenshot arrives as 1600x900.

**`MuMuAdapter`** uses `mumu-cli.exe` (JSON output) for discovery and lifecycle only; every capture and input goes through `adb.py`. Two rules were paid for in bugs, do not undo them:

- `_clean_environment` strips `QT_PLUGIN_PATH` and friends from every subprocess, because the PyInstaller bundle's Qt plugin paths break mumu-cli, which is itself a Qt application.
- `ensure_coc` escalates launch → poll → restart instance, because MuMu reports Android ready before a `monkey` launch will reliably stick.

**`adb.py` owns ADB.** `AdbController` wraps `adbutils`, one instance per serial, and `MuMuAdapter.controller()` caches them — that is how several emulators coexist, since each MuMu instance publishes its own port (`AdbEndpoint`, port 0 meaning not listening yet). `use_adb_executable` points `ADBUTILS_ADB_PATH` at MuMu's own `nx_main\adb.exe` so the adb server matches the emulator. Do not shell out to `adb.exe` from anywhere else.

`AdbController.shell` takes a list or a string, and the difference matters: adbutils escapes every argument of a list, so shell syntax has to go as a string. `tap_many` is the one caller that needs it, and both of its rules were paid for by a battle that deployed nothing while reporting success — a pre-joined list arrives as one unknown command name, and chained `input` calls land about 10 ms apart, well inside a display frame, so the game keeps only the first. The `sleep` between the taps is load-bearing, not politeness.

**Every capture and every input names a display.** MuMu runs several Android displays and opens the game on one of its own, leaving display 0 on the emulator's launcher. Unqualified, `screencap -p` prefixes the PNG with a multi-display warning and the decode fails, while `input tap` silently lands on the launcher. `AdbController.display_for(package)` finds the right one and returns a `DisplayTarget`; `screencap -d` takes its physical id and `input -d` its logical id, because MuMu numbers the two schemes apart. Do not drop the `-d` flags.

**`GeminiClient`** is the only place the app talks to Gemini, through the `google-genai` SDK's Interactions API. Every request body is a `GeminiRequest`, never a hand-built dict. `generate` returns the whole text; `stream` sets `stream=True` and yields the `step.delta` text events, which is what the chat and the screen analysis use; `generate_structured(prompt, SomeModel, png)` sets `response_format` from the model's JSON schema and returns the validated instance, so no code strips ```` ```json ```` fences by hand. Structured output cannot stream, so the agent loop stays on `generate_structured`. `list_text_models` feeds the Model picker in Settings and only appears after 測試連線 succeeds. The default model is `DEFAULT_GEMINI_MODEL` in `constants.py`.

**Storage** lives in `~/.ai_coc\`: `controller.sqlite3`, `frames/`, `account_json/` and the DPAPI-protected `gemini.key.dpapi`. The schema is created idempotently in `Database._initialize` with no migration tooling, so a changed table means bumping `SCHEMA_VERSION` and handling existing databases yourself. The API key never goes into `QSettings`, only into the DPAPI file.

**Village parsing is deliberately tolerant.** Unknown sections and fields are preserved verbatim, unknown `data_id`s are queued into `unknown_entities` instead of failing the import. Game updates add IDs; keep it tolerant.

## Project rules

- **Every structured value is a Pydantic `BaseModel`, no exceptions.** New shapes go in `models.py`: emulator and CLI payloads, database rows, parsed files, AI replies, requests, settings and the chat transcript. The adapters are models too (`Database`, `SecretStore`, `AdbController`, `MuMuAdapter`, `GeminiClient`), so they take keyword arguments and put their non-field state in `PrivateAttr`. Only Qt subclasses and the ctypes `DATA_BLOB` stay plain classes, because their base class rules it out. Do not introduce a `dataclass`, a `TypedDict`, or a bare `dict[str, Any]` that travels between functions, and do not read a value out with `.get("key")` when a model could have declared the field — historical key names belong in `AliasChoices`, not in an `or` chain. Parse at the boundary with `model_validate` / `model_validate_json`, and write JSON out with `model_dump_json()` / `model_dump()` rather than `json.dumps` over a hand-built dict; a bare list on its way into a prompt gets a `RootModel` (`UiElementList`, `AccountRowList`). Ask Gemini for structure through `GeminiClient.generate_structured` and a model, never by parsing the text yourself. Models mirroring an external format that gains fields between releases carry `model_config = TOLERANT` so unknown keys survive.
- **A model field's type must be importable at runtime.** `[tool.ruff.lint.flake8-type-checking] runtime-evaluated-base-classes` keeps `TC003` from moving those imports into `if TYPE_CHECKING`, which would leave the model unbuildable. If a new model base class appears, add it there.
- **Never invent master data.** `entity_levels` (costs, times, requirements) stays empty until a value is source-backed, and the UI shows `—` rather than a guess. This is a stated product decision, not an oversight.
- **`docs/` is generated and gitignored**, rebuilt from the three READMEs and the source by `make gen-docs`. Edit the READMEs and the docstrings, never the generated output.
- **UI strings, prompts and user-facing messages are Traditional Chinese**; code, comments, commit messages and anything published to GitHub are English.
- **Deliberate deviations from the repo template**, documented in `pyproject.toml` comments: coverage gate is `--cov-fail-under=12` because almost everything is the untested PyQt shell; `[tool.ty.environment] python-platform = "win32"` is required or `winreg`/`ctypes.windll` fail to resolve on Linux CI runners; ty excludes `cli.py`, `ui/main_window.py` and `ui/workers.py` because PyQt5 ships inaccurate stubs; `allowed-confusables` carries `／` and `？` for the Chinese UI strings; the `build_release.yml` matrix is Windows-only because nothing here runs elsewhere.
- **The version is never written down.** `constants.py` reads it from the installed package metadata, and CI derives that from the git tag through `dunamai`. The `0.1.0` in `pyproject.toml` is a placeholder CI overwrites; do not hand-edit a version anywhere else, and note that `version_info.txt` is generated from that same value rather than maintained.
- **The PyInstaller step needs `--copy-metadata`** for the version lookup and `--add-data` for `prompts/`, both in `build_release.yml`. Dropping the second one leaves a build that raises on the first prompt it tries to load, which is every AI call in the app.
- CodeQL and dependency-review jobs are gated on `github.event.repository.visibility == 'public'` because this private repo has no GitHub Advanced Security.
