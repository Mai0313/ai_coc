# 收證據

事後判斷一場戰鬥發生什麼事, 只有三種東西可以用: 報告的 JSON, log, 畫面. 三種各自能回答的問題不同.

## 三種畫面

**迴圈自己讀的那些** (`--record`). 檔名是迴圈當下在問的問題, 像 `0006_scout`, `0010_pass`, `0018_dropped`. 標籤是 `AttackRunner._frame` 的呼叫端給的, 所以要知道現在有哪些標籤就去 grep `self._frame(`. 這批畫面的價值在於它們是**判讀器真的看過的那一張**, 所以判讀錯的時候證據就在這裡.

**成對的那些.** `before-drop` 跟 `dropped` 是一對, 一次出兵到底有沒有成功是靠比較這兩張的卡片角落決定的, 不是靠 log 那行字. 查「英雄到底有沒有下去」就看這一對, 不要看戰場.

**心跳那些** (`--shot-every`). 檔名是 `tick_00012.3s.png`, 帶著跑到第幾秒, 整數位補到五位所以按檔名排就是按時間排. 迴圈只在它有問題的地方截圖, 兩次之間戰況整個崩掉的話什麼都不會留下, 這批就是補那個洞的. 五秒一張是合理的密度: 一場三分鐘會有三十幾張, 夠看出兵怎麼走的, 又不會太大.

兩種都要開. 一種說判讀器看到什麼, 另一種說戰場實際發生什麼.

## 把一張畫面丟給所有判讀器

```bash
uv run ai_coc read <png>
```

回來的是 `FrameReading`, 每個 parser 對這張圖的說法都在裡面: 戰利品面板, 倉庫水位, 兵力, 城牆選單, 採集器泡泡, 閒置工人, 升級按鈕, 卡片分組, 哪些卡還活著, 哪些英雄已經在場上, 以及 `counts` —— 每一張卡的 `xN` 角落讀到幾. 最後那個是查出兵節奏的第一站, 因為它現在決定一張卡被點幾下. 欄位的意思看 `models.py` 的 `FrameReading` 跟 `commands.read`.

**「這是哪個畫面」也全部在裡面**, 一輪卡住的時候先看這幾個而不是看兵: `world` (在哪個村莊, 或者 None 代表根本不是村莊), `attack_menu` 跟 `night_menu` (兩個世界的攻擊選單是兩張不同的對話框, 一個判讀器認不得另一個), `searching` (夜世界的配對還在等真人), `loot_cart` 跟 `cart_ready` (聖水推車的面板開著沒, 以及它的收集鈕是不是活的 —— 灰的那種是開著卻收不到東西, 兩個欄位才分得出來; 灰的**為什麼**看 `CartReport.held`, 那是面板上寫的車內存量), `battle_over` (結算畫面, 這才是戰鬥結束的判準而不是 `scout` 讀到 None), `dialog` (遊戲自己那張確定／取消面板, 兩顆按鈕的座標都在), `idle_dialog` 跟 `loading` (掉線與伺服器沒回應). 一輪的 `outcome` 是 `no_attack_menu` 的時候, 這幾個欄位直接說出它當時看到的是什麼.

**這是分辨「判讀錯」跟「點沒中」的唯一辦法.** 拿那張出問題的畫面丟進去: 如果 parser 讀到的東西跟你眼睛看到的一樣, 那問題在後面的動作; 如果不一樣, 問題就在 parser.

## 從活著的遊戲抓畫面

```bash
uv run ai_coc capture --count 30 --gap 1.5 --label <這次在測什麼>
```

要量一個判讀器還讀不懂的新畫面時用這個. 一次一張抓不到只存在於某個瞬間的畫面, 所以它是連拍.

**存到哪裡不能指定, 它自己進那次執行的 `frames/`**, 而 `--label` 是之後認出「這批是在測什麼」的唯一辦法, 所以要寫. **而且畫面只留七天** —— 過期的 `frames/` 會被下一次開跑的指令刪掉, 同個目錄的 `run.log` 跟 `result.json` 不動. 一個調整要跨好幾天對照的話, 把那幾張自己複製到別的地方去, 不要指望它們還在.

**不要自己去下裸的 `adb shell screencap`.** MuMu 會把遊戲開在它自己的 display 上, 不指定 display 的話截圖前面會被塞一段多 display 的警告導致解碼失敗, 而 `input tap` 會安靜地點到 launcher 上. `AdbController.display_for(package)` 才是正確的作法, 而 `ai_coc capture` 已經幫你做完了.

## 花一場戰鬥去量

```bash
uv run ai_coc probe --record          # 實測出兵邊界, 對照判讀器的說法
uv run ai_coc bounds --record         # 實測地圖邊緣, 回推村莊範圍
```

兩個都是丟掉一場戰鬥去換一組數字. 值得跑的時機: 遊戲更新之後, 村莊換了主題之後, 或者連續好幾場都在同一個地方出兵失敗而畫面看不出原因. 兩個指令的細節跟它們第一次跑出來的結果寫在 `CLAUDE.md` (`probe`) 跟 `parsers/boundary.py` 的註解 (`bounds`) 裡.

它們用 `LootThresholds()` 而不是設定檔, 因為它們要的是任何一場戰鬥, 不是一場好的.

## 讓一場戰鬥可以重播

每次執行的目錄底下都有一份 `plans.jsonl`, 不用開旗標, 一場一行, 每一行是那一輪真的用了什麼戰術, 帶著自己的輪數. `--plan` 照著一份 JSON 打而且**完全不呼叫 AI**. 這兩件湊起來是做對照實驗的前提: 沒有它們, AI 每場給不同的計畫, 你改的東西的效果會被那個變異蓋掉.

```bash
jq -c 'select(.round==2).plan' ~/.ai_coc/logs/<run>/plans.jsonl > .runs/tuned.json
```

`--plan-out` 也還在, 寫的是最後一輪, 路徑自己指定, 放 `.runs/` 底下因為 `.gitignore` 只認得那一個. 它是「我知道這一份要留」的時候用的; 事後才想查是哪一輪出問題的時候用 `plans.jsonl`, 因為它不需要事先想到.

一份計畫是完整的戰術: 一串照順序執行的 `steps`, 每一步是攻城機具、部隊 (帶著下兵線的兩端)、某個英雄下在哪、開誰的技能、狂暴或冰凍的每一瓶落點, 或者一段 `wait` —— 秒數從上一個動作做完開始算, 所以所有時序都在那串裡面, 設定檔已經沒有任何一個時鐘了. 手改一份 JSON 就等於提出一個新戰術, 不用碰任何程式碼.

## 更吵的 log

```bash
COC_LOG_LEVEL=DEBUG uv run ai_coc attack ...
```

DEBUG 會把送給 Gemini 的完整 prompt 跟它的回覆印出來. 只在懷疑規劃那一步出問題的時候開, 平常太吵.

## 讀一場戰鬥

**log 跟畫面都要看.** log 說迴圈以為自己在做什麼, 畫面說遊戲裡實際發生什麼, 而這個 skill 存在的理由就是這兩件事會不一樣. 只讀 log 找得出「哪一步報了 WARNING」, 找不出「兵下在完全沒用的地方但每一步都成功」, 而後者才是真正值得優化的那一類.

下面是一條夠用的路徑, 不是規定. 覺得直接從心跳畫面翻起比較快就翻:

1. `result.json` 裡這一輪的 `AttackReport`: 有沒有開打, 對手**擺出**多少 (`attacked` 是偵察畫面讀的可搶量, 不是帶回家的量), `outcome` 說這一輪怎麼結束的 (十四種, 清單在 `models.py` 的 `AttackOutcome`)
2. `run.log` 這一輪的那一段: 迴圈走到哪一步, 哪一步發了 WARNING
3. 那一步對應的畫面, 用檔名找
4. 那張畫面丟進 `ai_coc read`, 看 parser 到底讀到什麼
5. 心跳畫面把整場從頭看一次, 看兵往哪走, 打到什麼, 什麼時候停下來

第 5 步不要跳過. 前四步只能告訴你迴圈有沒有照自己的規則跑完, 「這個戰術對不對」只有整場的畫面回答得了.
