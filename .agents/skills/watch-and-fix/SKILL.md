# watch-and-fix

**主線是把資源打滿, 修東西是順便.** 迴圈永遠在跑, 你在它跑的空檔思考跟改東西.

先讀 `.agents/skills/farm/SKILL.md`: 開跑前的檢查, 盯的方式, 倉庫滿了怎麼花跟哪些要先問使用者, 停手的條件, 全部照那邊. 背景跑的機制在 `.agents/skills/farm/references/running.md`.

## 管到哪裡為止

盯的是**一輪的整條路**: 開起遊戲 -> 站上日世界或夜世界 -> 打完一場 -> 回到村莊 -> 開下一輪. 卡在載入, 船沒坐成, 彈窗蓋住攻擊鈕, 結算畫面認不出來, 都跟戰術一樣是這裡的題目, 而在 log 上都像「這場打得爛」.

`walls`, `collect`, `upgrade`, `hero` **不在這條路上**: 倉庫滿了會跑其中幾個 (見「資源滿了」; `walls` 要使用者開口才跑), 但它們自己壞掉不要在這一輪裡順手修, 那是另外開一次的題目.

## 誰在跑那個迴圈

你自己決定, 中途也可以換:

- **自己跑**: `run_in_background` 送出去, 前景讀 log 改東西. 隨時可以 `capture`, 代價是每一輪的通知都進你的 context.
- **交給 subagent**: 照 `CLAUDE.md` 那段派一個跑 `farm` 的 subagent (降一級模型, 降 thinking budget), 你只讀它留下的檔案. 省下盯的成本, 代價是你不在現場.

**使用者指名就照他的**: 「你親自監督執行」是第一種, 不要為了省 context 轉包出去.

**存畫面是事前決定, 看畫面是事後決定.** 問題幾乎都是事後才發現, 所以人不在現場時傾向開著 `--record`: 存了不看不花什麼, 沒存就得再賠一整場. 自己跑時可以不開, 隨時 `capture`. 貴的是看: 一晚幾百張, 所以圖拿來確認, 不拿來巡邏, 順序見「卡住的時候先問對問題」.

## 兩個村莊, 動手之前先確認在哪一個

兩張地圖之間只有一艘船, **遊戲會開在上次離開的那一個**, 而不指定世界的指令只做當下那一個, 不會自己切. 站錯村莊的症狀是「找不到」而不是「找錯」, 要好幾張截圖才發現.

```bash
uv run ai_coc world               # 回 day / night, 不動畫面也不點東西
uv run ai_coc world --go day      # 坐船切過去, 已經在那邊就什麼都不做
```

## 三份文件的分工

程式碼說現在是什麼, 常數旁邊的註解 (跟釘住它的測試) 說數字怎麼量出來的, `CLAUDE.md` 放規則跟不變式 (Attack loop 那節是必讀), 這份 skill 說怎麼判斷. 動常數之前先在 `src/` 跟 `tests/` 搜它: 多半是修某個實測 bug 才變成現在的值, 改回去就把 bug 放回來.

## 出兵沒有成本, 不要客氣

練兵不花錢也不花時間, 搜尋費微不足道: **整場拿去量測是正常支出.** 有疑問就打一場來問, 不要從一張截圖推理. **一場不是證據**: 對手的差異比你改的東西大, 下結論要 `--repeat 3` 以上. `MIN_ARMY_RATIO` 擋下的那一輪會收掉整個 series, 不是等一下再來.

## 開跑的旗標

```bash
uv run ai_coc world --go day
uv run ai_coc attack --repeat 0 --record --shot-every 5
```

**先 `world --go`**; 中途被換到另一邊就回 `other_village` 整批收工, 不會自己切回來. **`--repeat 0` 是主線的形狀**: 打到倉庫滿自己收工; 固定輪數是做對照用的.

`--record` 存迴圈自己讀的畫面, `--shot-every` 存定時的畫面. **分辨「判讀器讀錯」跟「點下去沒生效」只有畫面辦得到** (兩者在 log 上一模一樣), 所以查這類問題兩種都開. 怎麼讀在 `references/evidence.md`.

畫面, `run.log`, `result.json` 跟 `plans.jsonl` 都在這次執行的目錄底下, 路徑是開跑第一行 log, 不必自己重導向. **`plans.jsonl` 不用開旗標**: 一場一行, 是 AI 那一場的劇本 (照順序的步驟, 誰下在哪, 等幾秒). 把某一輪拉出來重播:

```bash
jq -c 'select(.round==2).plan' ~/.ai_coc/logs/<run>/plans.jsonl > .runs/tuned.json
uv run ai_coc attack --plan .runs/tuned.json
```

**你拿來下判斷的那幾張, 用檔案傳送機制發一份給使用者**, 說清楚為什麼重要. 他看不到你的工具輸出, 只給路徑等於要他自己去幾百張裡翻.

## 卡住的時候先問對問題

卡住先翻 `references/symptoms.md` (症狀對照該去看什麼), 不要直接改程式碼.

**先 plan 後畫面.** 那一輪的 `plans.jsonl` 對照 `run.log`: 對得上而結果還是爛, 問題在戰術 (prompt 或戰術檔); 對不上, 問題在迴圈, 才去畫面找哪一步歪掉.

**這個遊戲對「拒絕」幾乎不給訊號** (兵被無聲吞掉, 不同錯誤共用一條紅色橫幅), 所以出兵成不成功看**卡片自己**有沒有少 (`card_drained` / `field_units`). 截圖上沒看到兵, 不代表沒下去, 也不代表下去了.

## 調整的階梯, 從便宜爬到貴

每一層都比下一層便宜而且好回頭, 不要跳級.

1. **`~/.ai_coc/config.json`**: 戰利品門檻, 倉庫上限, 重開模擬器的間隔, 模型. 改數字重跑, 不用測試不用 PR. 它只決定打誰跟打到什麼時候, **沒有任何數字決定怎麼打**: 秒數都在 plan 的 `AttackStep` 上 (`act: wait` 從上一個動作做完算), 殘留的 `timings` 會被 `adapters/config.py` 刪掉. 所以「打得不夠好」從第二層開始
2. **戰術檔案**: `src/ai_coc/plans/flat.json` 是預設戰術 (夜世界的形狀看 `plans/night_flat.json`), `--plan` 餵一份進去**完全不呼叫 AI**, 只打它所屬的村莊, 遊戲在另一邊就回 `other_village`, 所以先 `world --go` 切過去. 寫 JSON 比改程式碼快, 而且拿掉 AI 這個變因才能對照
3. **`src/ai_coc/prompts/attack_plan.md`**: AI 每次都畫爛線或漏欄位是 prompt 的事. `AttackPlan` 除了 `deploy_from` 跟 `reason` 都必填, 是刻意的 (Gemini 會不寫有預設值的欄位), 見 model 上面的註解
4. **`src/ai_coc/ui/attack.py` 頂端的常數**: 到這層才需要量測撐腰, 來歷寫在各常數旁邊. `TAP_GAP` 住在 `adapters/adb.py`
5. **迴圈的邏輯**: 最後手段, 要跑測試, 要開 PR

## 改到程式碼的時候

- **先量再改.** 沒量測就改常數, 下一個人會以為那是量過的.
- **一次只動一件事**, 跑幾輪看差別.
- **流程照 `CLAUDE.md` 的 `## Development flow`**, 不用另外問使用者.
- **量到的新東西寫進常數旁邊的註解, 不寫進 `CLAUDE.md`**: 那裡只收規則, 不變式跟未修的已知缺陷; 真要加規則, 先把文字給使用者看過.
- 改的時候讓迴圈繼續跑. **要活的遊戲才驗得了的, 自己停掉迴圈, 驗完自己開回去**, 不用問, 規矩在 `.agents/skills/farm/references/running.md` 的「你自己要用畫面」那節. 驗證場對著的多半是打滿的村莊, 所以加 `--stop-at 0`.

## 對照要怎麼做

變因只能有一個:

- 用 `--plan` 餵同一份戰術
- 兩邊都跑 `--repeat 3` 以上
- 比**進帳的資源**跟**打完的百分比**, 不比「感覺比較順」
- 三場對三場只看得出很大的差別, 看不出百分之十

`--plan-out` 寫下實際跑的那份 (只留最後一輪, 要事先加), 好的可以重播, 爛的可以拿出來吵.

## 資源滿了

照 `farm` 的「倉庫滿了」: **預設什麼都不花**, 打到 `stop_at` 就收工通知, 除非使用者交辦時講了要花. 講了才花: 建築照他那句話做, 城牆跟英雄要指名, 兩種資源都花光不用留 (練兵不用錢). 怎麼花是 `spend-loot`, 什麼時候停是 `farm`. **「不浪費一分一秒」講的是你的時間不是他的資源**: 沒開口要花, 空檔拿去改東西.

## 任務報告

主線達成 (資源打滿) 時, 交 `farm` 的任務報告, 樣板一模一樣, 寫到 `~/.ai_coc/logs/<run>/report.md`. 沒達成就不套樣板, 照 `farm` 的規則講一段話.

報告後面接一節 `## 這批場次盯到什麼`:

- 看到什麼樣態: 整條路上哪一步最常出問題, 哪一種對手最常打壞
- 試了什麼, 結果是什麼, **包括沒用的**, 下次不用再試
- 改了什麼, 依據哪一次量測, PR 在哪
- 還沒解決的是什麼, 卡在哪

沒調到任何東西也要寫, 內容是「這批很順, 沒發現值得改的」. 那是結論, 不是空白.
