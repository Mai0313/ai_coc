# build-feature

兩件事同時進行: **探索遊戲並且把找到的東西做出來**, 以及**讓打資源的迴圈在背景一直跑**. 使用者開這個 skill 的意思包含後半段, 思考跟改碼的空檔不該讓模擬器閒著.

背景怎麼跑讀 `.agents/skills/farm/references/running.md`. 決策的部分讀 `.agents/skills/farm/SKILL.md`: 倉庫滿了轉刷牆, 牆刷不動了停手通知.

## 三份文件的分工

- **程式碼**說「現在是什麼」: 已經自動化了哪些事, 判讀器現在讀得懂哪些畫面
- **`CLAUDE.md`** 說「為什麼是這樣」: 專案的三層架構, 每條規則背後的 bug
- **這份 skill** 說「怎麼判斷」: 怎麼探索, 什麼算好題目, 做出來要放哪

開工前先讀 `src/ai_coc/cli.py` 的 `_parser()` 跟 `src/ai_coc/commands.py`, 那是「目前做得到什麼」的完整清單. 沒在那份清單上的就是可以做的.

## 探索一定要看圖

沒被自動化的東西, 按定義就是**還沒有人寫過判讀器的畫面**. 所以你不可能靠讀程式碼找到題目, 只能靠實際走進遊戲裡看. log 只說得出已經寫好的那些迴圈在做什麼, 它對還沒做的東西完全沉默.

```bash
uv run ai_coc capture .runs/explore --count 20 --gap 1.5   # 從活著的遊戲連拍
uv run ai_coc read <png>                                          # 現有 parser 對這張圖的說法
```

**不要下裸的 `adb shell screencap` 或 `adb shell input`.** MuMu 把遊戲開在它自己的 display 上, 不指定 display 的話截圖會因為前面多一段警告而解碼失敗, `input tap` 則會安靜地點到 launcher 上, 你會以為點了但什麼都沒發生. 正確的入口是 `AdbController`, 它會自己解析 display; 怎麼用在 `references/exploring.md`.

`ai_coc read` 是判斷「這個畫面現有的判讀器懂不懂」的方法. 每個欄位都是 `None` 或空的, 就代表這是一片沒開發過的地方.

**看到值得做的畫面就發一份給使用者.** 探索的產出本來就是「我看到這個, 它還沒被自動化」, 而那句話配上圖才成立. 用檔案傳送機制發出去, 不要只留路徑 —— 使用者看不到你的工具輸出, 而要不要做這個題目是他的決定.

## 什麼算好題目

**好的**:

- 重複而且每天都要做. 自動化省下來的是每天的時間, 不是一次的時間
- 成功與否可以從畫面上讀出來. 沒有訊號就沒辦法驗證, 也沒辦法在出錯的時候停下來
- 花掉的是會再生的資源 (金幣, 聖水, 黑水), 不是寶石或現金
- 失敗的代價小, 而且可以重來

**不好的**:

- 需要辨識遊戲美術才做得到. 每一級的城牆, 兵, 英雄造型都不同, 建築位置也不固定, 遊戲一改版就全壞. 這個專案的核心手法是**讀遊戲畫在上面的 UI, 不讀底下的東西**, `CLAUDE.md` 搜 `read the UI the game paints on top`. **但這條約束的是判讀器, 不是你** —— 一次性的辨認 (這棟是什麼, 那個東西在哪) 用看的就好, 那是 `upgrade-by-eye` 在做的事. 所以題目是壞的只有在它要求**每天跑幾百次**都認得出美術的時候
- 不可逆. 拆建築, 換陣型, 動帳號設定
- 會花寶石或現金. 加速所有同類項目跟城牆戒指都在按鈕列上而且圖示會被判讀成資源, 現有的程式碼是靠**結構**擋掉它們而不是靠檢查, `CLAUDE.md` 搜 `blue plate`
- 需要跟別的玩家互動而對方會受影響

找到候選之後跟使用者確認再做. 探索是便宜的, 做一個他不要的功能不是.

## 做出來要放哪

`CLAUDE.md` 的 Architecture 跟 Project rules 兩節是完整的規則, 這裡只點出做新功能一定會撞到的幾條:

- **headless 先行.** 新功能要能被 `commands.py` 叫到, 因為只能透過 widget 觸發的功能沒辦法在開發過程中對著活的遊戲跑. 視窗是最後才接的, 有時候根本不用接
- **三層目錄**: `ui/` 是編排, `adapters/` 是外面的世界, `parsers/` 是純函式. 判讀畫面的邏輯一定進 `parsers/`, 因為那一層可以用真實截圖當 fixture 寫測試
- **每個結構化的值都是 Pydantic model**, 而且統一放 `models.py`. 不要 dataclass, 不要 TypedDict, 不要在函式之間傳裸 dict
- **座標寫死 1600x900**, 收到別的尺寸要 raise 而不是硬讀. 現有的 parser 都是這樣寫的, 照抄
- **每次截圖跟每次輸入都要指定 display**
- **會花資源的能力要有程式層的 guard**. 授權目前只存在於 prompt 裡, prompt 底下沒有任何東西在擋

## 做的流程

1. **先在活著的遊戲上量.** 抓一批畫面, 找出那個畫面上哪些像素是穩定的, 哪些會隨等級或主題變動. 量到的數字寫成常數並且在旁邊註明是怎麼量的, 這個 repo 的每個常數都是這樣來的
2. **寫 parser 加測試.** 用真實截圖當 fixture. 一個 parser 沒有測試就等於下次改版沒人會發現它壞了
3. **接上 runner**, 放在 `ui/` 底下, 保持 Qt-free
4. **接上 `commands.py` 跟 `cli.py` 的 sub-command**, 這樣它才跑得起來
5. **對著活的遊戲驗證**, 而且要驗證失敗的路徑, 不是只驗證順利的那次
6. `uv run pytest` 跟 `make fmt`
7. **照 `CLAUDE.md` 的開發流程走完**: 讀 `gh-dev-flow`, 開 branch, 開 draft PR, 對 branch 跑 `code-review` 把站得住腳的意見修掉, CI 綠了就 merge. 這段不需要另外問使用者

**想寫進 `CLAUDE.md` 的段落先給使用者看過.** 那個檔案每次 session 都會被讀進去, 寫錯一行會一直付代價.

## 打資源要一直在背景跑

改碼跟等測試的時間拿去打資源. 這是使用者明講的要求, 不是加分項.

刷牆 (`walls`) 除了消耗資源之外還有第二個用途: 它是這個專案裡最新也最少被跑過的迴圈之一, 每跑一次都在測試它. 資源夠的時候順手跑, 跑出來的問題本身就是題目.

注意**絕對不能同時跑兩個指令**, 它們會搶同一個模擬器畫面. 要探索遊戲就先確認背景那輪停了, 或者等它跑完.

## 任務報告

功能做完並且 merge 之後才交報告. 只探索到一半, 或者做出來還沒驗證過, 就講一段話說現在到哪, 不要包裝成完成品.

```markdown
# 任務報告

**做了什麼**: <一句話>
**PR**: <連結>

## 探索到什麼
<走過哪些畫面, 現有判讀器讀不讀得懂, 附上關鍵截圖的路徑>

## 這次做的
<新增了什麼指令 / parser / runner, 量到哪些數字, 那些數字是怎麼量的>

## 怎麼驗證的
<對著活的遊戲跑了什麼, 順利的路徑跟失敗的路徑各驗了什麼>

## 還可以做的
<探索途中看到但這次沒做的題目, 各自的代價跟風險>

## 背景那輪打資源
<跑了幾輪, 進帳多少, 現在停在哪. 資源打滿的話直接套 farm 的任務報告那一節>
```

截圖不要貼進報告裡, 給路徑就好. 迴圈自己留的那些在 `~/.ai_coc/logs/` 底下, 而你自己 `capture` 出來的要放 `.runs/` —— `.gitignore` 只認得那一個路徑, 丟在 repo 根目錄的東西會出現在 `git status` 裡.
