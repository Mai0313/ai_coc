# Reading and driving the screen

## Cross-cutting rules

**Everything is 1600x900 at the game's far zoom.** Every coordinate was measured there, on a free scenery. A scenery bought from the shop zooms out about twice as far over a much larger map, where the game draws no markers and the corner clamp no longer frames the village, so `park_camera` brings it back to the free scale with the village dragged to the middle (below). Gemini answers percentages, converted with `x_pct * 16, y_pct * 9`. MuMu's `wm size` reports 900x1600 (LDPlayer's 1600x900) while the screenshot arrives as 1600x900 on both.

**The parsers read the UI the game paints on top, never the thing underneath.** Walls, buildings, heroes and troops are repainted at every level and by theme updates; buttons, icons, plates, numbers and borders are not. A wall is recognised by being upgradeable with gold *or* elixir, a resource by its icon. The rule binds the parsers, not a vision model making a one-off identification. **Finding a fixed piece of the game's furniture is a parser's job, not a new Gemini question**: a Gemini boat-finder was built and the user turned it down on 2026-10-04 as mechanical work (「這些屬於機械化操作」), and the marker the game paints over the boat replaced it. **Being accurate is not enough to add one either**: Gemini named every hero card right on 15 answers on 2026-10-08, but each reply took 15 to 224 s, and the user's direction is to depend on it less while it is that slow (「我覺得應該要少依賴 Gemini, 尤其是我們知道延遲很久的情況下」). A colour painted on top can still change, so a colour that stops matching is answered with a signal that does not depend on it, or one learned from the same frame (`_dark_bubbles`), never with another colour range.

**One feature is rarely enough.** Many detectors pair two readings because either alone matched something else in recorded frames (`night_attack_menu`, `settings_open`, `export_row`, `loot_cart_open`, and `uncovered`'s battle test). A threshold is drawn from what was measured on both sides of it, over recorded frames and the committed fixtures where they exist; its comment says how wide the margin is and what it was measured on.

**Spending is guarded in code, by structure where it can be.** `confirm --pay` presses only the price button `panel_wall_menu` located off the elixir drop and the gold coin a pitch left of it, so no other button on a wall's menu is reachable from it. Where a button cannot be kept out of reach, it is refused before any caller sees a price: two buttons in the building row carry icons that read as a resource — 加速所有同類項目 (a magic item) and the wall ring — and both sit on a **blue plate**, which `tap` refuses (`menu_spends_gems`) and `panel_wall_menu` refuses as a price button. The build panel's flow is driven by the agent through `tap` and `swipe`, and the one press that spends is `confirm`'s: it presses the sheet's green 確認 only when `sheet_offer` reads a gold, elixir or dark icon on it (a running row opens the same button as 立即完成 for gems), a price in yellow or white rather than red, and exactly the price the agent passes; `tap` refuses that button outright, along with a dialog's 確定, the HUD's + buttons and shop (shifted left while the panel is open), the panel's running rows, any big green button (立即完成, and the gem offer the game raises when 確認 meets every builder busy) anywhere on screen, or left of the panel while it is open, anything but the X on the prompt to hire an event's goblin builder (`goblin_prompt`, whose lime the green tests miss), a menu row that carries 立即完成 (its 取消 throws the upgrade away), and anything in a battle. With `--pay`, `confirm` starts a step earlier, on the wall menu a 城牆 row opens beside the panel (`panel_wall_menu`: the panel open, and a gold and an elixir price button a pitch apart priced alike): it presses that resource's button only when it asks exactly the price passed and in white, with no sheet or dialog already standing, and then pays what that raised — a single wall's sheet, held to the same price and resource, or a batch's 升級城牆 dialog, whose 確定 it presses because it raised that dialog itself (`_raised`). With `--goblin`, `confirm` pays gems, on one screen only: the prompt to hire an event's goblin builder (`goblin_offer`, read off its X, its pale panel and its button where that prompt draws them), whose one button it presses when it asks exactly the gems passed; how many the agent may pass is the user's cap, kept in the `upgrades` skill. Any new capability that spends resources needs its own guard of one of these kinds; a prompt or a skill line is not one.

**Which village is up** (`current_world`, `parsers/world.py`). The two villages are separate maps joined by a boat, and the game reopens on whichever it was closed on. Since the 2026-10 overhaul the bars in the top right end, on the home village, in a 護盾 bar the builder base cannot have, and the gems and shield bars each carry a green `+`; so the reading is **which heights carry a + button** (a green plate and a white cross, both). The shield's alone is enough; the home gems height only with the builder base's own absent. The build panel shifts the column and a storage tooltip can hang over it, and both read None, like battles, dialogs and loading screens. `read_stock` answers on both villages (the builder base's gems bar reads as `dark`, the gem count) and on a battle, which draws the same bars, so it can say a village is up but never which one.

**`back` is only pressed on a frame that is not a clear village** (`GameRunner._home`, `uncovered`). On a clear village `back` raises 確定退出遊戲嗎, whose 確定 is the same green in the same pixels as the one that pays for an upgrade, so `game_dialog` reports both buttons and picks neither; only the caller knows which question it asked. **`uncovered` also never presses at a battle**, where `back` aims at 放棄, because its callers hand it whatever is on screen, a game left mid-battle by a killed run included; `_home` presses `back` at one but never takes its storage bars for the village (`in_battle`), since a battle draws them in the same place. `uncovered` takes a frame for a battle only when a card row (`card_groups`) *and* the plate in the corner (`in_battle`, `ABANDON_BOX`) both read; `in_battle` alone reads only the plate. `_dump_leftovers` and `_cast` ask `in_battle` as well, so a tactic that outlived its battle stops tapping. Two windows read False over a live battle: the builder base draws no plate during its opening countdown, and a popup dims the plate away. The countdown was tested live: `back` there raises 確認退出遊戲 rather than surrendering, and `uncovered` never answers a dialog.

**Getting back to the village** (`GameRunner._home`, `ui/runner.py`). Four things block it and each wants its own answer: a game still loading is waited on, a panel gets `back`, a dialog gets 取消, and a dropped session gets its own 重新登入遊戲 / 再試一次 button, with a restart only when the tap did not clear it (`relogin`: a restarted game can come back under LDPlayer's 儲值 promotion, the user's call of 2026-10-09; 連線已中斷 is the same sheet, read by `idle_disconnected`), unless another device logged in (`session_taken`), which is left alone. `_seen_village` decides whether an unreadable frame gets the launch patience. A dialog has to be answered, since its dimming is what stops the storage bars reading.

**The camera is put back before the storages are read** (`GameRunner._settle_zoom`, `_settled`). A zoomed-in camera can put bright ground behind a translucent storage bar and fuse its digits, so `read_stock` fails and `_home` circles `back` → 確定退出遊戲嗎 → 取消 until it gives up. It runs once per run and is cleared on a restart. Either `current_world` or `read_stock` counts as a village for the pinch, but only `current_world` says *which* village the park should push toward, so a frame only the storages recognised is pinched and not parked, with a warning, which also leaves a bought scenery at its own far zoom. Known and open: such a frame hands the builder base's storages back to `_home`'s caller as the home village's. No recorded frame has taken that branch (4 304 swept), so it is a missing guard nobody has watched fail.

**A server outage is waited out, not tapped at** (`loading_screen`, `AttackRunner._wait_out_loading`). 正在載入 with the bar stuck at 1% has lasted 25 to 40 minutes, and neither kind of restart shortened it. `_open_attack_menu` polls it every `SERVER_POLL` up to `SERVER_POLLS` (45 minutes), checks the state file inside the wait, and waits once per load: a load that drops back onto it ends the round `server_flapping`. `uncovered` and `_home` never press `back` at it.

**Camera and zoom** (`park_camera`, `view_shift`, `ai_coc view`).

- A pinch sets the scale and does not move the camera. `park_camera` pinches out first and then swipes into the corner until `view_shift` says the picture stopped moving.
- **The corner is where the park starts, not where it ends** (the user's call of 2026-10-07). From the clamp, one slow drag per village (`CENTRE_DRAGS`) puts the village in the middle of the screen, so the whole of it is on screen, the wall block and collector row included. Only the crossing asks to stay in the corner (`corner=True`), and the loot cart is tapped on the centred view (`CART_SPOTS`, the corner spots carried by the drag). A free scenery's corner hid its collector row as well (1 marker against 15 once dragged), so it gets its own drag and no pinch. The drags were measured on one bought scenery, the jungle and the builder base. Parking on the view the game picks itself (after a search-and-leave, or a restart) was declined: 「算了 這點先不改了 我怕未來依賴系統默認 哪一天遊戲機制改了之類的」.
- **The attack does not park** (`_settle_game(park=False)`): it pinches out for the storage bars and taps no map coordinate before its battle, which measures its own camera; the builder base's cart visit parks for itself.
- Zoomed in, the camera runs off the village into the map's border, so `view --zoom in` never parks. `view` parks only on a village, because a swipe with a card selected deploys troops, while the pinch is safe on any screen; and not on one with a building or a wall left selected (`selection_row`, outcome `selected`), whose button row a drag would start on instead of moving the camera.
- The build panel 建造 opens (`build_panel_open`) shifts the corner column, so it reads as no village and no caller parks under it. `back` does not shut it, so `_home` and `uncovered` press its own X (`PANEL_CLOSE`).
- **A bought scenery is told apart by the boat's marker, not by its look.** A free scenery's home park has the marker on screen; a bought one's far zoom draws none, so `park_camera` drags the village to the middle and pinches in once about it (`CENTRED_PINCH`, `BOUGHT_PINCH`'s ratio), which brings back the free scale without moving the village: pinched in from the corner, the same gesture left it up to 100 px from one park to the next. The centred park takes a missing marker for a bought scenery without pinching to confirm it, because the confirmation made the camera settle three times over a park that had landed the first (the user's call of 2026-10-08); a free scenery whose marker something covered for that frame is pinched to twice its scale until its next park. The corner park, which the crossing's measured spots need, still confirms: it pinches with `BOUGHT_PINCH` and keeps it only if the marker then reads: on a free scenery whose marker something covered, the pinch carries the boat off the left edge, and the park goes back to the far zoom. `BOUGHT_PINCH` was measured on one bought scenery.

**Pinch mechanics** (`AdbController.pinch`, `touch_device_for`, `gesture_script`). `input` has no two-finger gesture, so a pinch is multi-touch events written to one input device node. `touch_device_for` resolves that node from `dumpsys input` (the display's physical id → the InputReader device → its EventHub path), keeping only a node `getevent` lists as multi-touch, because LDPlayer binds a `VirtualMouse` to the display ahead of its touchscreen; sending to every node lands two fingers on MuMu's launcher displays and switches away from the game. Whether a node's axes are the screen's swapped is read off its own ranges (`touch_devices`): MuMu's are (a point goes down as (y, x)), LDPlayer's are not. `BTN_TOUCH` is required, and so is `ABS_MT_PRESSURE` on a node whose pressure axis has a range (LDPlayer's is 0 to 2; MuMu's lists 0 to 0 and must be sent none): without it Android reads the finger as a hover and the game ignores it, which went unnoticed only while a real mouse click had left a pressure behind. The events are packed behind one redirect because opening the node cost 31 of every 33 ms a `sendevent` took, and written one `SYN_REPORT` at a time inside it, which is what makes the game see a drag; `PINCH_GAP` only paces those writes to a hand's speed.

**Crossing** (`ui/world.py`, `ai_coc world --go`). Park the camera, tap the marker the game floats over the home village's boat (`boat_marker`), and let `current_world` say whether it worked. The boat itself is never recognised: events redress it and **the home village's scenery decides where it is moored**, so the measured spots hold only on the scenery they were measured on. With no marker it taps the measured spots.
