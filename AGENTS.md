# AGENTS.md

This file provides guidance to every coding agent working in this repository.

## What this is

A Windows-only command-line app that drives Clash of Clans inside MuMu Player 12 or LDPlayer 14 (雷電). **The parsers read the screen, and Gemini answers two narrow questions**: how to attack a home village opponent that already passed the loot thresholds (`_plan`, once per battle), and how to attack a builder base (`_night_plan`, once per stage). Everything else — prices, card counts, storage bars, which village is up, whether a drop landed — is pixels.

**Where the reasoning lives.** The code says what is. The comments and docstrings in `src/`, and the tests that pin each threshold, say why a value is what it is and which measurement set it. This file holds the rules that no single comment can, and the files under `.agents/rules/` the map of the code and the rules for it. Before changing a constant, read its comment and grep `src/` and `tests/` for its name: most were set by a battle that went wrong, and changing one back reopens that bug. A new measurement goes into the comment beside the constant it sets, not here.

**Everything an agent has to follow lives in the repo**: this file, the rules under `.agents/rules/`, the skills under `.agents/skills/`, and the code. Codex, Antigravity and every other agent read the repo, not one runtime's private memory or a rules directory outside the repo, so a rule kept only there is a rule they break. Write it here, into the file under `.agents/rules/` that covers the code it is about, or into the skill that owns it; private notes keep one machine's history and nothing more.

## Driving the game

The skills under `.agents/skills/` own the judgement of driving the game, and they are the only copy of those rules; a rule written here as well would drift. They are `takeover`, `upgrades`, `watch-and-fix`, `share-emulator`, `repair-emulator`, `game-update` and `find-on-map`, and each one's description says when it applies. By default farming ends at `stock_full` with a report, and the loot is spent only when the user asked for that.

`share-emulator` owns what every command on the one emulator shares: the lock, borrowing a loop and giving it back, how a stop works and when it is safe, which commands run in the background and how a wait ends. `.agents/skills/takeover/references/runner.md` is what the farm subagent follows.

**A question about what the village has (an item's level, its max or cap, what its next level costs or takes, what is upgrading) is answered from `ai_coc search` and the newest saved export (`ai_coc status --last` for what is upgrading, `ai_coc export --last` for the rest) before `status` or the build panel**: neither touches the emulator, and `upgrades` says what each prints and when the answer has to be read fresh.

**Nothing drives the game while the user is playing on the emulator or has said not to**, no farm subagent and no takeover either, until he says so.

**A stop the user orders is run by whoever hears it.** The session the user said it to runs `ai_coc stop` itself, and a subagent that hears one does the same; passing the order on to the farm subagent is not enough, because a subagent blocked inside a command reads no message until that command returns. The user prefers the main session to run it. One stop ends both the command on the emulator and the upgrade watch; only a standing loan waits for a second stop once the borrowing command has ended, since a stop that finds a command running stops only that command. `share-emulator`'s 停 says how a stop works, and `runner.md`'s 被叫停, 被借走 what the stopped subagent does next.

**The loop runs the main checkout; the change is made somewhere else.** The subagent runs from the main checkout, which stays on the default branch, with every command as `uv run --no-sync ai_coc …`, and the work happens in a separate worktree with its own `uv sync`. A branch switch in the loop's checkout changes the code its next command runs, and on Windows a sync there fails with os error 32 while the loop's `ai_coc.exe` is running, or a sleeping `ai_coc watch`'s: a plain `uv run` does sync after `pyproject.toml` or `uv.lock` moved, which a merge pulling in a dependabot bump does, and that takes `ai_coc stop` down with it. So the loop does not pick up a merged fix by itself; `share-emulator` says who pulls it in. Anything run from the main checkout, `stop` and `giveback` included, is `uv run --no-sync` for the same reason. A branch that changes `AppConfig` runs no `ai_coc` command that reads the settings file (every one that touches the emulator does) while the loop is up: loading it rewrites the shared `~/.ai_coc/config.json` to the branch's shape (`adapters/config.py`), and the loop in the main checkout reads the same file.

**What runs on the emulator after a change lands is the agent's call.** Once a feature merges or a fix or repair is done, the session decides by itself whether the farm subagent, the takeover or the upgrade watch has to pull the change in, restart or be re-armed, and does it without asking: the user handed those decisions to the agent. The limits above still bind it: nothing drives the game while the user is playing or has said not to, until he hands it back.

**A code change during a takeover may go to a session of its own.** When a session running `takeover` needs to change the code, it decides by itself whether to make the change itself or hand it to a new session it starts. A session it starts stays under its control from start to finish, works in a worktree of its own and follows `gh-dev-flow`.

**Taking the game for a live test.** There is one emulator, so a test and the loop cannot both drive it. Take it whenever a test needs it and give it back afterwards, without asking either time, the way `share-emulator`'s 借, 用完還 says. Two rules it does not hold:

- A test spends nothing the user has not asked to spend. Testing `confirm` buys what it confirms, so a wall still needs him to have named walls (「順便測試升級牆壁」 is that); otherwise list walls among the options in the reply rather than buying one.
- **The user sometimes plays on the same emulator.** Park it with `ai_coc view --zoom out` before the first live test of a piece of work. A test that finds no village (a battle on screen, `not_a_village`), or a game that changes between two of your taps with nothing of yours to explain it, may be the user mid-game: take a frame with `ai_coc capture`, send it, and ask before trying again.

**Look before driving.** Before the first command of any piece of work, read `~/.ai_coc/state.json`. The file is a lock: a command that drives the emulator stands a live holder down first (see `.agents/rules/runtime.md`'s "Stopping and the state file"), so `running` or `stopping` there is somebody's run your command would end, or borrow from when it yields. A record whose process is gone is residue the claim takes over by itself. The file has three sections: `emulator`, the lock; `watch`, the `ai_coc watch` process sleeping on the upgrade timers, where a new watch takes over a live one, naming itself as `stop_by`; and `notes`, the user's standing instructions for each village, kept with `ai_coc note`. `read`, `stop`, `giveback`, `watch`, `note`, `growth`, `turnaround`, `search`, `farmed`, `tended`, `gamedata`, `export --last`, `status --last`, `capture` and a plain `world` never claim and are safe beside a loop. Never test a pid with `os.kill(pid, 0)`: on Windows signal 0 is `CTRL_C_EVENT`, so it sends a Ctrl+C to that console group, can kill the run it asked about, and still reads as alive.

**Say who is driving.** Every `ai_coc` command an agent runs carries `--agent` (its own name: `claude-code`, `antigravity`, `codex`), `--session` (its own session id) and `--mission` (one line on what the run is for). A command that claims the emulator writes them into `state.json`'s `caller`, which therefore always names whoever started the run holding it; every command, `stop` and `read` included, writes them into its own `run.log` on the line after the one naming its directory, and `stop` records its caller on the file as `stop_by`, which the `idle` record the stopped run ends with keeps.

**The user playing on their phone logs the emulator out**, and the file's `emulator` section does not show it. A run that cannot reach a village while somebody might be playing is a reason to stop and say so, not to retry. The game says so on the dropped-session sheet (另一部裝置正在連接到這座村莊), and `session_taken` tells it from the dropped sessions a restart answers: the attack loop ends its series `session_taken`, mid-battle included, and `_home` and `_settle_game` stand down instead of restarting. Starting any command still logs the emulator back in (`ensure_coc`'s launch, measured 2026-10-09), so after a `session_taken` nothing that touches the emulator runs until the user says so. A borrower whose command stood down on it runs `ai_coc stop` rather than `giveback`: a giveback, or the loan lapsing, lets the lender's queued command through. The one exception to both is `takeover`, which logs back in by itself five minutes later, borrowing or not, as that skill says.

**Check what subagents leave behind yourself; their word is not evidence.** Before calling a task finished: `state.json`'s `emulator` back to `idle`, no `ai_coc` process, no shell left polling; a watch left sleeping on purpose is one to name. Say out loud what stays deliberately; kill and name the rest. A wait with no upper bound cannot end on its own; `share-emulator` owns what a wait looks like.

## Development flow

Read `gh-dev-flow` before starting. In this repo the path always ends the same way: open the PR as a draft, run `code-review` over the branch and fix what holds up, then merge once CI is green. Merging on green needs no further approval.

**Every merge, and anything the user needs to know about the project, goes on top of one shared page.** Any session working on this repo, running `takeover` or not, adds an entry at the top of 「ai_coc 更新紀錄」, https://claude.ai/artifact/Fu6nrsHkscczMBKwRG5824 (private to the user), whenever it merges a change or learns something about the project it judges he needs to know, such as a decision left open or a finding that changes how something behaves. Newest first, one dated entry per takeover or stretch of work, which the session adds to as more merges and moves back to the top. Each merged PR gets what is new or different for him, when it comes into play (which situation, or which of his requests), how the agents now work differently (what they read, run or decide that they did not before: answering 「X 要多少」 with `search` instead of opening the build panel, say), how he can use it himself where he can, and its link; a bare result such as 「新增查詢」 tells him none of that. It also says whether the PR changed the project skills or this file and how, from his side: which skill now tells a new session to do what (`upgrades` now starts a price question from `search`, say), so he knows a fresh session will know about the change; or it says plainly that neither changed. Then come what is left open and any such finding. Write it from his side, with no module, function or file names or other internals of the code (a command he can run himself is not one), and let the length follow what changed: a tiny fix stays one line, and he asks when he wants more. Update that page; never start a new one. A long session gets its conversation compacted, so it cannot count on remembering later what it changed; the page is the record the user reads. The entry comes on top of what the reply or a skill's report carries, not instead of it. A runtime that cannot update the page puts the same entry in its report to the user, and a session that can adds it once he passes it on.

This file, the rules under `.agents/rules/` and the project skills are the agent's to edit: the user judges the project from the player's side and leaves its code and documents to the agent. Update them in the same PR as the change that outdates them without showing the text first, and say in the reply what changed for the user.

**That includes starting a project skill nobody asked for.** When a session works out how to do something in the game that a later session would have to work out again, a way through a screen, a check that settles what is on it, a repair, write it up as a new skill under `.agents/skills/` and take it through the flow above, with no approval; add its name to the list under Driving the game. Only global skills need the user's agreement.

**A skill says what the runtime has to do, not which runtime's tool does it** (#469). Codex and Antigravity run the same skills, so a step written as one CLI's tool or parameter is a step they cannot take.

**When a skill has to work around what a command prints, change the command.** A skill, or an agent following one, that has to reshape, join, translate or recompute a command's output before it can use it is a defect in the command, not a reason to add steps to the skill: give the command the field, the flag or the text output in the shape the skill reads (`search`, `growth` and `turnaround` already print text while `result.json` keeps the JSON), and drop the skill's workaround in the same PR. What a command hands over is facts; deciding what to do with them (continue an upgrade, switch to another, ask the user, what counts as done for him) stays with the agent, so no command prints a verdict for a skill to copy (the user: 「判斷應該是你, 不是 CLI. CLI 那邊只提供盡可能乾淨的資訊, 方便你來做判斷而已」). `status`'s 好了以後 column did, and its 做完收回 hid that a goblin's item still had a level to go. Keep such a change cut cleanly: each command keeps one job, the text shaped for a skill is a presentation layer built from the report rather than mixed into it, no catch-all command or flag bundles unrelated reports, and each skill reads the command that owns its data instead of one command growing to serve every skill. The structured form stays for programs: every run writes `result.json` whatever the terminal shows, and the project had a desktop window until #506 and may have one again. Such a change is the agent's call like any other change to the code.

**Before changing, planning or reviewing anything under `src/`, `tests/`, the workflows, the build, `pyproject.toml`, `.pre-commit-config.yaml` or the READMEs, read the files under `.agents/rules/` whose `paths` cover it.** Together they hold the map of the code, the invariants that span files, the known defects, the development commands and the rules for code. Claude Code (through `.claude/rules`) and Antigravity load each one by itself once a file under its `paths` is opened; nothing loads them at startup, so a plan or a review made before any such file is open, and every other agent, reads them by hand. A rule goes into the file whose `paths` match the code it governs, and each file stays under 24,000 bytes, where Antigravity cuts a rule file off; its frontmatter carries both `paths` (Claude Code) and `trigger: glob` with the same patterns quoted in `globs` (Antigravity), since either tool reads a file without its own keys as always on or not at all.

**Releases are built in CI only.** A release is made by publishing the draft `release_drafter.yml` keeps up to date, which carries the version git-cliff worked out and creates the tag; a tag pushed by hand gets a version the draft does not match. The `v*` tag runs `build_release.yml`, which publishes the wheel to PyPI and attaches a PyInstaller Windows build.

## Commands and their runs

Every `ai_coc` run is a sub-command, and the sub-commands are how the game is worked on; a smoke test against the live game is one of them run from a terminal. `cli.py`'s `_parser()` is the full reference.

**Every run gets its own directory** (`RunLog`, `~/.ai_coc/logs/<when>-<what>[-<label>]/`), and the log line `This run is being kept in` names it (the first line). It holds `run.log`, `result.json`, `frames/` (every capture under `--debug`, which every command that touches the screen takes, and without it only the frames a command keeps: `tap`, `swipe`, `confirm` and `boost`'s `after` or `refused`, `capture`'s burst, and `no_village` from `world` and `launch` when they could not find a village on a frame).

**`~/.ai_coc/runs.jsonl` is the history across runs** (`Journal` in `logging_setup.py`), kept outside `logs/` so it outlives a wipe of it. Every run writes a `start` (the line as typed, who ran it, the commit, its directory as `log`) and an `end` (exit code, outcome, and `result.json` — for `attack` only its last round, the others being on their `round` lines, and nothing when it runs past `JOURNAL_RESULT_LIMIT`, as an export does); in between come the emulator changing hands (`lock`), each attack round with its report, tactic and storages (`round`), and every warning with its trace (`warn`). Read it first for who ran what and when; a `start` with no `end` is a run that was killed or crashed. A `log` it names may be gone, which is not an error: the journal answers on its own, and the directory, where it survives, has the rest. `grep -r ~/.ai_coc/logs/*/run.log` still searches what the directories hold. The `round` line is the only record of which tactic a round played, so debug a bad battle from it before opening frames; `jq -c 'select(.event=="round" and .run=="<run directory name>" and .round==2).plan' ~/.ai_coc/runs.jsonl` pulls one back out for `--plan`.

**Frames are the only thing worth culling.** `FRAME_RETENTION_DAYS` culls `frames/` alone, rides on `RunLog.open`, and never fails the run it rides on. At the end of a task, once what the frames were evidence for is settled and nothing is running, delete them; keep the logs. Wiping `logs/` whole loses every run's full record though not the journal, so propose it rather than doing it quietly, and never delete `runs.jsonl`.

## Project rules

- **A limited-time event is not on its own a reason to build anything.** Its screens go away within weeks. If something an event shows looks worth automating, say so and let the user decide; build it when they want it.
- **There is no `CLAUDE.md`.** Claude Code reads this file by itself only while no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` sits in its working directory or above it, so adding one, a private `CLAUDE.local.md` included, hides this file from it.
- **`.claude/skills` is a symlink to `.agents/skills`**, and `.claude/rules` one to `.agents/rules`. Do not replace either link with a file. A Windows clone needs `git config core.symlinks true` and a fresh checkout of them, or they arrive as one-line text files that `end-of-file-fixer` rewrites and CI's `check-symlinks` then fails on. Make or repair one by writing the index (`git update-index --cacheinfo 120000,<blob>,<path>`), never with `ln -s`, which copies under Git Bash, or `mklink`, which stores backslashes.
- **A change that outdates a project skill updates that skill in the same PR.** Before opening the PR, grep the project skills for whatever was renamed, moved or reversed, and mention new capabilities they should know about.
- **This file and `.agents/rules/` get rules, not measurement records.** How a threshold was measured, what the previous value cost and which alternative was rejected go in the comment beside the constant (or the test that pins it). A paragraph here earns its place only as a rule an agent must follow, an invariant that spans files, or a known defect nobody has fixed; a number here is the evidence for one of those, or one a skill points at, not a record of its own. It grew from 7 KB to 235 KB between 2026-08-22 and 2026-09-25, mostly by restating those comments. A cut to this file, a file under `.agents/rules/` or a skill is checked by a reviewer holding the new text's claims against the code and reading old against new clause by clause; a diff review alone missed lost rules both times.
- **UI strings, prompts and user-facing messages are Traditional Chinese**; code, comments, commit messages and anything published to GitHub are English. The project skills are the exception for now: those written in Chinese stay Chinese and are edited in Chinese until #396 translates them (the user: 「現狀其實我蠻滿意的」).
- **Putting a decision to the user.** A choice in the game that is his (what to spend on, a goblin past the gem cap, what to do with a builder that freed up) reaches him as one push notification and a numbered list in the reply (#343): the push is one line, leading with what he would act on and saying something waits for him; the list has one item per real option, each with its price or cost, and always one to leave it (先不要動); none is marked as recommended, and no question is invented when there is nothing to decide. A choice that would expire before the report is pushed when it comes up; progress along the way is not pushed. The runtime's question tool is only for a runtime with no push. A push that comes back not sent usually means he is at the terminal, so the reply always carries everything too, and says so when he asked to be notified and the push did not go out.
- **Send the user every image you look at.** They cannot see your tool output, and a path they have to open themselves is one they will not open.
- **Debug from the screen, not from the log.** A failure that depends on what the game or the emulator was showing is settled by frames of it (`--debug`, `ai_coc capture`, or `repair-emulator`'s `look.py` when the emulator is the suspect), not reconstructed from `run.log` or logcat.
