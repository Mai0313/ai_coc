# AGENTS.md

This file provides guidance to every coding agent working in this repository.

## What this is

A Windows-only PyQt5 desktop app that drives Clash of Clans inside MuMu Player 12 or LDPlayer 14 (雷電). **The parsers read the screen, and Gemini answers two narrow questions**: how to attack a home village opponent that already passed the loot thresholds (`_plan`, once per battle), and how to attack a builder base (`_night_plan`, once per stage). Everything else — prices, card counts, storage bars, which village is up, whether a drop landed — is pixels. The 主控 tab runs the same `commands.*` functions the CLI does; the user calls this PyQt5 window the "TUI", and it is to be removed (#426).

**Where the reasoning lives.** The code says what is. The comments and docstrings in `src/`, and the tests that pin each threshold, say why a value is what it is and which measurement set it. This file holds the rules that no single comment can, and `.agents/architecture.md` the map of the code and the rules for it. Before changing a constant, read its comment and grep `src/` and `tests/` for its name: most were set by a battle that went wrong, and changing one back reopens that bug. A new measurement goes into the comment beside the constant it sets, not here.

**Everything an agent has to follow lives in the repo**: this file, `.agents/architecture.md`, the skills under `.agents/skills/`, and the code. Codex, Antigravity and every other agent read the repo, not one runtime's private memory or rules directory, so a rule kept only there is a rule they break. Write it here, into `.agents/architecture.md` when it is about the code, or into the skill that owns it; private notes keep one machine's history and nothing more.

## Driving the game

Six skills under `.agents/skills/` own the judgement of driving the game, and they are the only copy of those rules; a rule written here as well would drift. They are `farm`, `upgrades`, `takeover`, `watch-and-fix`, `repair-emulator` and `game-update`, and each one's description says when it applies. By default farming ends at `stock_full` with a report, and the loot is spent only when the user asked for that.

`.agents/skills/farm/references/running.md` owns the mechanics the skills that run a loop share: which commands run in the background, why a subagent blocks instead, what `result.json` holds, how a loop is stopped and when that is safe.

**Every session farms while it works, through one subagent.** This is the user's standing instruction: thinking, edits, test runs and reviews are all time the emulator could spend on a battle, whatever the task. Spawn **one** `farm` subagent — in the background, named so it can be messaged, **one model step down and no further**, with a lowered thinking budget where the runtime offers one (how low is the spawner's call), and told it is a subagent so it blocks the way `running.md` says. The brief carries what the user said about spending, since the subagent never sees his words: walls are bought only when he named them. Both villages are farmed, and every command it runs carries `--yield`, so a live test borrows the emulator from it instead of stopping it, and it never stands a test down. Spawn none while the user is playing on the emulator or has said not to drive the game (the user's call of 2026-10-12: 「不要控制遊戲 因為我要打部落戰」); nothing drives it then until he says so. Under `game-update` it waits until the village reads again (below).

**One farmer at a time, across sessions.** A `state.json` whose `emulator` holder is another session's yielding run (`yields: true`), or that carries a standing loan (`loan.ended` null) lent by another session, or whose `watch` another session started with a `--mission` naming 全天候託管 (`takeover` sleeping between its trips), is somebody already farming, so spawn nobody and say so in the reply. A second yielding loop would queue behind the first and then take turns with it between commands, each one's `world --go` sailing the other's next `attack` to the wrong village.

**Fixing and repairing is the dispatching session's job.** A subagent that hits a bug, or finds the emulator will not come up, stops and reports to the session that dispatched it (`farm`'s 途中撞到 bug), changing no code and repairing nothing; that session decides whether to take it into `watch-and-fix`, `repair-emulator` or `game-update`. Under `takeover` it does so without waiting for the user, who is usually away and would otherwise come back to a loop that stopped hours ago (the user's call of 2026-10-16).

**A stop the user orders is run by whoever hears it.** The session the user said it to runs `ai_coc stop` itself, and a subagent that hears one does the same; passing the order on to the farm subagent is not enough, because a subagent blocked inside a command reads no message until that command returns. The user prefers the main session to run it. One stop ends both the command on the emulator and the upgrade watch (the user's call of 2026-10-12); only a standing loan waits for a second stop once the borrowing command has ended, since a stop that finds a command running stops only that command. `running.md`'s 中止 section says what the stopped subagent does next.

**The loop runs the main checkout; the change is made somewhere else.** The subagent runs from the main checkout, which stays on the default branch, with every command as `uv run --no-sync ai_coc …`, and the work happens in a separate worktree with its own `uv sync`. A branch switch in the loop's checkout changes the code its next command runs, and on Windows a sync there fails with os error 32 while the loop's `ai_coc.exe` is running, or a sleeping `ai_coc watch`'s: a plain `uv run` does sync after `pyproject.toml` or `uv.lock` moved, which a merge pulling in a dependabot bump does, and that takes `ai_coc stop` down with it. So the loop does not pick up a merged fix by itself; `running.md` says who pulls it in. Anything run from the main checkout, `stop` and `giveback` included, is `uv run --no-sync` for the same reason. A branch that changes `AppConfig` runs no `ai_coc` command that reads the settings file (every one that touches the emulator does) while the loop is up: loading it rewrites the shared `~/.ai_coc/config.json` to the branch's shape (`adapters/config.py`), and the loop in the main checkout reads the same file.

**`watch-and-fix` is an exception, and only to the delegating half of that rule**: it still farms, but there the loop is the task, so that skill decides whether to drive the loop itself or hand it to a `farm` subagent, and a user who says 「你親自監督執行」 settles it. **`game-update` defers the farm subagent** until the village and its storages read again: before that every round ends `no_attack_menu` and the series ends itself, and exploring the new UI drives the emulator between every one of its commands.

**Taking the game for a live test.** There is one emulator, so a test and the loop cannot both drive it. Take it whenever a test needs it and give it back afterwards, without asking either time, the way `running.md`'s 「你自己要用畫面」 says. Two rules it does not hold:

- A test spends nothing the user has not asked to spend. Testing `confirm` buys what it confirms, so a wall still needs him to have named walls (「順便測試升級牆壁」 is that); otherwise list walls among the options in the reply rather than buying one.
- **The user sometimes plays on the same emulator.** Park it with `ai_coc view --zoom out` before the first live test of a piece of work (the user's call of 2026-10-07). A test that finds no village (a battle on screen, `not_a_village`), or a game that changes between two of your taps with nothing of yours to explain it, may be the user mid-game: take a frame with `ai_coc capture`, send it, and ask before trying again.

**Look before driving.** Before the first command of any piece of work, read `~/.ai_coc/state.json`. The file is a lock: a command that drives the emulator stands a live holder down first (see `.agents/architecture.md`'s "Stopping and the state file"), so `running` or `stopping` there is somebody's run your command would end, or borrow from when it yields. A record whose process is gone is residue the claim takes over by itself. The file has two sections: `emulator`, the lock, and `watch`, the `ai_coc watch` process sleeping on the upgrade timers; a new watch takes over a live one, naming itself as `stop_by`. `read`, `stop`, `giveback`, `watch`, `capture` and a plain `world` never claim and are safe beside a loop. Never test a pid with `os.kill(pid, 0)`: on Windows signal 0 is `CTRL_C_EVENT`, so it sends a Ctrl+C to that console group, can kill the run it asked about, and still reads as alive.

**Say who is driving.** Every `ai_coc` command an agent runs carries `--agent` (its own name: `claude-code`, `antigravity`, `codex`), `--session` (its own session id) and `--mission` (one line on what the run is for). A command that claims the emulator writes them into `state.json`'s `caller`, which therefore always names whoever started the run holding it; every command, `stop` and `read` included, writes them into its own `run.log` on the line after the one naming its directory, and `stop` records its caller on the file as `stop_by`, which the `idle` record the stopped run ends with keeps.

**Two drivers the file's `emulator` section does not show** (both bit on 2026-09-21):

- A **monitor** session re-running `ai_coc status` reads `idle` between runs, because what loops is an agent rather than a process. It sleeps between reads on `ai_coc watch --next <wake> --about …` in the background, which is the timer that wakes it (on a runtime whose background commands wake nobody, the record beside a schedule of its own, as `running.md` says) and the process the file's `watch` section names, so `ai_coc stop` reaches it; a monitor that sleeps any other way can only be stopped by killing it. Each of its reads borrows from a yielding loop, which then waits for a `giveback` or `LOAN_TIME`.
- **The user playing on their phone** logs the emulator out. A run that cannot reach a village while somebody might be playing is a reason to stop and say so, not to retry. The game says so on the dropped-session sheet (另一部裝置正在連接到這座村莊), and `session_taken` tells it from the dropped sessions a restart answers: the attack loop ends its series `session_taken`, mid-battle included, and `_home` and `_settle_game` stand down instead of restarting. Starting any command still logs the emulator back in (`ensure_coc`'s launch, measured 2026-10-09), so after a `session_taken` nothing runs until the user says so (the user's call of 2026-10-09: stop and notify, never take the session back). A borrower whose command stood down on it runs `ai_coc stop` rather than `giveback`: a giveback, or the loan lapsing, lets the lender's queued command through.

**Check what subagents leave behind yourself; their word is not evidence.** Before calling a task finished: `state.json`'s `emulator` back to `idle`, no `ai_coc` process, no shell left polling; a watch left sleeping on purpose is one to name. Say out loud what stays deliberately; kill and name the rest. A wait with no upper bound cannot end on its own; `running.md` owns what a wait looks like.

## Development flow

Read `gh-dev-flow` before starting. In this repo the path always ends the same way: open the PR as a draft, run `code-review` over the branch and fix what holds up, then merge once CI is green. Merging on green needs no further approval.

This file, `.agents/architecture.md` and the project skills are the agent's to edit: the user judges the project from the player's side and leaves its code and documents to the agent. Update them in the same PR as the change that outdates them without showing the text first, and say in the reply what changed for the user.

**Before changing, planning or reviewing anything under `src/`, `tests/`, the workflows, the build, `pyproject.toml`, `.pre-commit-config.yaml` or the READMEs, read `.agents/architecture.md`.** Nothing loads it at startup: it holds the map of the code, the invariants that span files, the known defects, the development commands and the rules for code.

**Releases are built in CI only.** A release is made by publishing the draft `release_drafter.yml` keeps up to date, which carries the version git-cliff worked out and creates the tag; a tag pushed by hand gets a version the draft does not match. The `v*` tag runs `build_release.yml`, which publishes the wheel to PyPI and attaches a PyInstaller Windows build.

## Commands and their runs

`uv run ai_coc` opens the window and takes no flags. The sub-commands run headless, and they are how the game is worked on; a smoke test against the live game is one of them run from a terminal. `cli.py`'s `_parser()` is the full reference.

**Every run gets its own directory** (`RunLog`, `~/.ai_coc/logs/<when>-<what>[-<label>]/`), from the CLI and the window alike, and the log line `This run is being kept in` names it (the first line, unless a frame cull was logged ahead of it). It holds `run.log`, `result.json`, `frames/` when asked for (`--debug`; `world` and `launch`, which have no `--debug`, keep `frames/no_village.png` when they could not find a village on a frame, and log its path), and for `attack` a `plans.jsonl` with one line per round carrying the tactic that round played; `jq -c 'select(.round==2).plan'` pulls one back out for `--plan`. Nothing else records which line a round drew, so debug a bad battle from `plans.jsonl` before opening frames. There is no merged log: the directory listing is the history, and `grep -r ~/.ai_coc/logs/*/run.log` searches across runs.

**Frames are the only thing worth culling.** `FRAME_RETENTION_DAYS` culls `frames/` alone, rides on `RunLog.open`, and never fails the run it rides on. At the end of a task, once what the frames were evidence for is settled and nothing is running, delete them; keep the logs, which are this machine's history. Wiping `logs/` whole throws that history away, so propose it rather than doing it quietly.

## Project rules

- **A limited-time event is not on its own a reason to build anything.** Its screens go away within weeks. If something an event shows looks worth automating, say so and let the user decide; build it when they want it.
- **`CLAUDE.md` is a symlink to this file**, and `.claude/skills` one to `.agents/skills`. Do not replace either link with a file. A Windows clone needs `git config core.symlinks true` and a fresh checkout of both, or they arrive as one-line text files that `end-of-file-fixer` rewrites and CI's `check-symlinks` then fails on. Make or repair one by writing the index (`git update-index --cacheinfo 120000,<blob>,<path>`), never with `ln -s`, which copies under Git Bash, or `mklink`, which stores backslashes.
- **A change that outdates a project skill updates that skill in the same PR.** Before opening the PR, grep the project skills for whatever was renamed, moved or reversed, and mention new capabilities they should know about.
- **This file and `.agents/architecture.md` get rules, not measurement records.** How a threshold was measured, what the previous value cost and which alternative was rejected go in the comment beside the constant (or the test that pins it). A paragraph here earns its place only as a rule an agent must follow, an invariant that spans files, or a known defect nobody has fixed; a number here is the evidence for one of those, or one a skill points at, not a record of its own. It grew from 7 KB to 235 KB between 2026-08-22 and 2026-09-25, mostly by restating those comments. A cut to this file, `.agents/architecture.md` or a skill is checked by a reviewer holding the new text's claims against the code and reading old against new clause by clause; a diff review alone missed lost rules both times.
- **UI strings, prompts and user-facing messages are Traditional Chinese**; code, comments, commit messages and anything published to GitHub are English. The project skills are the exception for now: those written in Chinese stay Chinese and are edited in Chinese until #396 translates them (the user: 「現狀其實我蠻滿意的」).
- **Send the user every image you look at.** They cannot see your tool output, and a path they have to open themselves is one they will not open.
- **Debug from the screen, not from the log.** A failure that depends on what the game or the emulator was showing is settled by frames of it (`--debug`, `ai_coc capture`, or `repair-emulator`'s `look.py` when the emulator is the suspect), not reconstructed from `run.log` or logcat. The user asked for this on 2026-09-26, after a launch failure was chased through logcat instead of looked at.
